## 1. R — 아키타입 규칙 (25 · 폐기 9, 투자관점별)

> 접두 — `INC`=`income` · `OWN`=`owner_occupied` · `DEV`=`development` ·
> `OPR`=`operating` · `TRD`=`trading`.
> 기존 `R01~R09`는 `R-INC-01~09`로 개명되었고 원 코드는 폐기입니다.

### 1.0 v0.5 — `R-INC-02` 중복 정의 해소 🔴

`R-INC-02`가 **두 문서에서 다른 뜻**이었습니다.

| 문서 | R-INC-02 | R-INC-03 | R-INC-04 |
|---|---|---|---|
| 이 문서 §1.1 (v0.4) | 밸류애드형 | 쾌속개발형 | *[확인 필요]* |
| `CATALOG_ASSET_TYPES` §3.2 | **임대료 정상화형** | **공실 해소형** | **리모델링형** |

`L02`가 `R-INC-02`를 조건으로 편성을 바꾸므로, 어느 정의를 읽느냐에 따라
**당산동(임대료 정상화)에 가치 상승 실행 계획이 편성**되거나 그 반대가 됩니다.

**이 문서를 정본으로 하고, `CATALOG_ASSET_TYPES` §3.2의 정의는 `R-INC-04~06`으로
이관합니다.** 그 세 자리는 마침 `[v0.1 원본 확인 필요]` 공란이었고, 실증 근거가 있는
정의로 채우는 편이 빈칸으로 두는 것보다 낫습니다. 원본이 나오면 충돌 여부를 확인합니다.

### 1.0.1 v0.5 — 라벨 교정

`초안정`은 근거 없는 단정이라 금지어이고, `밸류애드`는 `가치 상승 여력`으로 치환합니다
(`CATALOG_LEXICON.md` §7). **아키타입 이름은 M01~M04 마스크를 타고 IM 문장이 되므로
`internal_label` 범위에 해당합니다.**

| 코드 | v0.4 라벨 | **v0.5 라벨** |
|---|---|---|
| `R-INC-01` | 초안정 수익형 | **임대 안정형** |
| `R-INC-02` | 밸류애드형 | **가치 상승 여력형** |

**코드는 그대로 둡니다.** 코드를 바꾸면 과거 IM의 해석이 사후에 바뀝니다.

## 2. T · P — 임대차 · 필지 규칙

### 2.1 T — 임대차 법적 지위 (v0.4에서 **상가·주택 분기**)

> **v0.4 파괴적 변경.** v0.2~v0.3의 `T01~T06`은 상가건물임대차보호법만 가정했습니다.
> 다가구·상가주택·주거용 오피스텔은 **주택임대차보호법**이 적용되며 판정이 전혀 다릅니다.
> `T01~T06` → **`T-C-01~06`** 으로 개명하고 **`T-R-01~07`** 을 신설합니다.

법령 선택은 `buildingUse`가 결정합니다 (`CATALOG_ASSET_TYPES.md` §1.2). 혼합 물건은 **호실별로 분기**합니다.

```ts

export function effectiveArea(parcels: Parcel[]): number {
  return parcels.reduce((sum, p) => {
    if (p.ownership === 'shared' && p.shareNumerator == null) {
      // 🔴 지분 미상을 100%로 가정하면 대지가 과대 계상되고
```

#### G23 — 만료 경과는 공실이 아닙니다 🔴

```ts
// 상가건물임대차보호법 제10조 갱신요구권과 민법 제639조 묵시의 갱신이 있어,
// leaseState 가 '임대중' 인 한 차단하지 않고 경고합니다.
const past = rows.filter(r => r.leaseState === '임대중' && expired(r, asOf));
if (past.length / live.length > 0.5) warn('G23');
if (rows.some(r => r.leaseState === '공실' && expired(r, asOf))) block('G23');
```

만료일이 지났다고 공실로 처리하면 **실제로는 묵시 갱신으로 계속 임대 중인 호실을
공실로 표기**하게 됩니다. 수익률이 실제보다 낮게 나오고 매도인이 IM을 거부합니다.

#### G30 — 포스처 계약 미충족 시 차단

```ts
export function gateG30(doc: IMDoc): GateResult {
  const missing = unfilledContractKeys(doc.posture);   // ONTOLOGY_V0.5_SPEC §3
  return missing.length === 0
    ? { ok: true }
    : { ok: false, code: 'G30',
        message: `${doc.posture} 포스처는 계약 ${missing.length}칸이 비어 발행할 수 없습니다` };
}
```

v0.5 시점에는 **5종 전부 13/13을 채워 이 게이트를 통과합니다.**
`trading` 이 발행되지 않는 것은 G30이 아니라 **L축 R0 → D등급** 때문입니다
(`holding_history` 수집 경로 미구현). **계약 충족과 자료 충족은 다릅니다.**

계약이 빈 포스처의 IM은 등급을 매길 수도 결손을 말할 수도 없으므로 이 게이트는
남겨 둡니다 — 6번째 포스처를 붙일 때 다시 필요합니다.

### 4.3 판정 규칙

`fail`이 하나라도 있으면 발행 API가 4xx를 반환합니다. `warn`은 통과시키되 로그에 남깁니다.
`applies_to` 에 해당 포스처가 없으면 **게이트를 돌리지 않습니다** — 개발형에 NOI 검사를
돌리면 항상 실패하고, 항상 실패하는 검사는 곧 무시됩니다.

**G05 구현 주의** — 정규식으로 숫자 패턴을 찾는 방식은 오탐이 많습니다.
IR의 `Valued.band` 유무로 **타입 수준에서** 판정하십시오.

**G20 구현 주의** — 마스킹 **전** 원본을 외부 API로 보내지 않습니다. 그 사진에
임차인 상호가 찍혀 있습니다.
