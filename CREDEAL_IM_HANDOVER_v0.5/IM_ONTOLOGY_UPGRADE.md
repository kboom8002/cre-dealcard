## 0. 답

**예. 보완해야 합니다.** 그것도 "있으면 좋은" 수준이 아니라, 보완 없이는
**다른 포스처에서 D22-8 과 같은 사고가 다시 납니다.**

D22-8 에서 무슨 일이 있었는지 되짚으면 이유가 분명합니다. 다필지·제척·
토지이용계획 필터는 **이미 설계돼 있었습니다.** 그런데 계산식을 소유하던
`IM_PRECISION_SPEC.md` 가 폐기되면서 승계 문서에 한 줄도 옮겨지지 않았고,
저는 그 위에 새 스펙을 쌓았습니다. 슬롯 정의(`exclusions`)는 살아 있는데
그 값으로 무엇을 계산하는지가 사라진 상태였습니다.

그 구조가 **아직 그대로입니다.** 방금 측정했습니다.

```
CATALOG_SLOTS.md:4  → IM_PRECISION_SPEC     "계산식이 소유"      🔴 폐기 문서
CATALOG_SLOTS.md:4  → ONTOLOGY_V0.3_SPEC    "구조·원칙이 소유"   🔴 폐기 문서
CATALOG_RULES.md:4  → IM_PRECISION_SPEC     "계산식이 소유"      🔴 폐기 문서
```

살아 있는 정본 3곳이 폐기 문서를 **규칙의 주인으로 지목하고 있습니다.**
같은 사고가 다시 날 자리가 세 군데 남아 있다는 뜻입니다.

## 1. 증거 — 왜 지금 보완해야 하는가

세 가지를 실측했습니다. 어느 것도 추정이 아닙니다.

### 1.1 폐기 문서 소유 참조 3건이 살아 있습니다

폐기 선언된 문서가 8종, 살아 있는 정본이 이를 참조하는 곳이 **34건**,
그중 **"소유" 문언이 붙은 것이 3건**입니다. 나머지 31건은 정보용 인용이라
허용되지만, 소유 3건은 규칙의 주인이 무덤에 있다는 말입니다.

`qa/ontology_check.py ①` 이 매번 이것을 봅니다.

### 1.2 포스처 무관 규칙이 수익형 전용 문서에 갇혀 있습니다

| 규칙 | 지금 사는 곳 | 성격 | 문제 |
|---|---|---|---|
| 금지어 **26종** | `IM_STANDARD_수익형.md` §6 | 포스처 무관 | 개발형 IM 에서 "우량"·"확정적"을 막을 근거 없음 |
| 치환 사전 **14쌍** | 동일 | 포스처 무관 | 동일 |
| 숫자·단위 표기 | 동일 | 포스처 무관 | 동일 |
| 출처 등급 6단 | `D19 §1` (구현 규격) | 포스처 무관 | 온톨로지 `Provenance` enum 과 어긋남 |

`CATALOG_LEXICON.md` 는 라벨과 alias 만 소유하고 **금지어는 0건**입니다.
포스처 무관한 규칙을 포스처 전용 문서에 두면, 다른 포스처를 붙일 때
목록이 하나 더 생깁니다. 검사기 두 개의 금지어 교집합이 8/26 이었던 것과
정확히 같은 병입니다.

### 1.3 포스처 2종은 아키타입이 0건입니다

```
포스처              아키타입  레이아웃  제약  게이트  슬롯표
income                 11       0      0     0      ○
owner_occupied          4       1      1     0      ○
development             4       1      2     0      ○
operating               0       1      1     0      ✗   🔴
trading                 0       0      0     0      ✗   🔴
```

읽히는 것이 세 가지입니다.

- **operating · trading 은 아키타입도 슬롯 매트릭스 열도 없습니다.** 필수 슬롯이
  정의된 적이 없으니 등급을 매길 수도, 결손을 말할 수도 없습니다.
- **포스처 조건 게이트가 전 포스처 0건입니다.** 불변조건 1(운영비 없이 NOI 금지)은
  수익형·운영형에만 걸리는 규칙인데, 게이트에는 그 구분이 없어 NOI 개념이
  없는 개발형에서도 같은 검사가 돕니다.
- **income 만 전용 레이아웃 규칙과 전용 제약이 0 입니다.** 암묵적 기본값으로
  취급되고 있다는 신호입니다. 기본값이 곧 수익형이면, 다른 포스처를 붙일 때
  **무엇이 수익형 전용인지 구분할 방법이 없습니다.**

### 1.4 덧붙여 — 주력 밴드 자산에 정의 없는 Pack 3종

`CATALOG_ASSET_TYPES.md` §7 은 Pack 8종을 표로 선언하고 "상세 슬롯 정의는
`CATALOG_SLOTS.md`" 라고 가리킵니다. 그런데 `CATALOG_SLOTS.md` §3 에는
`physical_spec` · `development_plan` · `vacate_plan` · `occupancy_plan` ·
`permit_risk` **5종만** 있습니다.

정의가 없는 3종이 걸린 자산이 이렇습니다.

| 자산유형 | 필요 Pack | 정의 |
|---|---|:-:|
| `retail_strip` 근린상가·집합상가 | `sectional_spec` | **없음** |
| `knowledge_center` 지식산업센터 | `sectional_spec` | **없음** |
| `officetel` 오피스텔 | `residential_spec` · `sectional_spec` | **없음** |
| `mixed_shop_house` 상가주택 | `residential_spec` | **없음** |
| `hotel` 호텔·모텔 | `hospitality_spec` | **없음** |

🔴 **근린상가와 지식산업센터는 30억~500억 밴드의 주력입니다.** 구분등기 여부·
호실별 대지권·공동담보 그룹을 담을 슬롯이 없으면, 이 자산의 IM 은
구분소유 구조를 서술할 수 없습니다. 이것도 1.1 과 같은 실패 유형입니다 —
**포인터는 있는데 가리키는 곳에 내용이 없습니다.**

## 2. 보완 8건

전부 `credeal/ssot/im.ontology.yaml` 에 기계 판독으로 들어 있고,
`qa/ontology_check.py ⑤` 가 목표값 대비 현재값을 매번 출력합니다.

### O1 · 폐기 문서를 소유자로 지목한 참조를 회수합니다 — **차단**

- `IM_PRECISION_SPEC` 의 계산식을 `CATALOG_RULES §3`(P 코드군)으로 회수
- `ONTOLOGY_V0.3_SPEC` 참조를 `V0.4` 로 갱신
- 나머지 31건은 "참고" 로 문언을 바꿔 **소유와 구분**

> 소유와 참조를 문언으로 구분해야 검사기가 둘을 나눌 수 있습니다.
> 지금은 `'소유' in line` 하나로 판별합니다.

### O2 · CATALOG_SLOTS 를 v0.3 에서 v0.4 로 올립니다 — **차단**

- §4 매트릭스 축을 폐기된 `AssetClass`(income·owner_occupied·development·
  **land·logistics**)에서 `InvestmentPosture` 5종으로 교체
- **operating · trading 열 신설**
- 헤더 "Core 슬롯군 8" 을 실측 **9** 로 정정
- Pack 3종 정의 추가 — `residential_spec` · `sectional_spec` · `hospitality_spec`

### O3 · 어휘 규칙을 CATALOG_LEXICON 으로 승격합니다 — 중대

- `CATALOG_LEXICON` 에 `banned` · `substitutions` · `context_exclude` ·
  `negation` 절 신설 (26 · 14 · 11 · 15)
- `IM_STANDARD_수익형 §6` 은 "`CATALOG_LEXICON` 이 소유" 로 참조 전환
- `im.lexicon.yaml` 의 `owner` 를 `CATALOG_LEXICON` 으로 변경
- 숫자·단위 표기 규칙도 함께 승격

### O4 · 코드군 선언과 실측을 맞춥니다 — 중대

| 군 | 헤더 선언 | 절 제목 | 실측 | 공란 |
|---|:-:|:-:|:-:|:-:|
| R | — | — | 23 | 2 |
| C | 32 | 28 | 32 | 8 |
| G | 16 | 14 | 14 | 0 |
| L | 24 | 20 | 24 | 0 |
| M | 24 | 24 | 20 | 2 |

세 값이 갈립니다. **개수를 못 믿으면 "다 있는가" 를 물을 수 없습니다.**
공란 12건은 정의가 `[v0.1 원본 확인 필요]` 로만 남아 구현이 불가능합니다.

- 헤더 표·절 제목·실제 나열을 한 값으로 통일
- 공란 12건에 정의를 채우거나 **명시적으로 폐기** — 결번으로 두지 않습니다
- R 코드군 개수를 헤더 표에 등록 (지금 없습니다)
- 흡수를 선언한 `R-LND` · `R-LOG` 는 취소선 처리

### O5 · G 코드 자릿수를 두 자리로 통일합니다 — 중대

CATALOG 은 `G1~G16`(1자리), 레지스트리는 `G01~G26`(2자리)입니다.

> 🔴 `G1 실패` 로 grep 하면 G10~G16 이 함께 걸리고, `G01` 로 grep 하면
> CATALOG 쪽이 안 걸립니다. **장애 때 로그 검색이 갈립니다.**

`CATALOG_RULES` 의 G1~G9 를 G01~G09 로 개명하고 마이그레이션 매핑을 등록합니다.

### O6 · 포스처 조건 게이트를 신설합니다 — 중대

게이트마다 `applies_to` 를 답니다.

| 코드 | 내용 | applies_to |

| G10 | 수익률에 basis | income · operating · trading |
| G12 | 제척 합계 검증 | all |
| G22~G24 | 만료 게이트 | income · operating |

불변조건 21 에도 같은 표시를 답니다 — 어느 것이 포스처 의존인지 지금은
구분이 없습니다.

### O7 · R-OPR · R-TRD 아키타입을 정의합니다 — 중대

- 운영형 `R-OPR-01~04` · 트레이딩 `R-TRD-01~04`

- 실증 딜이 0건이므로 **가설임을 명시** — 데이터가 쌓이면 재정의

### O8 · 신규 IM 규격을 온톨로지 코드로 등록합니다 — 중대

## 5. 파이프라인 업그레이드(D23)가 온톨로지에 요구하는 것

D23 에서 도출한 보완 중 온톨로지 변경 없이는 못 하는 것이 7건입니다.

| 출처 | 요구 | 소유 문서 |
|---|---|---|
| D23 §1.1 | 운영 게이트를 `QG` 로 개명 · CATALOG `G` 는 발행 게이트 전용 | `CATALOG_RULES §4` 코드군 표 |
| D23 §2.2 | 슬롯 정의에서 **JSON Schema 를 생성**할 수 있어야 함 | `CATALOG_SLOTS` — 지금 Zod 스니펫이 산문 안에 있습니다 |
| D23 §2.4 | `Provenance` enum 에 S2a · S2b · S4 추가 | `CATALOG_SLOTS §5` |
| D23 §2.4 | 등급 8카테고리를 L축 · P축 · 축무관으로 분류 | `ONTOLOGY_V0.4 §6.1` |
| D23 §5.2 | NLG 문형(F3 · F4 · F5 · OPINION)을 M 코드군에 정의 | `CATALOG_RULES §6` — M01~M12 가 공란 |

## 7. 자동 검사 — 요구서를 문서로만 두지 않습니다

`qa/ontology_check.py` 는 ①~⑤ 를 봅니다.

```
① 폐기 문서를 소유자로 지목하는가
② 코드군 선언 개수와 실측이 맞는가 · 정의가 빈 코드가 몇 개인가

```

현재 출력 (⑤ 발췌)

```
