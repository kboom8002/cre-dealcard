## 0. 먼저 — 파이프라인은 이미 포스처를 압니다

**과장하지 않겠습니다.** 현행 파이프라인은 생각보다 잘 되어 있습니다.

| 이미 되는 것 | 근거 |
|---|---|
| `investmentPosture` 5종 추출 | 현행 명세 §2.4 |
| 포스처별 섹션 편성 7개 + 강조 2 | 동 §6.2 |
| 바텀시트 조건부 섹션 4종 (물류·운영·개발·자가) | 동 §4.3 |
| 등급에서 `income`/`operating` 렌트롤 필수 캡 | 동 §5.3 |
| 포스처별 재무 계산 · 용어집 오버레이 | 동 §6.3 |
| 할루시네이션 탐지 · LLM-as-Judge · 결정적 렌트롤 주입 | 동 §6.3 |

**"파이프라인이 포스처를 모른다"는 틀린 진단입니다.** 문제는 더 구체적입니다.

## 1. 실측 — v0.5 대비 새로 생긴 갭 8건

### 1.1 🔴 섹션이 7개인데 포스처 표준은 8~12개를 요구합니다

현행 15개 섹션 유형 = 공통 5 + 포스처 전용 10. **딜당 7개**를 씁니다.

```
공통 5    property_overview · location_access · risk_check
          investment_thesis · next_steps
포스처 2  (예: income → lease_status · income_analysis)
```

포스처 표준이 요구하는 섹션과 대조하면 이렇게 빕니다.

| 포스처 | 표준 요구 | 현행 | **없는 섹션** |
|---|:-:|:-:|---|
| `income` | 12 | 7 | 토지 상세 · 권리·등기 · 비교사례 · **확인사항** · 필지 |
| `operating` | 10 | 7 | 시설 구성 · 운영사 계약 · 용도 적법성 · 권리 · **확인사항** |
| `development` | 10 | 7 | 토지 상세 · 명도 계획 · 인허가 로드맵 · 권리 · **확인사항** |
| `owner_occupied` | 9 | 7 | 건물 스펙 · 잔여 임대 · 권리 · **확인사항** |
| `trading` | 8 | 7 | 권리 제약 · 보유 이력 · **확인사항** |

🔴 **다섯 포스처 전부에서 "확인사항"이 빠져 있습니다.**

**불변조건 13은 "결손은 사라지지 않고 확인사항으로 이동한다"입니다.**
그런데 이동할 자리가 없습니다. `risk_check`가 겸하고 있다면 **리스크와 결손이
한 면에서 섞입니다** — 매수자는 "확인이 안 된 것"과 "확인했는데 위험한 것"을
구분할 수 없습니다. 성격이 완전히 다릅니다.

| | 리스크 | 확인사항 |
|---|---|---|
| 뜻 | 알고 있는 나쁜 소식 | **아직 모르는 것** |
| 해소 주체 | 매수자의 판단 | **중개인·매도인의 자료 제출** |
| 불변조건 9 | — | **공개 단계에서도 마스킹하지 않습니다** |

### 1.2 🔴 등급 카테고리에 Pack이 없습니다

현행 8카테고리 가중치 합 100:

```
lease_roll 25 · building_basic 15 · land_parcel 15 · financial_input 15
zoning 10 · title_encumbrance 10 · road_access 5 · market_comp 5
```

**Pack 슬롯군이 하나도 없습니다.** 결과가 이렇습니다.

| 포스처 | 필수 Pack | 등급 기여 |
|---|---|:-:|
| `operating` | `operating_performance` · `hospitality_spec` | **0** |
| `development` | `development_plan` · `vacate_plan` · `permit_risk` | **0** |
| `owner_occupied` | `occupancy_plan` · `physical_spec` | **0** |
| `trading` | `holding_history` | **0** |

🔴 **운영형 물건은 3개년 실적을 다 넣어도 등급이 1점도 안 오릅니다.**
반대로 렌트롤(25점)은 운영형에 존재하지 않는데 분모에 남아 있습니다.
**운영형은 구조적으로 A를 받을 수 없습니다.**

`CATALOG_ASSET_TYPES` §6 `BASE_PROFILE`은 `hotel`에 Pack 30을 배정하는데,
구현 엔진에는 그 열이 없습니다. **문서와 코드가 갈려 있습니다.**

### 1.3 🔴 포스처를 LLM이 확정합니다

현행 §2.4 — `investmentPosture`는 **LLM 추출**입니다.

온톨로지는 다르게 말합니다.

> `investmentPosture` — **중개인이 매수자 목적에 맞춰 선택**합니다
> (`CATALOG_ASSET_TYPES` §3)
>
> **자동 판정은 제안까지만** 합니다. 복합 물건에서 자동 판정은 반드시 틀리고,
> 틀린 판정은 IM 전체 구성을 바꿉니다 (`ONTOLOGY_V0.5_SPEC` §4 유효 조합)

**같은 물건도 관점에 따라 다른 IM이 나옵니다.** 잠원동과 당산동은 법정 용도·시장
유형이 같고 포스처만 다른데 IM이 완전히 달랐습니다. 메모에 그 정보가 없으면
LLM은 **가장 흔한 값을 찍습니다.**

> 🔴 `MIGRATION_RUNBOOK` §8 · D10 §10.1 — **"현재 62건 전부 income"이
> 기본값의 결과일 수 있습니다.** 단계 0에서 기본값을 제거한 뒤 30일 재관측이
> 필요하다고 이미 적혀 있습니다. **LLM 추출도 같은 성격의 기본값입니다.**

### 1.4 🔴 `Provenance` 5종이고 이름도 다릅니다

| 현행 | 계수 | 온톨로지 v0.5 |
|---|:-:|---|
| `public_data` | 1.00 | `registry` 1.00 **+ `public_api` 0.95** (분할 필요) |
| `expert_verified` | 0.95 | `expert` 0.95 |
| `seller_declared` | 0.65 | `seller` 0.65 |
| `broker_input` | 0.60 | `broker` 0.60 |
| `ai_inferred` | 0.30 | `assumed` 0.30 |
| — | — | **`broker_aug` 0.80** (없음) |
| — | — | **`ledger` 0.70** (없음) |
| — | — | **`derived` 최약 고리** (없음) |

**`derived`가 없는 것이 가장 큽니다.** 파생값에 입력보다 높은 신뢰도가 붙는 것을
막는 장치가 타입 수준에 없습니다 (제약 `C21`).

**`ai_inferred`라는 이름도 문제입니다.** 가정값(공사비 단가·지가 변동률)은
AI가 추론한 것이 아니라 **사람이 정한 시장 기본값**입니다
(`ASSUMPTION_REGISTRY`). 이름이 출처를 왜곡합니다.

### 1.5 등급 임계가 점수인데 v0.5는 L×P입니다

```
현행   A ≥ 75점 · B 40~74 · C < 40
v0.5   A = L≥R2 ∧ P≥P2 · B = L≥R1 ∧ P≥P2 · C = L≥R1 ∧ P=P1 · D = L=R0 ∨ P=P0
```

**점수가 같아도 원인이 다르면 중개인이 할 일이 다릅니다.** 65점이 "공부는 다
있는데 렌트롤이 없다"인지 "렌트롤은 있는데 지번이 틀렸다"인지 구분되지 않습니다.

v0.4 가중 점수는 **폐기하지 않습니다** — 축 내부 채움률 계산에 씁니다
(`ONTOLOGY_V0.5_SPEC` §6.5). 대체가 아니라 층이 다릅니다.

### 1.6 바텀시트 조건부 섹션 4종 — 6종이 빠졌습니다

| 있는 것 | 없는 것 |
|---|---|
| 물류센터 · 운영형 · 개발형 · 자가사용 | **단기매매** · `sectional_spec` · `residential_spec` · `holding_history` · `operating_performance`(운영형과 분리) · 필지·제척 |

🔴 **`sectional_spec`이 없는 것이 실무적으로 가장 아픕니다.**
근린상가·지식산업센터는 **30억~500억 밴드의 주력**인데, 구분등기 여부·호실별
대지권·공동담보 그룹을 입력할 자리가 없습니다. 당산동에서 공동담보 중복 합산으로
32억을 16억으로 정정한 사고가 이 슬롯의 근거입니다 (`C32`).

**필지·제척 입력도 없습니다.** D22-8에서 계산은 복구했지만 **바텀시트에 입력란이
없으면 값이 영원히 비어 있습니다** (`FR35`).

### 1.7 입력 순서가 L축 우선이 아닙니다

현행 폼 순서 — 소재지 → 재무 → 임대 → 사진 → 조건부.

**개발형은 "명도 책임"이 렌트롤보다 먼저 확인할 항목입니다**
(`IM_STANDARD_개발형` §3.1). 명도 책임이 매도인이면 L≥R1로 끝나고,
매수인이면 R3까지 호실별로 받아야 합니다. **순서가 반대면 중개인이
필요 없는 것부터 30분을 씁니다.**

### 1.8 결손 되먹임이 "무엇을 채우면 되는가"까지 가지 않습니다

등급이 나오지만 **다음 한 단계**가 없습니다.

```
지금   "C등급입니다. 데이터를 보강하세요"
필요   "운영비를 입력하면 순수익률이 열립니다 (C → B)"
```

D23 §5.5가 "다음 한 단계만 말합니다"로 규정했으나 **등급 엔진이 그 계산을
하지 않습니다** — 어느 슬롯을 채우면 어느 축이 몇 %p 오르는지가 없습니다.

## 2. 완성의 정의 — 5가지가 관통해야 합니다

**단계별로 고치는 것이 아니라, 다섯 가지가 4단계를 관통해야 합니다.**

| # | 관통해야 하는 것 | 메모 | 딜카드 | 바텀시트 | IM |
|:-:|---|:-:|:-:|:-:|:-:|
| 1 | **포스처** | 제안 | **중개인 확정** | 조건부 폼 | 섹션 편성 |
| 2 | **Pack 10종** | 신호 추출 | 필수 판정 | 입력란 | 섹션·등급 |
| 3 | **L×P 등급** | — | P축 확정 | L축 확정 | 잠금·문구 |
| 4 | **Provenance 9종** | `broker` | `registry`/`public_api` | `broker_aug`/`ledger` | `derived` 승계 |
| 5 | **결손** | 미검출 | P축 결손 | L축 결손 | **확인사항 섹션** |

**하나라도 중간에 끊기면 그 뒤는 복구할 수 없습니다.**
바텀시트에 `sectional_spec` 입력란이 없으면 IM에 구분소유 구조가 나올 방법이
없습니다 — 렌더러를 아무리 고쳐도 안 됩니다.

## 3. 보완 8건

### P1 · 확인사항 섹션 신설 — **차단**

`risk_check`에서 결손을 분리합니다.

```
risk_check        알고 있는 나쁜 소식 — 매수자가 판단
checklist  🆕     아직 모르는 것 — 자료 제출로 해소
```

| 항목 | 값 |
|---|---|
| 섹션 유형 | 16번째 신설 — 전 포스처 공통 |
| 위치 | 마지막 직전 (`next_steps` 앞) |
| 마스킹 | **하지 않습니다** (불변조건 9) |
| 내용 | 결손 슬롯 · 게이트 경고 · 미확인 가정 · 잠긴 지표와 사유 |
| 잘림 | **금지** — 전량 표기 (D22-7 사고: 11건 중 8건만 렌더) |

**모든 결손은 여기로 모입니다.** 어느 단계에서 났든 사라지지 않습니다.

### P2 · 등급 엔진을 L×P로 교체 + Pack 카테고리 신설 — **차단**

```ts
// 축 배정은 포스처 계약이 정합니다 (ONTOLOGY_V0.5_SPEC §6.2)
const P_AXIS = ['land_parcel','building_basic','zoning','road_access','title_encumbrance'];
const L_AXIS = POSTURE_CONTRACT[posture].lAxisSlots;   // 포스처마다 다릅니다
// 축 무관 슬롯군은 두 축 분모에서 모두 제외 (§6.2.1)

function grade(slots, posture) {
  const p = fillRate(slots, P_AXIS);          // 가중 채움률
  const l = fillRate(slots, L_AXIS);
  return matrix(resolve(l), resolve(p));      // §6.3
}
```

Pack 카테고리를 가중치 표에 넣습니다. `BASE_PROFILE`의 Pack 단일 열을
**Pack별로 쪼개야** 하며, 행 합계 100 검증을 다시 돌립니다
(`ONTOLOGY_V0.5_SPEC` §6.5의 미해결 항목).

🔴 **임의로 쪼개지 않습니다.** 근거 없이 배분하면 등급이 이유 없이 바뀝니다.
포스처별 실증 딜에서 실측한 뒤 확정합니다.

### P3 · 포스처를 중개인이 확정 — **차단**

```
메모 추출    → 포스처 **제안** (신뢰도 함께)
딜카드 생성  → 중개인에게 확인 요구. 기본값 없음
확정 전      → 바텀시트 조건부 섹션이 뜨지 않습니다
```

| 규칙 | 이유 |
|---|---|
| **기본값을 두지 않습니다** | 기본값이 곧 분포가 됩니다 (62건 전부 income) |
| 제안 신뢰도를 보여 줍니다 | "메모에 개발 관련 표현이 3회 — 개발형 제안" |
| 확정 이력을 남깁니다 | 제안 ↔ 확정이 다른 비율이 LLM 정확도입니다 |
| 변경 시 재생성 | 포스처가 바뀌면 섹션 편성이 통째로 바뀝니다 |

**조합 매트릭스로 먼저 거릅니다** — 나대지 × `income`은 차단,
오피스텔 × `income`은 경고 (`CATALOG_ASSET_TYPES` §4).

### P4 · `Provenance` 9종 전환 — 중대

`MIGRATION_RUNBOOK` §9 V5-3이 절차를 소유합니다. 파이프라인 쪽 작업은 셋입니다.

| 단계 | 작업 |
|---|---|
| 딜카드 | 수집 경로별로 `registry` / `public_api` 분기 (`CATALOG_SLOTS` §1.3) |
| 바텀시트 | 중개인이 공공값을 고치면 `broker_aug`, 원장 업로드면 `ledger` |
| 등급·IM | 파생값에 `derived` + `inputs[]` — **최약 고리 승계** |

`ai_inferred` → `assumed` 로 개명합니다. 가정값은 AI 추론이 아니라
**사람이 정한 시장 기본값**입니다.

### P5 · 바텀시트 조건부 섹션 6종 추가 — 중대

| 신설 | 조건 | 왜 |
|---|---|---|
| **필지·제척** | 항상 (필지 ≥ 2면 확장) | `FR35` — 계산은 되는데 입력란이 없습니다 |
| **`sectional_spec`** | `assetType ∈ {retail_strip, knowledge_center, multi_family, officetel, serviced_residence}` | 🔴 주력 밴드 |
| **`residential_spec`** | `mixed_shop_house` · `multi_household` · `multi_family` · `officetel` | 위반건축물 등재 → 대출 차단 |
| **`holding_history`** | `posture = trading` | 이것이 없어 `trading`이 D등급 |
| **`operating_performance`** | `posture = operating` | 요양시설·주차장은 객실이 없습니다 |
| **단기매매 조건부** | `posture = trading` | 유일하게 빠진 포스처 |

**`sectional_spec`의 `landShareSum`은 입력 즉시 1.0 검증**합니다 (`C30`) —
나중에 게이트에서 잡으면 중개인이 그 화면을 떠난 뒤입니다.

### P6 · 입력 순서를 L축 우선으로 — 중대

**포스처가 확정되면 그 포스처의 L축부터 묻습니다.**

| posture | 첫 질문 |
|---|---|
| `income` | 임대 현황 (호실 수 → 정밀 모드 판정) |
| `development` | **명도 책임** (매도인/매수인/미정 → 최소 L이 갈립니다) |
| `operating` | 실적 몇 개년 있는가 |
| `owner_occupied` | 현 임차료·만기 |
| `trading` | 비교사례 몇 건 확보 가능한가 |

**첫 질문의 답이 나머지 폼의 길이를 정합니다.** 개발형에서 "매도인 부담"이면
호실별 렌트롤을 아예 묻지 않습니다.

### P7 · 결손 되먹임 — 다음 한 단계 — 중대

등급 엔진이 **"어느 슬롯을 채우면 어느 축이 얼마나 오르는가"** 를 반환합니다.

```ts
interface GradeResult {
  grade: 'A'|'B'|'C'|'D';
  L: LeaseResolution;  P: PropertyResolution;
  lockedMetrics: { key: MetricKey; missing: SlotKey[] }[];
  nextStep: {           // 🔴 하나만 반환합니다
    slot: SlotKey;
    unlocks: MetricKey[];
    gradeAfter: Grade;
    axis: 'L' | 'P';
  } | null;
}
```

| 원칙 | |
|---|---|
| **하나만 말합니다** | 목록을 주면 중개인이 아무것도 안 합니다 |
| 등급이 오르는 것을 우선 | 지표 하나 여는 것보다 등급 상승이 큽니다 |
| 축을 표시 | P축이면 우리 일, L축이면 중개인 일 |

### P8 · 섹션 유형 확장 — 중대

15 → **포스처 표준이 요구하는 만큼**. 공통 섹션을 늘리는 것이 효율적입니다.

| 신설 공통 | 대상 |
|---|---|
| `checklist` (P1) | 전 포스처 |
| `title_rights` 권리·등기 | 전 포스처 |
| `land_detail` 토지 상세 (필지·제척) | income · development · trading |
| `comparables` 비교사례 | income · operating · trading |

포스처 전용은 표준 문서가 정합니다. **섹션을 늘리면 생성 시간이 늘어나므로
D13 병렬화가 선행**입니다 (D26 §6.2).

## 4. 착수 순서

```
0  D13 섹션 병렬화              ← 섹션을 늘리기 전에 시간을 확보합니다
   │
1  P3 포스처 중개인 확정        ← 이것이 확정돼야 나머지가 분기합니다
   │
2  P5 바텀시트 6종  ─┬─ P6 입력 순서
   │                └─ P1 확인사항 섹션
   │
3  P4 Provenance 9종            ← 마이그레이션 V5-3 과 동시
   │
4  P2 등급 L×P + Pack 카테고리  🔴 되돌릴 수 없음 (V5-4)
   │
5  P7 결손 되먹임               ← 등급 엔진 교체 뒤
   │
6  P8 섹션 유형 확장
```

**0번이 먼저인 이유** — 현행 122초는 이미 한계 2초 초과입니다.
섹션을 늘리면 확실히 실패합니다 (불변조건 15).

**1번이 먼저인 이유** — 포스처가 LLM 기본값이면 P5·P6·P8이 전부
income 경로로만 검증됩니다. **잘못된 분포 위에서 테스트하면 통과합니다.**

---

## 5. 이 규격으로도 안 되는 것

| 항목 | 왜 |
|---|---|
| 🔴 **이미지 마스킹** | 검출 모델이 필요합니다. P1~P8 어디에도 해법이 없습니다 |
| Pack 가중치 배분 | 포스처별 실증이 쌓여야 근거가 생깁니다 |
| `trading` 발행 | `holding_history` **수집**(등기부 파싱)이 P5(입력란)와 별개입니다 |
| `QG01~QG16` | 운영 코드를 읽어야 합니다 |
| 포스처 제안 정확도 | 확정 이력이 쌓이기 전까지 측정할 수 없습니다 |
