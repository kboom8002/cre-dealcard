#### 모바일 명세가 통째로 비어 있습니다

8개 명세 문서에 PPTX 매핑은 A01~A15까지 상세한데, **모바일 화면 구조는 한 줄도 없습니다.** `im-lite/page.tsx`가 아키텍처 다이어그램에만 등장합니다.

**주 배포 채널의 명세가 없는 상태입니다.**

### 1.4 파이프라인이 해결할 수 없는 것

정직하게 적습니다. 공수를 더 써도 안 되는 항목입니다.

| 항목 | 이유 | 대응 |
|---|---|---|
| **NOI (운영비)** | 매도인이 관리비 내역을 주지 않으면 끝 | `gross` 계열만 산출 · NOI 미표기 |
| **대출 가능액** | 은행 감정가가 결정 | 시나리오만 제시 + 주의 문구 |
| **최초 계약일** | 계약서를 봐야 앎 · API 없음 | 렌트롤 양식으로 수집 |
| **소형 상업용 comps** | 실거래가 API 커버리지 낮음 | `manual_comps` 중개인 입력 (이미 있음) |

**이것들은 결손으로 표시하는 것이 정답입니다.** 만들어내면 안 됩니다.

## 2. 질문 ② — Basic/Pro 통일

### 2.1 결론

**통일에 찬성합니다. 단, "합치는" 것이 아니라 "축을 분리하는" 방식입니다.**

Basic/Pro라는 라벨 하나가 **성격이 다른 세 가지 일**을 동시에 하고 있습니다.

| 축 | 현행 동작 | 실제 성격 | 올바른 소관 |
|---|---|---|---|
| **(a) 노출 통제** | 블라인드 티저 → 실명 정보 | 협상·개인정보 | **노출 마스크** |
| (b) 완성도 단계 | 자료 부족 → 완비 | 자료 해상도 | **R1~R3 체계** |
| (c) 발행 게이트 | B등급이면 Pro 차단 | 자료 충분성 | **DeficiencyLedger** |

**(b)(c)는 해상도 체계가 이미 담당합니다.** Basic/Pro에 남는 일은 **(a) 하나뿐**입니다.

그리고 노출 통제는 **버전이 아니라 같은 문서에 씌우는 필터**입니다.

```
현행:  Basic 문서  ≠  Pro 문서        (두 벌 제작 · 두 벌 유지 · 두 벌 검증)
개선:  골디락스 문서 하나  +  노출 마스크 2단
```

### 2.2 근거 — R1에서도 12p가 나옵니다

당산동을 해상도별로 시뮬레이션했습니다.

| 해상도 | PPTX | 확인사항 | 미산출 지표 |
|---|:-:|:-:|---|
| **R1 (현재 자료)** | **12p** | 5줄 | 환산보증금·갱신권·명도계획·임대료정상화·NOI |
| R2 | 13p | 3줄 | 갱신권·명도계획·NOI |
| R3 + 등기·운영비 | 15p | 0줄 | — |

**자료가 부족해도 12페이지가 나옵니다.** 확인사항이 5줄 붙을 뿐입니다.

그렇다면 **"Basic은 축약본, Pro는 완전본"이라는 구분 자체가 성립하지 않습니다.** 문서는 하나이고 채워진 정도만 다릅니다.

### 2.3 통합 아키텍처

```
                    ┌─────────────────────────┐
                    │   콘텐츠 코어 (1개)       │
                    │  · 검증된 수치 (anchors) │
                    │  · 12섹션 본문           │
                    │  · DeficiencyLedger     │
                    └───────────┬─────────────┘
                                │
              ┌─────────────────┴─────────────────┐
              ▼                                   ▼
      ┌───────────────┐                  ┌───────────────┐
      │ PPTX 렌더      │                  │ 모바일 렌더     │
      │ (앉아서 검토)   │                  │ (카톡 · 30초)  │
      └───────┬───────┘                  └───────┬───────┘
              │                                   │
        ┌─────┴─────┐                       ┌─────┴─────┐
        ▼           ▼                       ▼           ▼
    공개 마스크   전체공개                 공개 마스크   전체공개
```

**한 번 만들고 한 번 검증합니다.** 산출물 4종은 같은 코어에서 나옵니다.

| 현행 | 개선 |
|---|---|
| Basic PPTX · Pro PPTX · Basic 모바일 · Pro 모바일 = **4벌 제작** | 코어 1벌 → **4벌 렌더** |
| 재발행 시 4벌 동기화 | 코어만 갱신 |
| 검증 4회 | 검증 1회 |
| 수치 불일치 위험 4×3 조합 | 없음 |

### 2.4 노출 마스크 정의

**숨기는 것이 아니라 밴딩(banding)합니다.** 빈칸을 남기면 매수인이 불신합니다.

| 슬롯 | 공개 마스크 | 전체 공개 |
|---|---|---|
| 소재지 | **당산동 일대** | 당산동5가 11-47 |
| 임차인 상호 | **병원·약국 등 생활밀착 업종** | 고은약국·로뎀나무내과 |
| 호실별 금액 | **총액만** (보증금 2.9억 / 월세 1,946만) | 호실별 전체 |
| 계약 만료일 | **"60일 내 만료 4건"** | 호실별 날짜 |
| 매매가 | 밴드 **110~120억** | 115억 |
| 공부 첨부 | ✗ | ○ |
| 확인사항 | **○ 동일 노출** | ○ |

#### 🔴 확인사항은 마스킹하지 않습니다

**결손 표시는 공개 단계에서도 그대로 보여줍니다.** 이것이 신뢰를 만드는 요소이므로 가릴 이유가 없습니다.

```ts
export function applyMask(core: IMCore, level: 'public' | 'full'): IMRendered {
  if (level === 'full') return render(core);
  return render({
    ...core,
    address:    bandAddress(core.address),        // 지번 → 동
    leases:     aggregateLeases(core.leases),     // 호실별 → 총액
    price:      bandPrice(core.price),            // 정확값 → 밴드
    attachments: [],                              // 공부 제외
    deficiencies: core.deficiencies,              // ★ 그대로 노출
  });
}
```

### 2.5 마스크 해제 조건

| 단계 | 조건 | 획득 |
|---|---|---|
| 공개 | 없음 | 밴딩된 골디락스 IM |
| **전체 공개** | 이름 · 연락처 · 매수 주체(개인/법인) | 지번 · 호실별 · 공부 |

**NDA는 마스크 해제 조건이 아니라 별도 계약**으로 분리합니다. 실사 자료(계약서 사본·등기부 원본)를 받을 때 필요하지, IM을 보는 데 필요하지 않습니다.

> 현행 `next_steps`의 "1단계 NDA 체결"이 문턱을 지나치게 높입니다. 50~60대 매수인은 관심 단계에서 NDA를 요구받으면 이탈합니다.

## 3. 통일의 이득과 위험

### 3.1 이득

| # | 이득 |
|:-:|---|
| 1 | **수치 불일치가 구조적으로 불가능** — 코어가 하나 |
| 2 | 재발행 시 코어만 갱신 · 4벌 동기화 불필요 |
| 3 | 덱 시퀀서에서 `tier` 축 제거 → 조합 수 절반 |
| 4 | 등급→tier 게이트 제거 → **B등급도 완전한 IM** |
| 5 | 중개인이 "어느 버전을 보낼까" 고민할 필요 없음 |
| 6 | 검증 1회로 축소 |

### 3.2 위험과 대응

| 위험 | 대응 |
|---|---|
| **공개용이 너무 상세해 협상력 상실** | 밴딩 강도를 조절 가능하게 · 매도인이 선택 |
| **밴딩된 값이 실제와 어긋남** | `assertBandContains(band, actual)` 단위 테스트 강제 |
| 마스크 누락으로 지번 노출 | 슬롯별 `visibility` 필수 선언 · 미선언 시 **렌더 거부** |
| 확인사항이 공개돼 물건이 나빠 보임 | **의도된 설계** — 결손 표시가 신뢰를 만듭니다 |
| Pro 전용 기능 상실 우려 | 없음 — Pro의 실체는 마스크 해제뿐 |

### 3.3 🔴 남겨야 할 구분 하나

**PPTX와 모바일은 통일하지 않습니다.**

| | PPTX | 모바일 |
|---|---|---|
| 독자 상태 | 앉아서 검토 | 이동 중 30초 |
| 목적 | 판단 | 다음 단계로 넘길지 결정 |
| 분량 | 12p | 첫 화면 + 접힘 5 |

**모바일을 PPTX 축약본으로 만들면 실패합니다.** 같은 코어를 쓰되 렌더 전략이 다릅니다.

## 5. 요약 답변

### ① 골디락스를 만들 수 있는가

**27일로는 12p 중 7p입니다.** 투자 구조 슬라이드(A16)와 모바일 명세가 통째로 없어 **총 42일**이 필요합니다.

다만 **파이프라인 골격은 재설계가 필요 없습니다.** 결정론적 렌트롤 주입·numericalAnchors·basis-enforcer·비중복 렌더링 원칙은 그대로 쓰면 됩니다. 산식을 고치고 화면 두 개를 만드는 일입니다.

**운영비·감정가·최초계약일·소형 comps는 파이프라인으로 해결되지 않습니다.** 결손으로 표시하는 것이 정답입니다.

### ② Basic/Pro를 통일할 것인가

**통일에 찬성합니다.** 다만 두 문서를 합치는 것이 아니라, **Basic/Pro가 떠맡고 있던 세 가지 일을 분리**하는 것입니다.

```
Basic/Pro  ─┬─ (a) 노출 통제  → 노출 마스크 (유지 · 라벨만 변경)
            ├─ (b) 완성도     → R1~R3 해상도 체계 (이관)
            └─ (c) 발행 게이트 → DeficiencyLedger (이관)
```

**(b)(c)를 이관하고 나면 Basic/Pro는 마스크 이름일 뿐이므로, "골디락스 IM + 공개/전체공개"로 부르는 편이 정확합니다.**

핵심 근거는 하나입니다 — **R1 자료로도 12페이지가 나옵니다.** 축약본을 따로 만들 이유가 없습니다.
