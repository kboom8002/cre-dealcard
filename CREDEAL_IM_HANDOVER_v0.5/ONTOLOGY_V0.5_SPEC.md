## 0. 왜 또 바꾸는가

### 0.1 v0.4가 남긴 것

v0.4는 `AssetClass` 하나에 눌려 있던 세 가지를 분리했습니다. 그 판단은 옳았고 유지합니다.
문제는 **분리한 뒤에 생긴 빈칸**입니다.

포스처가 5종이 되었는데, **새 포스처를 붙일 때 무엇을 채워야 하는지가 어디에도 없었습니다.**
그 결과가 이렇습니다.

```
포스처              아키타입  레이아웃  제약  게이트  슬롯표
income                 11       0      0     0      ○
owner_occupied          4       1      1     0      ○
development             4       1      2     0      ○
operating               0       1      1     0      ✗
trading                 0       0      0     0      ✗
```

`operating` · `trading` 은 v0.4에서 **신설했는데 필수 슬롯이 정의된 적이 없습니다.**
`income` 은 전용 레이아웃 규칙도 전용 제약도 0입니다 — 암묵적 기본값이라는 뜻이고,
기본값이 곧 수익형이면 **다른 포스처를 붙일 때 무엇이 수익형 전용인지 구분할 수 없습니다.**

### 0.2 D22-8이 드러낸 진짜 원인

다필지·제척·토지이용계획 필터는 **이미 설계돼 있었습니다.** 슬롯(`exclusions`)은 살아 있었는데
[HIST] 계산식을 소유하던 `IM_PRECISION_SPEC.md`가 폐기되면서 승계 문서에 한 줄도 옮겨지지 않았고,
그 위에 새 스펙이 쌓였습니다.

**살아 있는 정본이 폐기 문서를 규칙의 주인으로 가리키고 있었기 때문**입니다.
v0.4 시점에 3곳이 그랬습니다.

```
[HIST] v0.4 시점 실측 — v0.5에서 전부 회수했습니다
[HIST] CATALOG_SLOTS.md:4  → IM_PRECISION_SPEC     "계산식이 소유"
[HIST] CATALOG_SLOTS.md:4  → ONTOLOGY_V0.3_SPEC    "구조·원칙이 소유"
[HIST] CATALOG_RULES.md:4  → IM_PRECISION_SPEC     "계산식이 소유"
```

회고로 폐기 문서를 언급해야 하는 줄에는 **`[HIST]` 태그**를 답니다.
`qa/ontology_check.py ①` 이 태그 없는 소유 지목만 위반으로 셉니다.
어절 기반 예외(“…않습니다”)는 한국어에서 사실상 전면 면제가 되어 폐기했습니다.

### 0.3 온톨로지 스스로 자기 규칙을 어기고 있습니다

가장 아픈 실측입니다.

| 위치 | 문언 | 위반 |
|---|---|---|
| `CATALOG_RULES` §1.1 | R-INC-01 **초안정** 수익형 | `초안정` 은 근거 없는 단정 — 금지어 |
| `CATALOG_RULES` §1.1 | R-INC-02 **밸류애드**형 | `밸류애드` → `가치 상승 여력` 치환 대상 |
| `CATALOG_RULES` §5.1 | L02 → **밸류애드** 실행 계획 편성 | 동일 |
| `CATALOG_ASSET_TYPES` §3.2 | R-INC-01 **초안정**형 | 동일 |

수익형 전용 문서(`IM_STANDARD_수익형` §6)에 갇혀 있어서, 온톨로지를 쓰는 사람은
그런 규칙이 있는 줄 몰랐습니다. §8이 이것을 다룹니다.

## 2. 층위 소유 규칙 🆕

**새 규칙을 만들 때 여기부터 봅니다.** 층을 잘못 고르면 다른 포스처로 확장할 때
반드시 다시 만들게 됩니다.

| 층 | 담는 것 | 판별 질문 | 정본 |
|---|---|---|---|
| **1 · 온톨로지** | 슬롯·enum · 코드 공간 · 어휘 · 출처 등급 · 등급 체계 · 변경 절차 | **"개발형에서도 참인가?" → 예** | `CATALOG_*` 4종 + 이 문서 |
| **2 · 포스처 표준** | 섹션 구성 · 강조 섹션 · 수익률 기준 조합 · 필수 요소 · 분량 | **"이 포스처에서만 참인가?" → 예** | 포스처 표준 5종 (§3.3) |
| **3 · 구현 규격** | 페이지 순서 · 프리셋 · 텍스트 예산 · 블록 게이팅 · 지면 기하 | 지면과 카피의 구체 | `D19` · `D22` 세트 |
| **4 · 기계 판독** | 위 세 층의 **값** | 서술은 md, 값은 yaml | `credeal/ssot/*.yaml` |

### 2.1 판별이 애매할 때

두 층에 걸치는 것처럼 보이면 **위 층에 두고 아래 층이 참조**합니다.
아래 층에 두고 위에서 참조하면, 아래 층 문서가 폐기될 때 규칙이 사라집니다 — D22-8이 그랬습니다.

### 2.2 v0.5에서 층을 옮기는 것

| 대상 | v0.4 위치 | v0.5 위치 | 이유 |
|---|---|---|---|
| 금지어 26 · 치환 14 · 문맥 예외 11 · 부정 표지 15 | `IM_STANDARD_수익형` §6 (2층) | **`CATALOG_LEXICON` §7 (1층)** | 포스처 무관 |
| 숫자·단위·기준 표기 규칙 | 동 (2층) | **`CATALOG_LEXICON` §8 (1층)** | 포스처 무관 |
| 출처 등급 6단 | `D19` §1 (3층) | **`CATALOG_SLOTS` §1.2 (1층)** | 포스처 무관 |
| P01~P04 필지·제척 계산식 | [HIST] `IM_PRECISION_SPEC` (폐기) | **`CATALOG_RULES` §2.2 (1층)** | 주인이 무덤에 있었음 |
| 교차검증 X01~X05 | `D19` (3층) | **`CATALOG_RULES` §2.3 (1층)** | 공부 정합성은 포스처 무관 |

### 2.3 층을 옮기지 않는 것

| 대상 | 유지 위치 | 이유 |
|---|---|---|
| 페이지 순서 · 프리셋 | `im.pages.yaml` (4층) | 지면은 포스처별로 다릅니다 |

## 3. 포스처 확장 계약 🆕

새 포스처를 붙이거나 기존 포스처를 상용화할 때 **13칸을 전부 채웁니다.**
하나라도 비면 그 포스처는 `internal_only` 입니다 — IM 발행 API가 거절합니다.

```ts
export interface PostureContract {
  posture: InvestmentPosture;
  archetypes:        ArchetypeCode[];   // ≥ 3
  sections:          SectionKey[];      // ≥ 7
  emphasisSections:  SectionKey[];      // ≥ 2
  requiredSlots:     SlotGroupKey[];
  valueMetric:       MetricKey;         // 이 포스처의 핵심 지표
  yieldBasis:        CapRateBasis | 'none';
  lAxisSlots:        SlotGroupKey[];    // §6 — 중개인만 알 수 있는 것
  minResolution:     { L: 'R0'|'R1'|'R2'|'R3'; P: 'P0'|'P1'|'P2'|'P3' };
  gradeAdjustment:   Record<SlotGroupKey, number>;
  layoutRules:       LayoutCode[];      // ≥ 1
  constraints:       ConstraintCode[];  // ≥ 1
  gates:             GateCode[];        // applies_to 에 이 포스처가 든 것
  nlgMasks:          MaskCode[];        // ≥ 2
  status: 'commercial' | 'beta' | 'internal_only';
}
```

### 3.1 칸별 소유 문서

| # | 칸 | 소유 | 최소 |
|---:|---|---|:-:|
| 1 | `archetypes` | `CATALOG_RULES` §1 | 3 |
| 2 | `sections` | 포스처 표준 (§3.3) | 7 |
| 3 | `emphasisSections` | 동 | 2 |
| 4 | `requiredSlots` | `CATALOG_SLOTS` §4 매트릭스 | — |
| 5 | `valueMetric` | `CATALOG_ASSET_TYPES` §3 | 1 |
| 6 | `yieldBasis` | `CATALOG_LEXICON` §2.3 | 없으면 `none` 명시 |
| 7 | `lAxisSlots` | 이 문서 §6.2 | ≥ 1 |
| 8 | `minResolution` | 이 문서 §6.4 | — |
| 9 | `gradeAdjustment` | 이 문서 §6.5 | — |
| 10 | `layoutRules` | `CATALOG_RULES` §5 | 1 |
| 11 | `constraints` | `CATALOG_RULES` §3 | 1 |
| 12 | `gates` | `CATALOG_RULES` §4 `applies_to` | — |
| 13 | `nlgMasks` | `CATALOG_RULES` §6 | 2 |

> 🔴 **`lAxisSlots` 는 `CATALOG_SLOTS`에 실재하는 슬롯군만 담습니다.**
> §6.2 표의 서술어(“운영 실적”·“보유 이력·매도 사유”)는 사람이 읽는 설명이고,
> 계약에 넣는 값은 슬롯군 키입니다. **슬롯이 없으면 그 칸은 채울 수 없습니다** —
> v0.5에서 `holding_history`·`operating_performance` 두 Pack을 신설해 5종 전부
> 실재 키로 채웠습니다 (`CATALOG_SLOTS` §3.9·§3.10).
>
> 🔴 **다만 `trading` 은 슬롯이 정의됐을 뿐 수집 경로가 없습니다.**
> 정의와 수집은 다릅니다 — 계약은 통과하고 등급이 막습니다 (§3.3).

### 3.2 `status` 가 하는 일

```ts
export function assertPublishable(p: InvestmentPosture): void {
  const c = POSTURE_CONTRACT[p];
  const missing = CONTRACT_KEYS.filter(k => isEmpty(c[k]));
  if (missing.length > 0) {
    throw new OntologyViolation('G30',
      `${p} 포스처는 계약 ${missing.length}칸이 비어 있어 발행할 수 없습니다: ${missing.join(' · ')}`);
  }
}
```

> **차단하는 것이 맞습니다.** 계약이 빈 포스처로 IM을 내면, 그 IM은 등급을 매길 수도
> 결손을 말할 수도 없습니다. "아무것도 검사하지 않은 문서"를 매수자에게 보내게 됩니다.
> 지금 `operating`·`trading`이 정확히 그 상태입니다.

### 3.3 현재 계약 충족 현황

**정본은 `credeal/ssot/im.ontology.yaml` `posture_contract.current_coverage` 이며,
`qa/ontology_check.py ③` 이 매번 실측합니다.** 아래는 v0.5 반영 직후 실측값입니다 —
문서에 손으로 적은 수는 반드시 낡으므로, 어긋나면 검사기 출력이 이깁니다.

| posture | 아키타입 | 레이아웃 | 제약 | 게이트 | 남은 미충족 칸 | status |
|---|---:|---:|---:|---:|---|---|
| `income` | 9 | 1 | 7 | 10 | — | **commercial** |
| `owner_occupied` | 4 | 1 | 1 | 2 | 실증 **0건** | **beta** |
| `development` | 4 | 1 | 5 | 3 | 실증 2건 | **beta** |
| `operating` | 4 | 1 | 7 | 10 | 아키타입 **가설** · 실증 1건 | **beta** |
| `trading` | 4 | 1 | 4 | 1 | 🔴 `holding_history` **수집 경로 미구현** | **internal_only** |

v0.4 시점과 비교하면 이렇습니다.

```
              아키타입      레이아웃       제약        게이트
income        11 →  9      0 → 1      0 → 7      0 → 10
owner_occ      4 →  4      1 → 1      1 → 1      0 →  2
development    4 →  4      1 → 1      2 → 5      0 →  3
operating      0 →  4      1 → 1      1 → 7      0 → 10
trading        0 →  4      0 → 1      0 → 4      0 →  1
```

> `income` 아키타입이 11 → 9로 줄어든 것은 삭제가 아닙니다. v0.4 실측 11은
> 해설 문장의 언급까지 센 값이었고, 표 행만 세면 9입니다 (§8.4에서 R-INC-04~06을
> 정의했으므로 실제 정의 수는 늘었습니다). 검사기의 계수 오류를 함께 고쳤습니다.

### 3.3.1 아직 남은 것

**13칸은 `qa/doc_integrity.py ④` 가 포스처 표준 문서의 계약 표를 파싱해 검증합니다.**
칸 이름만 나열해도 통과하지 않도록 **값 칸이 비어 있지 않은지**까지 봅니다.
`qa/ontology_check.py ③` 은 그중 `archetypes`·`layoutRules`·`constraints`·`gates`
네 칸을 **정본 쪽에서 역방향으로** 셉니다 — 문서의 주장과 정본의 실측을 대조하는 것이
두 검사기를 나눈 이유입니다.

| 남은 일 | 막고 있는 것 |
|---|---|
| `holding_history` **수집 경로**(등기부 파싱) | `trading` 발행 |
| `im.pages.yaml` 에 포스처별 면 순서 | 렌더 편성 · 분량 검증 |
| `operating`·`trading` 실증 딜 축적 | 아키타입 가설 → 확정 |
| `owner_occupied` 실증 1건 | 섹션 편성 검증 |

`trading` 만 `internal_only` 인 이유는 **슬롯은 정의됐으나 수집 경로가 없어서**입니다.
정의와 수집은 다릅니다.

## 5. 출처 등급 — 저장과 표시를 분리 🆕

정확도가 다른데 배지가 같으면 책임 소재가 흐려집니다.

### 5.1 저장 — `Provenance` 9종

```ts
export const Provenance = z.enum([
  'registry',    // 공부 — 건축물대장 · 등기부 · 토지대장
  'public_api',  // 공공 API 원시 — V-World · 실거래가
  'broker_aug',  // 공공 API + 중개인 보강         🆕
  'expert',      // 전문가 — 감정평가 · 구조진단
  'ledger',      // 원장 — 임대차 원장 · 관리비 내역   🆕
  'seller',      // 매도인 진술
  'broker',      // 중개인 진술
  'derived',     // 파생 — 계산 결과              🆕
  'assumed',     // 가정
]);
```

### 5.2 표시 — `SourceTier` 6단

| 티어 | 표기 | Provenance | 신뢰도 |
|---|---|---|---:|
| **S1** | 공부 | `registry` | 1.00 |
| **S2a** | 공공 | `public_api` | 0.95 |
| **S2b** | 공공+보강 | `broker_aug` | 0.80 |
| **S3** | 자료·진술 | `expert` · `ledger` · `seller` · `broker` | 0.95 / 0.70 / 0.65 / 0.60 |
| **S4** | 파생 | `derived` | **최약 고리 승계** |
| **S5** ◇ | 가정 | `assumed` | 0.30 |

```ts
export function tierOf(p: Provenance): SourceTier { /* 위 표 */ }
export function confidenceOf(v: Valued): number {
  return v.provenance === 'derived'
    ? Math.min(...v.inputs.map(confidenceOf))   // S4 는 최약 고리
    : BASE_CONFIDENCE[v.provenance];
}
```

> **S4가 자기 신뢰도를 갖지 않는 것이 요점입니다.** 계산 결과에 입력보다 높은 등급을
> 붙이는 것을 구조적으로 막습니다 (제약 C21과 같은 취지, 이제 타입 수준에서).

### 5.2.1 티어와 신뢰도는 다른 축입니다 🔴

이 표를 단일 서열로 읽으면 틀립니다. 실제로 이렇게 어긋납니다.

| 어긋남 | 사실 |
|---|---|
| `expert` 0.95인데 S3 | 감정평가는 중개인 진술과 같은 배지를 답니다 |
| `broker_aug` 0.80인데 S2b | 진술보다 높은 배지인데 신뢰도는 `expert` 보다 낮습니다 |
| S3 내부 폭 0.60~0.95 | **S1~S2b 전체 폭(1.00~0.80)보다 넓습니다** |
| `derived` 입력이 전부 공부면 1.00 | 신뢰도는 S1급인데 배지는 S4입니다 |

**의도한 것입니다.** 두 축이 답하는 질문이 다릅니다.

```
티어(S)     "이 값이 어디서 왔는가"        →  독자에게 보여주는 출처
신뢰도       "얼마나 믿을 수 있는가"        →  등급 계산에 쓰는 가중치
```

감정평가서는 **사람이 만든 자료**라는 점에서 공부와 다릅니다 — 평가 시점과 목적에 따라
값이 달라집니다. 그래서 배지는 S3이지만, 방법론이 정해져 있어 신뢰도는 높습니다.
반대로 `derived` 는 출처가 계산이라는 사실을 숨기면 안 되므로 배지는 항상 S4입니다.

🔴 **그래서 두 값을 정렬 키로 섞어 쓰면 안 됩니다.** 등급 계산에는 `confidence`,
지면 배지에는 `tier` 를 씁니다. `contracts/im-registry.d.ts` 의 `SourceGrade` 를
서열로 비교하는 코드가 있으면 잘못된 것이며, `confidenceOf()` 로 바꿔야 합니다.

**S3에 4종이 몰린 것은 남은 문제입니다.** 지면에서 감정평가서와 중개인 구두 진술이
같은 배지를 다는 것은 실무적으로 불편합니다. S3를 쪼갤지는 실제 IM에서 혼동이
관측된 뒤에 정합니다 — 지금 쪼개면 근거 없이 티어가 7단이 됩니다.

### 5.3 마이그레이션

```
public   → registry     (건축물대장·등기부·토지대장 유래)
         → public_api   (그 외 공공 API)
expert   → expert       (변경 없음)
seller   → seller       (변경 없음)
broker   → broker       (변경 없음)
assumed  → assumed      (변경 없음)
신규      broker_aug · ledger · derived
```

`public` 분할은 슬롯별 수집 경로를 봐야 하므로 **자동 변환하지 않습니다.**
**`CATALOG_SLOTS.md` §1.3의 수집 경로 표**를 근거로 일괄 매핑하고, 판단이 안 서는
슬롯은 `public_api`(낮은 쪽)로 둡니다.

> [HIST] 이 표는 `IM_DATA_PIPELINE.md` §2에 있었습니다. 그 문서가 폐기되었으므로
> 마이그레이션의 유일한 근거가 무덤에 있는 상태였고 — **D22-8과 똑같은 구조입니다** —
> v0.5에서 `CATALOG_SLOTS` 로 회수했습니다.

## 6. 등급 — L×P 이중 해상도 🆕

### 6.1 왜 단일 점수로는 안 되는가

v0.4는 슬롯군 가중 합계로 0~100점을 내고 A/B/C/D를 매겼습니다.
그런데 **점수가 같아도 원인이 다르면 중개인이 할 일이 다릅니다.**

```
65점  —  공부는 다 있는데 렌트롤이 없다      →  중개인이 렌트롤을 채우면 됩니다
65점  —  렌트롤은 있는데 지번이 틀렸다        →  지번부터 고쳐야 합니다
```

두 축으로 나눕니다.

| 축 | 뜻 | 채우는 주체 | 전 포스처 공통 |
|---|---|---|:-:|
| **P** (P0~P3) | 물건 자료 — **지번만 있으면 공공에서 오는 것** | 자동 | ○ |
| **L** (R0~R3) | **중개인만 알 수 있는 것** | 중개인 | **✗ — 포스처별로 다름** |

### 6.2 L축은 포스처마다 다른 슬롯군을 봅니다 🔴

**이것이 v0.5의 핵심 설계입니다.** 수익형의 L축은 렌트롤이지만, 개발형의 L축은
명도·인허가이고, 운영형의 L축은 영업 실적입니다. 축의 정의를 고정하면
다른 포스처에서 등급이 의미를 잃습니다.

| posture | `lAxisSlots` (실재 슬롯군 키) | R3 (최상) 조건 |
|---|---|---|
| `income` | `lease_roll` · `financial_input` | 임대 현황 전량 + 최초 계약일 + 운영비 실적 |
| `owner_occupied` | `occupancy_plan` · `physical_spec` | 인원·면적 배분 + 현 임차료·만료일 |
| `development` | `vacate_plan` · `permit_risk` · `development_plan` | 명도 대상·비용·기간 + 인허가 전 항목 상태 |
| `operating` | **`operating_performance`** · `hospitality_spec` | 3개년 실적 + 운영사 계약 조건 |
| `trading` | `market_comp` · **`holding_history`** | 권역 실거래 6건 이상 + 보유기간·매도 사유 |

> **Pack 2종은 v0.5에서 신설했습니다** (`CATALOG_SLOTS` §3.9·§3.10).
> `holding_history` 가 없던 동안 `trading` 은 축은 정의됐는데 담을 그릇이 없어
> **구조적으로 D등급**이었고, `operating` 의 L축이 `hospitality_spec` 하나였을 때는
> 요양시설·주차장·골프연습장이 등급을 받을 수 없었습니다.

> 🔴 **`trading` 은 여전히 `internal_only` 입니다.** 슬롯은 정의됐지만
> **수집 경로(등기부 파싱)가 미구현**이라 실제로는 비어 있습니다.
> 정의와 수집은 다릅니다 (§3.3).

### 6.2.1 축 배정 — 남는 슬롯군의 귀속

L·P 어느 축에도 없는 슬롯군이 생깁니다. 귀속을 정해 두지 않으면 **채움률의 분모가
정의되지 않아 P2/R2 판정이 성립하지 않습니다.**

| 슬롯군 | 축 | 근거 |
|---|---|---|
| `land_parcel` · `building_basic` · `zoning` · `road_access` · `title_encumbrance` | **P** | 지번만 있으면 공공에서 옵니다 |
| `lease_roll` · `lease_legal` | **L** (income·development·operating) | 중개인만 압니다 |
| `financial_input` | **L** | 매매가·운영비는 중개인·매도인 자료입니다 |
| `market_comp` | **P** (trading에서만 L) | 실거래가 API로 옵니다 |
| Pack 슬롯군 | 포스처 계약의 `lAxisSlots` 에 있으면 **L**, 없으면 **축 무관** | |

**축 무관 슬롯군은 두 축의 분모에서 모두 제외**하고, 가중치는 §6.5의
`not_applicable` 재배분과 같은 방식으로 각 축 내부에 비례 배분합니다.

### 6.3 등급 매트릭스

```
        P0        P1        P2        P3
  R3     D         C         A         A
  R2     D         C         A         A
  R1     D         C         B         B
  R0     D         D         D         D
```

| 등급 | 조건 | 뜻 |
|---|---|---|
| **A** | L≥R2 ∧ P≥P2 | 상용 발행 가능 |
| **B** | L≥R1 ∧ P≥P2 | 발행 가능 · 일부 지표 잠금 |
| **C** | L≥R1 ∧ P=P1 | 내부 검토용 |
| **D** | L=R0 ∨ P=P0 | 발행 불가 |

> **P가 아무리 좋아도 L=R0이면 D입니다.** 공부만으로는 IM이 되지 않습니다.
> 반대로 L=R3이어도 P=P0이면 D입니다 — 지번이 틀리면 나머지가 전부 틀립니다.

### 6.4 `minResolution` — 포스처별 발행 하한

| posture | 최소 | 근거 |
|---|---|---|
| `income` | L≥R2 · P≥P2 | 수익률을 내려면 렌트롤 전량이 필요합니다 |
| `owner_occupied` | L≥R1 · P≥P2 | 현 임차료 하나로도 비교가 성립합니다 |
| `development` | **L≥R1**\* · P≥P3 | 용적률·인허가가 틀리면 사업수지 전체가 틀립니다 |
| `operating` | L≥R2 · P≥P2 | 실적 1개년으로는 계절성을 못 봅니다 |
| `trading` | L≥R1 · P≥P2 | 비교사례 중심이라 L 의존이 낮습니다 |

\* 🔴 **개발형 L은 명도 책임에 따라 갈립니다.** 조사 결과 **매도인 명도가 관행**이며
(`IM_STANDARD_포스처확장.md` v3.0 §4), 매수인이 명도된 상태로 인수하면 호실별
갱신요구권 판정이 불필요합니다.

```ts
// 정본 — CATALOG_RULES 가 아니라 여기가 소유합니다 (등급 체계이므로)
export function developmentMinL(d: DealTerms): LeaseResolution {
  return d.vacateResponsibility === 'seller' ? 'R1' : 'R3';
}
```

| 명도 책임 | 최소 L | 비중 |
|---|:-:|:-:|
| 매도인 부담 | **R1** | 다수 |
| 매수인 부담 | **R3** | 소수 |
| 미정 | **R3** | — (가장 위험) |

**"명도 책임"이 렌트롤보다 먼저 확인할 항목입니다.** v0.4는 일괄 R3였고,
v0.5 초안은 일괄 R2였는데 둘 다 틀렸습니다 — 조건부입니다.

### 6.5 v0.4 가중치는 폐기하지 않습니다

L·P는 **어느 축이 막혔는가**를 말하고, v0.4의 가중 점수는 **그 축 안에서 얼마나 찼는가**를
말합니다. 대체가 아니라 층이 다릅니다.

```
P2 판정   =  P축 슬롯군의 가중 채움률 ≥ 70% ∧ 필수 슬롯 결손 0
R2 판정   =  L축 슬롯군의 가중 채움률 ≥ 70% ∧ 포스처 필수 슬롯 결손 0
```

`BASE_PROFILE[assetType]`(`CATALOG_ASSET_TYPES` §6) × `POSTURE_ADJUSTMENT[posture]` 는
산식을 그대로 씁니다. 다만 **축별로 정규화**해서 각 축의 채움률을 냅니다.

> 🔴 **두 표의 키가 어긋나 있습니다.** `BASE_PROFILE` 은 Pack 전체를 **단일 열**로
> 두는데, `POSTURE_ADJUSTMENT` 는 `occupancy_plan` · `hospitality_spec` ·
> `physical_spec` 을 **개별 키**로 보정합니다. 보정 대상이 프로파일에 없으므로
> 지금 상태로는 보정이 조용히 무시됩니다.
>
> **`BASE_PROFILE` 의 `Pack` 열을 Pack별로 쪼개는 것이 정답**이며, 행 합계 100 검증을
> 다시 돌려야 합니다. v0.5에서는 문제를 드러내는 데까지이고 수치 재배분은
> `CATALOG_ASSET_TYPES` §6 개정으로 넘깁니다 — 임의로 쪼개면 등급이 근거 없이 바뀝니다.

### 6.6 등급 컷 재검토 — v0.4 결정 유지

역설계 5건 중 4건이 C 이하였습니다. **지금 조정하지 않습니다.** 표본 5건은 근거가
되지 못하며, 성급한 완화는 등급 체계의 의미를 없앱니다. 자산유형별 20건이 쌓인 뒤
재검토합니다.

## 8. 어휘 규칙의 적용 범위 🆕

### 8.1 문제

금지어 26종·치환 14쌍은 **포스처 무관 규칙인데 수익형 전용 문서에 있었습니다.**
그 결과 온톨로지를 쓰는 사람은 그런 규칙이 있는 줄 몰랐고, 아키타입 이름에
금지어가 들어갔습니다 (§0.3).

동시에 반대 문제도 있습니다. 내부 명세 문서에서 `Cap Rate`·`NOI`·`렌트롤`을 쓰는 것은
**정상**입니다. 개발자끼리는 정확한 용어가 낫습니다. 규칙에 적용 범위가 없으면
검사기가 명세 문서를 잡습니다.

### 8.2 적용 범위 3단

```ts
export type LexiconScope = 'reader_facing' | 'internal_label' | 'engineering';
```

| 범위 | 대상 | 금지어 | 치환 |
|---|---|:-:|:-:|
| **`reader_facing`** | IM 본문 · 딜카드 · 제목 · 캡션 · 각주 | **적용** | **적용** |
| **`internal_label`** | enum 값 · 아키타입 이름 · 슬롯 라벨 · 게이트 문구 | **적용** — 지면에 나갑니다 | **적용** |
| **`engineering`** | 명세 문서 · 코드 주석 · 로그 · 변수명 | 미적용 | 미적용 |

> 🔴 **`internal_label`을 `engineering`으로 착각한 것이 §0.3의 원인입니다.**
> 아키타입 이름은 내부 코드처럼 보이지만 M01~M04 마스크를 타고 IM 문장이 됩니다.
> `BuyerPurpose` 값도 L12 필터 제목으로 지면에 나갑니다.

### 8.3 v0.5에서 고치는 라벨

| 코드 | v0.4 | **v0.5** |
|---|---|---|
| `R-INC-01` | 초안정 수익형 | **임대 안정형** |
| `R-INC-02` | 밸류애드형 | **가치 상승 여력형** |
| `BuyerPurpose.value_add` | 밸류애드 | **가치 상승 여력** |
| L02 동작 문구 | 밸류애드 실행 계획 편성 | **가치 상승 실행 계획 편성** |

**코드는 그대로 두고 라벨만 바꿉니다.** 코드를 바꾸면 과거 IM의 해석이 사후에 바뀝니다.

### 8.4 R-INC-02 중복 정의 해소 🔴

§0.4의 충돌을 이렇게 정리합니다. `CATALOG_RULES` §1.1을 정본으로 하고,
`CATALOG_ASSET_TYPES` §3.2의 정의는 **다른 코드로 분리**합니다.

| 코드 | 정본 정의 | 출처 |
|---|---|---|
| `R-INC-01` | 임대 안정형 — WALT ≥ 3년 ∧ 공실률 ≤ 5% ∧ 수익률 ≥ 권역 평균 | RULES §1.1 |
| `R-INC-02` | **가치 상승 여력형** — 건물연령 ≥ 20년 ∧ 유효 용적률 여유 ≥ 50%p | RULES §1.1 |
| `R-INC-03` | 개발 준비형 — 명도 완료 ∨ 임대차 0건 ∧ 개발 가능 | RULES §1.1 |
| **`R-INC-04`** 🆕 | **임대료 정상화형** — 시세 대비 저렴 ∧ 갱신 도래 (당산동) | ASSET_TYPES §3.2에서 이관 |
| **`R-INC-05`** 🆕 | **공실 해소형** — 공실률 > 15% | 동 |
| **`R-INC-06`** 🆕 | **리모델링형** — 건물연령 > 20년 ∧ 자본 투입 여지 | 동 |

`R-INC-04~06`은 §4.5의 "정의가 빈 코드" 였습니다. **v0.1 원본을 찾는 대신, 실증에서
확인된 정의로 채웁니다.** 원본이 이 세 개와 달랐을 가능성은 있으나, 빈칸으로 두는 것보다
낫고 실증 근거가 있습니다. 원본이 나오면 충돌 여부를 확인합니다.

`L02`의 조건도 함께 갱신합니다 — `R-INC-02`(가치 상승)와 `R-INC-04`(임대료 정상화)는
**편성이 정반대**이므로 분기를 나눕니다.
