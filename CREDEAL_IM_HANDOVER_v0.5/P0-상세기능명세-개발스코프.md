# P0-1. 크로스브로커 매수자 풀 (Cross-Broker Buyer Pool)

## 1.1 목적 및 성공 기준

### 목적

400명의 중개인이 각자 등록한 매수 의향서를 **조직 단위 공동 풀로 전환**하여, 매물 보유 중개인이 조직 전체의 매수 수요에 접근할 수 있도록 한다.

### 해결하는 문제

현재 `buyer_intent_lite`와 `match_results`가 `broker_id` 스코프로 제한되어 있어, 400명이 사실상 **400개의 고립된 1인 CRM**을 사용하고 있습니다. 400명이 각자 매수자 5명씩만 등록해도 2,000명 규모 풀이 형성되지만 현재 구조에서 그 가치는 0입니다.

### 성공 기준 (릴리스 후 8주 시점)

| 지표 | 목표 | 측정 방법 |
|:---|:---|:---|
| 풀 등록 매수 의향서 수 | 300건 이상 | `buyer_intent_lite WHERE pool_visibility != 'private'` |
| 크로스브로커 매칭 생성 | 주당 20건 이상 | `match_results WHERE is_cross_broker = true` |
| G2 연결 요청 승인율 | 50% 이상 | `buyer_gate_requests` 승인/전체 |
| 크로스브로커 발 임장 | 5건 이상 | `bookings` 중 크로스 매칭 유래 |
| **크로스브로커 발 성사** | **1건 이상** | P0-3 연계 시 자동 측정 |

마지막 지표 1건이 나오면 이 기능은 성공입니다. 400명 조직에서 확산은 제품 성능이 아니라 **첫 성공 사례**가 만듭니다.

## 1.2 핵심 설계 판단 — 왜 Gate를 재사용하는가

미국식 MLS가 한국에서 반복 실패한 원인은 기술이 아니라 인센티브입니다. **매물 공개 = 수수료 분할**이므로 중개인은 공개를 거부합니다.

그러나 **매수 니즈 공개는 손해가 없습니다.** 내 매수자의 "강남 200억 이하, 수익률 3.5% 이상"이라는 조건이 공개된다고 해서 매수자를 뺏기지 않습니다. 뺏기는 것은 **매수자의 신원**입니다.

따라서 설계 원칙은 하나입니다.

> **조건은 열고, 신원은 잠근다. 신원 해제는 공동중개 약정 체결과 교환한다.**

이미 매물용으로 구축된 Gate/Disclosure(G1~G3) 메커니즘과 `DisclosureGuardAgent`를 **매수자에 대칭 적용**하면 됩니다. 새로운 개념을 만들지 않으므로 중개인의 학습 비용도 0입니다.

## 1.3 게이트 3단계 정의

| 단계 | 공개 범위 | 전이 조건 | 승인 주체 |
|:---|:---|:---|:---|
| **G1**<br>조건 공개 | 권역(구 단위), 자산유형, 예산 밴드, 목표수익률 밴드, 용도, 거래 시급도, 등록 시점, 담당 중개인 **소속만**(성명·연락처 비공개) | 조직 소속 broker 자동 | — |
| **G2**<br>중개인 간 연결 | 매수자 담당 중개인 **성명·연락처 공개**. 상세 조건(층수, 엘리베이터, 특약 요구 등) 공개 | 매물 보유 중개인이 특정 딜카드를 지정하여 요청 | 매수자 담당 중개인 |
| **G3**<br>매수자 접촉 | 매수자 신원(법인명/성명) 및 직접 연락처 공개 | **공동중개 약정 체결 완료** | 매수자 담당 중개인 + 시스템 검증 |

### 중요 규칙

- **G3는 반드시 공동중개 약정과 결합**되어야 합니다. 약정 없이 신원을 공개하면 매수자를 뺏길 수 있다는 우려가 현실이 되고, 기능 전체가 즉시 사용 중단됩니다.
- P0-3(보수약정 모듈)이 배포되면 G3 전이 조건을 **P0-3의 공동중개 약정 서명 완료**로 연결합니다. 그 전까지는 체크박스 + 이력 기록으로 대체합니다.
- `DisclosureGuardAgent`를 재사용하되, 입력 스키마에 매수자 컨텍스트를 추가합니다.

## 1.5 RLS 정책

```sql
-- buyer_intent_lite

-- (1) 본인 소유: 전체 열람·수정
CREATE POLICY bil_owner_all ON buyer_intent_lite
  FOR ALL USING (broker_id = auth.uid());

-- (2) 조직 내 G1 열람: 풀 공개 + 미만료 + 동일 org
--     주의: 이 정책은 행 자체를 노출하므로, criteria 등 민감 컬럼은
--     반드시 아래 1.6의 VIEW를 경유해서만 접근하도록 애플리케이션에서 강제
CREATE POLICY bil_org_g1_read ON buyer_intent_lite
  FOR SELECT USING (
    pool_visibility IN ('org','network')
    AND (pool_expires_at IS NULL OR pool_expires_at > now())
    AND org_id = (SELECT org_id FROM profiles WHERE id = auth.uid())
    AND (SELECT role FROM profiles WHERE id = auth.uid()) = 'broker'
  );

-- buyer_gate_requests
CREATE POLICY bgr_participant ON buyer_gate_requests
  FOR SELECT USING (requester_id = auth.uid() OR owner_broker_id = auth.uid());

CREATE POLICY bgr_insert ON buyer_gate_requests
  FOR INSERT WITH CHECK (requester_id = auth.uid());

CREATE POLICY bgr_decide ON buyer_gate_requests
  FOR UPDATE USING (owner_broker_id = auth.uid());
```

> **보안 경고**: RLS만으로는 컬럼 단위 보호가 되지 않습니다. `criteria`(원본)와 `public_summary`(비식별)가 같은 테이블에 있으므로, **G1 조회는 반드시 아래 뷰를 경유**해야 합니다. 애플리케이션 코드에서 `buyer_intent_lite`를 직접 select 하는 경로를 코드 리뷰에서 차단하십시오.

## 1.6 보안 뷰

```sql
-- migration 00071_buyer_pool_view.sql

CREATE VIEW buyer_pool_g1 AS
SELECT
  b.id,
  b.org_id,
  b.public_summary,
  b.urgency,
  b.pool_published_at,
  b.pool_expires_at,
  p.id   AS owner_broker_id,
  -- G1에서는 담당 중개인 성명 비공개, 소속만 노출
  CASE WHEN EXISTS (
    SELECT 1 FROM buyer_gate_requests g
    WHERE g.buyer_intent_id = b.id
      AND g.requester_id = auth.uid()
      AND g.gate_level = 'G2'
      AND g.status = 'approved'
      AND g.expires_at > now()
  ) THEN p.display_name ELSE NULL END AS owner_broker_name,
  NULL::text AS criteria   -- 원본은 절대 노출하지 않음
FROM buyer_intent_lite b
JOIN profiles p ON p.id = b.broker_id
WHERE b.pool_visibility IN ('org','network')
  AND (b.pool_expires_at IS NULL OR b.pool_expires_at > now());
```

| `POST` | `/api/broker/buyer-intents/[id]/publish` | 풀 공개. `public_summary` 생성 후 저장 | 본인 |
| `POST` | `/api/broker/buyer-intents/[id]/unpublish` | 풀에서 회수 | 본인 |

| `POST` | `/api/broker/buyer-pool/match` | 특정 딜카드에 대한 크로스브로커 매칭 실행 | broker |
| `POST` | `/api/broker/buyer-gate-requests` | G2/G3 요청 생성 | broker |

| `GET` | `/api/broker/buyer-pool/contributions` | 내 기여 현황 | 본인 |

### 매칭 실행 로직 (`/api/broker/buyer-pool/match`)

```
1. 입력: building_id (또는 deal_card_id)
2. building_ssot_lite에서 자산 속성 추출 (권역/유형/가격대/면적/수익률)
3. buyer_pool_g1 뷰에서 org 범위 후보 조회
   - 1차 필터: 규칙 기반 (권역 교집합, 예산 밴드 중첩, 자산유형 일치)
     → LLM 호출 전에 후보를 30건 이하로 줄일 것 (비용·지연 관리)
4. 2차: buyer-memo-writer 에이전트로 적합도 평가
   - 입력에서 PII는 sanitizer 통과 (public_summary만 사용하므로 원천적으로 안전)
5. S/A/B/C 등급 산출 → match_results INSERT (is_cross_broker=true)
6. ai_runs 기록
7. 응답: 등급, fit_reasons, caution_reasons, 누락 질문 리스트
```

> **비용 관리**: 400명 × 딜카드마다 전체 풀을 LLM에 태우면 토큰 비용이 폭증합니다. **1차 규칙 필터는 필수**이며, 2차 LLM 평가는 상위 후보 10~30건으로 제한하십시오.

# P0-2. 토지거래허가 스크리너 (Land Transaction Permit Screener)

## 2.1 목적 및 성공 기준

### 목적

딜카드 및 모바일 IM 생성 시 **토지거래허가 대상 여부와 심사 요건을 자동 판정·표시**하여, 딜 초기에 절차 리스크를 스크리닝한다.

### 시급성 근거

2025년 10월 20일부로 **서울 25개 자치구 전역**이 토지거래허가구역으로 지정되었으며, 효력은 2026년 12월 31일까지입니다. 상업용은 대지지분 15㎡ 초과부터 적용되어 **크리딜이 다루는 사실상 모든 딜에 절차가 부과**된 상태입니다.

이는 리스크인 동시에 **비대칭 진입장벽**입니다. 전 물건에 절차가 붙었으므로 절차 역량이 곧 수임 경쟁력이 됩니다.

### 성공 기준

| 지표 | 목표 |
|:---|:---|
| 딜카드 생성 시 토허 판정 커버리지 | 서울 소재 딜 95% 이상 |
| 판정 정확도 (수동 검증 표본 100건) | 대상 여부 98% 이상 |
| IM 「허가 리스크」 섹션 노출률 | 대상 딜 100% |
| 중개인 만족도 (설문) | "유용" 이상 70% |

## 2.2 핵심 설계 판단 — 법령을 코드에 넣지 마십시오

토허 제도는 **지정 효력이 2026년 12월 31일까지**이며 연장·해제·요건 변경이 언제든 발생합니다. 또한 구청별 심사 지침이 상이합니다.

> **설계 원칙: 모든 법령 파라미터는 코드가 아니라 데이터로 관리한다.**

규칙을 하드코딩하면 법령 변경 때마다 배포가 필요하고, 잘못된 판정이 배포 시점까지 지속됩니다. **관리자 화면에서 수정 가능한 규칙 테이블**로 구현하십시오.

## 2.3 판정 로직

```
입력: PNU (또는 주소 → address-resolver로 PNU 변환)
  │
  ├─ [1] land-use-api (LURIS) → 용도지역, 건폐율, 용적률, 규제사항
  ├─ [2] building-register-api → 대지면적, 연면적, 주용도
  └─ [3] 행정구역 코드 → 시군구 식별
  │
  ▼
[규칙 엔진] ltp_zone_rules 조회
  ├─ 해당 시군구가 지정 구역인가?
  ├─ 지정 기간 내인가? (오늘 기준)
  ├─ 용도지역별 기준면적 × 강화계수 = 임계면적
  └─ 거래 대상 대지지분 > 임계면적?
  │
  ▼
출력: {
  is_subject: boolean,           // 허가 대상 여부
  confidence: 'high'|'medium'|'low',
  threshold_sqm: number,         // 적용된 임계면적
  subject_area_sqm: number,      // 판정에 사용된 면적
  zone: string,                  // 용도지역
  district: string,              // 시군구
  designation_period: {from, to},
  requirements: string[],        // 실수요 요건 등
  district_notes: string|null,   // 구청별 특이사항
  disclaimer: string             // 필수
}
```

### 신뢰도(confidence) 산정

| 등급 | 조건 | UI 처리 |
|:---|:---|:---|
| `high` | PNU 확정 + 대지면적 공부 확인 + 용도지역 확인 | ✓공부확인 배지, 판정 표시 |
| `medium` | 일부 데이터 추정 (예: 대지지분 미확정) | ⚙AI추정 배지 + "확인 필요" 경고 |
| `low` | 주소만 있고 PNU 미확정, 또는 API 실패 | **판정 표시하지 않고** "확인 필요"만 안내 |

> **`low`에서 판정을 표시하지 않는 것이 중요합니다.** 틀린 법률 판정을 표시하면 신뢰를 잃을 뿐 아니라 분쟁 소지가 됩니다.

# P0-3. 보수약정 · 전속중개 모듈 (Fee Agreement Module)

## 3.1 목적 및 성공 기준

### 목적 — 두 가지 문제를 동시에 해결

**① 판례 리스크 방어**

중개대상물 확인·설명서에 기재된 요율은 **권리관계 설명용 법정 서식일 뿐 수수료를 확정하는 계약서가 아니라는 판례**가 존재합니다. 또한 고액 거래에서는 상한 0.9%를 그대로 적용하지 않고 협의로 크게 낮추는 것이 관행이므로, **상한 기재는 청구 근거가 되지 못합니다.** 현재 400명 전원이 동일 리스크에 노출되어 있습니다.

**② Closed 관측 = AI 학습 데이터 확보**

보수약정 서명 시점이 곧 거래 성사 시점입니다. 이 모듈이 도입되면 **Deal Prediction 엔진의 학습 정답(ground truth)이 비로소 생성**되며, 현재 근거가 취약한 성사 확률 게이지가 실제 데이터 기반으로 전환됩니다.

> 현 시스템의 가장 심각한 구조적 결함 — 파이프라인이 `Negotiating → Closed`로 정의되어 있으나 계약·잔금·등기가 전부 시스템 외부에 있어 **무엇이 성사인지 시스템이 알지 못하는 상태** — 를 해소하는 유일한 경로입니다.

### 성공 기준

| 지표 | 목표 (릴리스 후 12주) |
|:---|:---|
| 보수약정서 생성 건수 | 50건 이상 |
| 서명 완료율 | 60% 이상 |
| **Closed 상태 자동 기록 건수** | **20건 이상** |
| 약정서 미보유 딜 비율 | 40% 이하로 감소 |

## 3.2 범위 정의 — 무엇을 만들고 무엇을 만들지 않는가

| 만든다 | 만들지 않는다 |
|:---|:---|
| 중개보수 약정서 생성·서명·보관 | 매매계약서 (법무 영역) |
| 전속중개계약서 (선택) | 등기 신청 |
| 공동중개 약정서 (P0-1의 G3 전제) | 자금 에스크로 |
| 업무 수행 이력 자동 기록 | 세금 계산 |
| Closed 상태 자동 전이 | 국토부 실거래 신고 (2단계) |

> **핵심**: 이 모듈은 **거래계약**이 아니라 **중개인과 의뢰인 간의 보수 약정**을 다룹니다. 범위를 넘으면 법무 리스크와 개발 규모가 동시에 폭증합니다.

## 3.3 축소 실행안 (권고)

상업용 고액 거래는 여전히 종이 계약과 법무법인 검토 관행이 강하며, 전자계약 32만건의 대부분은 주거 임대차입니다. 따라서 **국토부 전자계약 연계는 2단계로 분리**하고, 1단계는 자체 전자서명으로 구현할 것을 권고합니다.

| 단계 | 범위 | 기간 |
|:---|:---|:---|
| **1단계 (P0)** | 보수약정서 생성 + 자체 전자서명 + 업무이력 + Closed 전이 | 4주 |
| 2단계 (P1) | 국토부 전자계약 시스템 연계, 실거래 신고 자동화 | 4주 |

1단계만으로 두 가지 목적(판례 방어 + Closed 관측)이 모두 달성됩니다.

### 3.4.4 Pipeline 상태 연동

```sql
-- migration 00077_pipeline_closed_trigger.sql

-- fee_agreements.deal_outcome 변경 시 파이프라인 상태 자동 전이
CREATE OR REPLACE FUNCTION sync_pipeline_on_outcome()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.deal_outcome = 'closed' AND (OLD.deal_outcome IS DISTINCT FROM 'closed') THEN
    UPDATE building_ssot_lite
       SET details = jsonb_set(
             COALESCE(details,'{}'::jsonb),
             '{pipeline_state}', '"Closed"'
           )
     WHERE id = NEW.building_id;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_pipeline
  AFTER UPDATE ON fee_agreements
  FOR EACH ROW EXECUTE FUNCTION sync_pipeline_on_outcome();
```

> **확인 필요**: 현행 파이프라인 상태가 `building_ssot_lite.details` JSONB에 저장되는지, 별도 테이블인지 저장소 확인 후 조정.

## 3.5 상태 머신

```
draft ──[발송]──▶ sent ──[상대방 서명]──▶ signed ──[결과 입력]──▶ deal_outcome 확정
  │                 │                        │
  │                 ├─[거절]──▶ declined      └─ closed  → Pipeline: Closed
  │                 └─[만료]──▶ expired          failed  → Pipeline: 유지 + 사유 기록
  └─[취소]──▶ cancelled
```

**서명 후 문서는 불변(immutable)입니다.** 수정이 필요하면 새 약정서를 생성하고 이전 것을 `cancelled` 처리하십시오. `document_hash`가 이를 보장합니다.

## 3.6 서명 플로우 (1단계 — 자체 전자서명)

```
1. 중개인이 딜카드에서 [보수약정서 만들기] 클릭
2. 약정 유형 선택 (보수약정 / 전속중개 / 공동중개)
3. 상대방 정보 + 보수 조건 입력
   └ 요율 입력 시 예상 보수액 실시간 계산 표시
   └ ⚠️ "상한 0.9%"를 기본값으로 프리필하지 말 것 (아래 3.9 참조)
4. 미리보기 → document_html 생성 + SHA-256 해시
5. [발송] → 상대방에게 카카오 알림톡 또는 SMS로 서명 링크
6. 상대방: 링크 접속 → 본인확인(SMS OTP) → 약정서 열람 → 동의 서명
7. 서명 완료 → 양측에 PDF 사본 발송, status='signed'
8. 딜 종료 시 중개인이 결과 입력 (성사가 / 무산사유)
```

### 서명 링크 보안

- 만료 시간이 있는 서명 토큰 (기본 7일)
- 1회용 (서명 완료 시 즉시 무효화)
- 본인확인 OTP 필수
- 링크 접근 로그 기록

## 3.9 준법 설계 — 반드시 지킬 것

> ⚠️ **아래 사항은 법무 검토 후 문안을 확정하십시오. 본 명세는 설계 방향만 제시합니다.**

| 1 | **상한 요율을 기본값으로 프리필하지 않는다** | 요율 입력란을 빈 값으로 두고, 상한은 안내 문구로만 표시. 상한 프리필은 "협의 없이 상한을 적용했다"는 인상을 주어 오히려 불리 |

| 4 | **AI가 요율을 권장하지 않는다** | 기존 AI 규칙 "가격 권장·투자 조언 금지"를 요율에도 적용. AI는 문안 작성만 지원하고 금액·요율은 제안하지 않음 |
| 5 | **약정 주체는 자격 중개사** | 플랫폼은 도구이며 중개 당사자가 아님을 약정서 및 이용약관에 명시 |

## 3.10 수용 기준

- [ ] 서명 완료된 약정서는 수정이 불가하다 (DB 제약 + API 검증)
- [ ] `document_hash`로 위변조를 검증할 수 있다
- [ ] 서명 토큰은 1회용이며 7일 후 만료된다
- [ ] OTP 없이 서명이 완료되지 않는다
- [ ] 요율 입력란에 상한값이 프리필되지 않는다
- [ ] `deal_outcome='closed'` 입력 시 파이프라인이 자동으로 `Closed`로 전이된다
- [ ] 파이프라인에서 약정서 없이 `Closed`로 수동 전이할 수 없다
- [ ] `failure_reason`은 선택지 기반으로 입력된다 (자유 텍스트 단독 불가)
- [ ] 업무 이력이 `activity_events`에서 자동 파생된다
- [ ] 서명 페이지가 모바일 및 카카오톡 인앱 브라우저에서 정상 동작한다
- [ ] AI가 요율·금액을 제안하지 않는다 (프롬프트 가드 테스트)
- [ ] 약정서 PDF가 A4 규격으로 정상 출력된다
