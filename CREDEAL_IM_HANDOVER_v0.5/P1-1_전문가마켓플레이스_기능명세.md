### 0.1 왜 이 과제가 P1 최우선으로 올라왔는가

세 가지가 동시에 성립합니다.

| 근거 | 내용 |

## 1. 목적 및 성공 기준

### 1.1 목적

중개인이 딜 진행 중 필요한 **전문가 용역(감정평가·가설계·세무·시설점검 등)을 시스템 안에서 조달·결제·검수**할 수 있게 하고, 그 산출물이 모바일 IM의 신뢰도 배지로 환류되게 한다.

### 1.2 세 주체의 효용

| 주체 | 얻는 것 |
|:---|:---|
| **중개인** | 아는 사람에게 술 사고 부탁하던 것을 → 견적 비교 후 계약. 산출물이 IM 신뢰도로 전환됨 |
| **매수자** | `★전문가검증` 배지가 붙은 IM. 실사 비용·기간의 사전 예측 |
| **전문가** | 딜 플로우 접근. 400명 중개인이 만드는 연 수천 건 파이프라인 |

### 1.3 성공 기준 (릴리스 후 12주)

| 지표 | 목표 | 측정 |
|:---|:---|:---|
| 등록·검증 완료 전문가 수 | 30명 이상 | `expert_profiles WHERE verification_status='verified'` |
| 견적 요청 건수 | 60건 이상 | `expert_rfqs` |
| 계약 성사율 (요청→계약) | 35% 이상 | `expert_engagements` / `expert_rfqs` |
| 에스크로 정상 완료율 | 90% 이상 | `released` / `held` |
| **`★전문가검증` 배지 발급 건수** | **20건 이상** | `provenance_badges WHERE tier='expert_verified'` |
| 전문가 재사용률 | 40% 이상 | 동일 중개인이 2회 이상 의뢰 |

마지막에서 두 번째 지표가 이 과제의 존재 이유입니다. **배지가 실제로 발급되기 시작해야 IM의 차별화가 완성됩니다.**

## 2. 핵심 설계 판단

### 2.1 판단 ① — 에스크로는 "용역비"에만 적용한다

```
❌ 매매대금 50억원  → PG 한도 초과. 법무사 신탁·은행 에스크로 영역. 절대 불가
✅ 전문가 용역비 300만원 → PG 범위 내. TossPayments 처리 가능
🟡 중개보수 2,500만원  → 기술적으로는 가능하나 P0-3 완료 후 별도 검토
```

**하드 가드를 코드에 박으십시오.** 금액 상한을 설정으로 두고, 초과 시 에스크로 없이 직접 결제 안내로 폴백해야 합니다. 사고가 나면 되돌릴 수 없습니다.

```typescript
// src/domain/expert/escrow.ts
const ESCROW_MAX_AMOUNT = Number(process.env.EXPERT_ESCROW_MAX ?? 20_000_000);

export function assertEscrowEligible(amount: number, category: EngagementCategory) {
  if (amount > ESCROW_MAX_AMOUNT) {
    throw new EscrowIneligibleError('AMOUNT_EXCEEDS_LIMIT');
  }
  if (category === 'property_purchase' || category === 'brokerage_fee') {
    throw new EscrowIneligibleError('CATEGORY_NOT_ALLOWED');
  }
}
```

### 2.2 판단 ② — 자격사 규제가 카테고리를 둘로 가릅니다

> ⚠️ **본 절은 설계 방향이며 법률 자문이 아닙니다. 개발 착수 전 반드시 법무 확인이 필요합니다.**

일부 전문직은 **소개료·알선 대가 수수를 법으로 금지**하고 있습니다. 대표적으로 변호사법은 변호사가 아닌 자가 사건 알선의 대가를 받는 것을 금지하는 조항을 두고 있으며, 세무사법·공인회계사법·감정평가법에도 유사한 취지의 규정이 존재할 수 있습니다.

따라서 **모든 전문가에게 동일한 성사 수수료 모델을 적용하면 안 됩니다.**

| 그룹 | 전문가 유형 | 수익 모델 | 법무 검토 |
|:---|:---|:---|:---|
| **Group A**<br>일반 용역 | 건축사(가설계), 시설점검, 인테리어·리모델링, 측량, 환경조사(석면·토양), 구조기술사, FM·PM | **거래 수수료 가능** (용역비의 N%) | 표준 검토 |
| **Group B**<br>자격사 | 감정평가사, 세무사, 공인회계사, 법무사, 변호사 | **거래 수수료 금지 가정.**<br>구독형 등재료 또는 무료 등재 | 🔴 **개별 확인 필수** |

**1단계는 Group A만 오픈**하고, Group B는 "연결만 제공, 결제·수수료 없음"으로 시작할 것을 권고합니다. 이렇게 하면 규제 리스크 없이 기능을 검증할 수 있고, 법무 검토 결과에 따라 2단계에서 확장하면 됩니다.

### 2.3 판단 ③ — "감정평가"라는 단어를 함부로 쓰지 마십시오

크리딜은 이미 모바일 IM에서 Cap Rate, DCF NPV, AI 추정가를 산출합니다. 여기에 감정평가사가 들어오면 **AI 추정가와 법정 감정평가액이 UI에서 혼동될 위험**이 생깁니다.

용어를 분리하십시오.

| 산출 주체 | 용어 | Provenance 배지 |
|:---|:---|:---|
| 시스템 AI | **AI 추정가** | ⚙AI추정 |
| 공부 데이터 | **공시가격 / 실거래가** | ✓공부확인 |
| 감정평가사 | **감정평가액** (정식 명칭 사용) | ★전문가검증 |
| 중개인 | **호가 / 제시가** | 👤중개인입력 |

### 2.4 판단 ④ — 플랫폼은 용역 계약의 당사자가 아닙니다

계약 주체는 **전문가와 의뢰인(중개인 또는 매수자)**입니다. 플랫폼은 매칭·결제 처리·산출물 보관만 담당합니다. 이 경계를 이용약관과 각 계약서에 명시하고, UI에서도 "크리딜은 계약 당사자가 아닙니다"를 노출하십시오.

### 3.1 카테고리 체계

### 3.2 자격 검증 (Deal OS EEAT → CRE판 재설계)

Deal OS의 EEAT 스코어는 콘텐츠 권위 중심입니다. CRE에서는 **자격의 실재성**이 훨씬 중요합니다.

| 검증 축 | 배점 | 검증 방법 |
|:---|---:|:---|
| **자격증 실재 확인** | Pass/Fail | 자격증 사본 + 협회 등록번호. **미통과 시 등재 불가** |
| 사업자등록 확인 | Pass/Fail | 사업자등록증 |
| 배상책임보험 가입 | 15 | 보험증권 (전문직 배상책임) |
| CRE 수행 실적 | 30 | 상업용 부동산 실적 건수·규모 |
| 크리딜 내 완료 실적 | 25 | `expert_engagements` 완료 건수 |
| 의뢰인 평가 | 20 | 5점 척도 평균 (최소 3건 이상 시 반영) |
| 응답 속도 | 10 | 견적 요청 → 응답 중앙값 |

**핵심: 자격증 실재 확인과 사업자등록은 점수가 아니라 게이트입니다.** 무자격자가 등재되면 플랫폼 전체의 신뢰가 즉시 붕괴합니다.

> **1단계는 수동 검증**을 권고합니다. 30명 규모에서 자동화는 과잉이며, 관리자가 서류를 눈으로 확인하는 것이 가장 안전합니다.

**`scope_excluded`가 `scope_included`보다 중요합니다.** Deal OS의 히든코스트 감지 사상을 여기서 구현합니다. 불포함 항목을 필수 입력으로 강제하면 사후 추가 청구 분쟁이 크게 줄어듭니다.

## 6. 매칭 엔진 (`expert-entity-matcher` 개작)

### 6.1 스코어링 축 교체

| Deal OS 원본 | 배점 | → | CRE판 | 배점 |
|:---|---:|:---:|:---|---:|
| 도메인 권위 | — | → | **카테고리 적합** | 30 |
| 키워드 오버랩 | — | → | **자산군 전문성** | 20 |
| 카테고리 관련성 | — | → | **권역 커버리지** | 15 |
| — | — | → | **크리딜 실적·평점** | 20 |
| — | — | → | **가용성 (리드타임)** | 10 |
| — | — | → | **가격 적합 (예산 힌트 대비)** | 5 |

```typescript
// src/domain/expert/matcher.ts
export function scoreExpert(rfq: Rfq, expert: ExpertProfile): MatchScore {
  const category  = expert.categories.includes(rfq.category) ? 30 : 0;
  if (category === 0) return { total: 0, excluded: true };   // 하드 필터

  const asset     = overlapRatio(expert.asset_specialties, rfq.assetTypes) * 20;
  const region    = coversRegion(expert.service_regions, rfq.region) ? 15 : 0;
  const record    = normalize(expert.credibility_score, 0, 100) * 20;
  const avail     = expert.typical_lead_days <= rfq.leadDaysNeeded ? 10 : 0;
  const price     = priceFit(expert.base_price, rfq.budget_hint) * 5;

  return { total: category + asset + region + record + avail + price, excluded: false };
}
```

### 6.2 LLM 사용 원칙

**매칭은 규칙 기반으로만 수행하십시오.** LLM은 다음 두 가지에만 사용합니다.

1. `scope_summary` 자유 텍스트 → `scope_structured` 정규화 (신규 에이전트 `expert-scope-normalizer`)
2. 견적 비교표의 차이점 요약 (신규 에이전트 `quote-diff-summarizer`)

전문가 순위를 LLM이 매기면 근거를 설명할 수 없고, 전문가로부터 "왜 내가 하위인가" 문의가 왔을 때 답변이 불가능합니다.

│ 소요 기간       │ 10일     │ 14일     │ 7일               │
│ 신뢰도 점수     │ 82       │ 71       │ 94                │

**`scope_excluded` 행이 비교표의 핵심입니다.** 최저가가 실제로 최저가가 아님을 드러내는 것이 이 기능의 가치입니다. Deal OS의 히든코스트 감지 사상을 CRE에 맞게 구현한 형태입니다.

### 7.2 AI 요약 가드

`quote-diff-summarizer` 에이전트는 **차이를 서술만 하고 추천하지 않습니다.**

```

```

크리딜 AI 규칙("가격 권장·투자 조언 금지")과 일관됩니다.

## 8. 상태 머신

```
[RFQ]  open ──▶ quoted ──▶ awarded ──▶ (Engagement 생성)
         └──▶ cancelled / expired

[Engagement]
created ──▶ escrow_held ──▶ in_progress ──▶ delivered ──▶ accepted ──▶ settled
                              │                  │            │
                              │                  │            └─ 배지 발급 ★
                              │                  └─ revision_requested (재제출)
                              └─ cancelled (에스크로 환불)
                                                 
                        disputed ◀── (양측 어디서든 제기 가능)
```

### 분쟁 처리 (1단계 = 수동)

Deal OS 로드맵에는 "AI 1차 중재"가 있으나 **1단계에서는 이식하지 마십시오.** 30건 규모에서 관리자 수동 처리가 더 정확하고 안전합니다. 자동 중재는 잘못된 판정 시 회복 불가능한 신뢰 손상을 만듭니다.

- 분쟁 접수 → 에스크로 동결 → 관리자 검토 → 전액/부분/환불 결정
- SLA: 접수 후 5영업일 내 1차 회신

## 11. 수용 기준

- [ ] `verification_status != 'verified'`인 전문가는 디렉토리에 노출되지 않는다
- [ ] 자격증·사업자등록 미검증 시 `verified` 전이가 불가하다
- [ ] **전문가는 다른 전문가의 견적을 조회할 수 없다** (담합 방지)
- [ ] 에스크로 금액이 한도(기본 2천만원)를 초과하면 결제가 차단된다 (API + DB 이중)
- [ ] `category IN ('property_purchase','brokerage_fee')`에 에스크로가 적용되지 않는다
- [ ] Group B 전문가에게 플랫폼 수수료가 부과되지 않는다 (`platform_fee_rate = 0`)
- [ ] 견적 제출 시 `scope_excluded` 입력이 강제된다 (빈 배열 허용, NULL 불가)
- [ ] RFQ의 `disclosure_level='blind'`일 때 정확한 지번이 전문가에게 노출되지 않는다
- [ ] 산출물 제출 후 7일 무응답 시 자동 승인되고 정산이 실행된다
- [ ] 산출물 승인 시 해당 필드의 `provenance_badges`가 `expert_verified`로 승격된다
- [ ] 배지에 만료일이 설정되며 만료 후 자동으로 하위 등급으로 강등된다
- [ ] IM 뷰어에 전문가 실명이 노출되지 않는다
- [ ] `quote-diff-summarizer`가 특정 전문가를 추천하는 문구를 생성하지 않는다 (프롬프트 가드 테스트)
- [ ] 모든 AI 실행이 `ai_runs`에 기록된다

## 14. 단계별 확장 계획

| 단계 | 범위 | 시점 |
|:---|:---|:---|
| **1단계 (본 명세)** | Group A 7개 카테고리, 수동 검증, 수동 분쟁 처리 | P1 |
| 2단계 | Group B 확장 (법무 확정 시), 자동 자격 조회 API 연동 | P2 |
| 3단계 | 매수자 직접 의뢰 (중개인 경유 없이), 전문가 구독 티어 | P2 |
| 4단계 | 전문가 산출물 → 데이터 자산화 (실사 결과 DB) | P2+ |

4단계가 장기 가치입니다. 수백 건의 건물 상태 점검·설비 실사 결과가 축적되면, 그 자체가 **금융기관 담보평가와 보험사에 판매 가능한 데이터**가 됩니다. 비주택 부동산은 정보 공백이 커 이런 실측 데이터의 희소성이 높습니다.
