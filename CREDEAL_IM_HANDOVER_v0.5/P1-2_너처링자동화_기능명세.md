## 0. 요약

### 0.1 문제 정의 — 크리딜에서 가장 조용한 손실

크리딜의 딜 사이클은 **6개월~1년**입니다. 그런데 크리딜에는 그 기간 동안 고객 관계를 유지하는 자동화가 **하나도 없습니다.**

```
[현재]
딜카드 생성 ──▶ IM 발송 ──▶ ??? (6~10개월) ──▶ 성사 또는 소멸
                              ↑
                     시스템이 아무것도 하지 않음
                     중개인의 기억력에만 의존
```

중개인 1인당 연 성사 3~5건, 수입 전액이 성공보수인 구조에서 **잊혀서 사라지는 딜 1건은 연소득의 20~30%**입니다. 이것은 기능 부족이 아니라 **측정되지 않는 누수**입니다.

### 0.2 역설 — 짧은 딜보다 긴 딜에서 너처링이 더 중요합니다

Deal OS는 수일~수주짜리 여행·웨딩 딜을 위해 너처링을 만들었습니다. 그런데 **짧은 딜은 잊어버릴 틈이 없습니다.** 8개월짜리 딜이 3개월째에 잊힙니다.

> **Deal OS의 너처링 자산은 원래 도메인보다 CRE에서 가치가 더 큽니다.** 이것이 본 과제를 P1 신규로 추가하는 이유입니다.

### 0.3 Deal OS 이식 매핑

| # | Deal OS 자산 | 크리딜 대상 | 이식 방식 | 개작률 |
|:--|:---|:---|:---|---:|
| 1 | `followupAgent` + `funnel-followup-daily` | `nurture-scheduler` | 골격 그대로, 케이던스 재정의 | 30% |
| 2 | `funnel-stale-daily` (7일 → dormant) | `deal-stale-daily` | 임계값 7일 → **60일** | 20% |
| 3 | `lead-auto-nurture` | `deal-auto-nurture` | 액션 세트 교체 | 40% |
| 4 | `funnelDiagnosisAgent` (7축) | `deal-readiness-agent` | **7축 전면 재설계** | 85% |
| 5 | `proofExpansionAgent` | `proof-expansion-agent` | 출력 채널 교체 (매거진·프로필) | 45% |
| 6 | `vendorLeadScoreAgent` | `counterparty-score-agent` | 대상 교체 (벤더 → 매도·매수인) | 60% |
| 7 | `leadIntakeAgent` | ❌ 이식 안 함 | 크리딜 `memo-router-agent`와 중복 | — |
| 8 | `proposalDraftAgent` | ❌ 이식 안 함 | 크리딜 `buyer-memo-writer`와 중복 | — |
| 9 | `funnel_leads` 스키마 (스코어 0-100, 7단계) | `deal_nurture_state` | 상태 체계 재정의 | 50% |
| 10 | Admin CRM 리드 워크벤치 | `/admin/nurture/*` | 화면 구조 이식 | 35% |

**6개 에이전트 중 4개 이식, 2개는 크리딜 기존 에이전트와 중복이므로 제외합니다.** 무비판적으로 6개를 다 가져오면 `memo-router-agent`와 `leadIntakeAgent`가 같은 일을 두 번 하게 됩니다.

## 1. 목적 및 성공 기준

### 1.1 목적

딜 사이클 전 구간에서 **정체를 자동 탐지하고, 다음 행동을 중개인에게 제시하며, 방치된 딜을 되살린다.**

### 1.2 성공 기준 (릴리스 후 16주)

| 지표 | 목표 | 측정 |
|:---|:---|:---|
| 너처링 액션 발생 건수 | 주당 200건 이상 | `nurture_actions` |
| 액션 수행률 (중개인이 실제로 실행) | 40% 이상 | `completed` / `dispatched` |
| **60일 이상 정체 딜 비율** | **30% → 15%로 감소** | `deal_nurture_state.stale_days > 60` |
| 되살아난 딜 (dormant → active) | 20건 이상 | 상태 전이 로그 |
| 딜 준비도 점수 평균 상승 | +12점 | `readiness_score` 추이 |
| **딜당 소요일수** | **−15%** | P0-3 Closed 데이터 기준 |

마지막 지표가 최종 목표입니다. 너처링의 가치는 성사율이 아니라 **속도**로 먼저 나타납니다.

## 2. 핵심 설계 판단

### 2.1 판단 ① — 자동 발송이 아니라 "행동 제안"입니다

Deal OS는 B2C 리드에 자동 이메일을 발송합니다. **CRE에서 이 방식을 그대로 쓰면 안 됩니다.**

| 이유 | 설명 |
|:---|:---|
| 관계의 성격 | 50억 자산 소유주에게 자동 발송 메일이 가면 관계가 손상됩니다 |
| 규제 | 자동 발송 콘텐츠가 가격·투자 조언을 담으면 크리딜 AI 규칙 및 공인중개사법 저촉 |
| 신뢰 | 중개인의 이름으로 나가는 메시지를 시스템이 임의 발송하면 중개인이 통제권을 잃습니다 |

> **설계 원칙: 시스템은 "지금 이 사람에게 이런 연락을 하십시오"를 제안하고, 발송 버튼은 중개인이 누릅니다.**

예외는 **거래 사실 알림**뿐입니다 (일정 확정, 게이트 요청 도착, 서명 요청). 이는 이미 크리딜이 하고 있습니다.

### 2.2 판단 ② — 7축 진단을 전면 재설계합니다

Deal OS의 7축은 **콘텐츠·마케팅 준비도** 중심입니다.

```
Deal OS 7축: 질문 명확성 · 답변 완결성 · 증거 가시성 · 경계 안전성
            · CTA 강도 · 미디어 준비도 · ZFAC 준비도
```

CRE에서는 **딜 자체의 성사 가능성**을 진단해야 합니다. 축 이름만 바꾸는 것이 아니라 개념을 통째로 갈아야 합니다.

### 2.3 판단 ③ — 진단 데이터는 이미 시스템 안에 있습니다

새 데이터를 수집할 필요가 거의 없습니다. 7축 전부가 크리딜이 이미 가진 데이터에서 계산됩니다. 이것이 이 과제의 공수가 낮은 이유입니다.

## 3. CRE판 딜 준비도 7축

### 3.1 축 정의

| # | 축 | 배점 | 데이터 출처 | 낮을 때의 의미 |
|:--|:---|---:|:---|:---|
| 1 | **자료 완비도** | 20 | Owner Readiness 체크리스트 10항목 | IM 품질 저하, 매수자 신뢰 하락 |
| 2 | **가격 현실성** | 20 | 호가 vs 실거래가 밴드(`real-transaction-api`) | 최다 무산 원인 |
| 3 | **매도 의사 확실성** | 15 | 전속 여부(P0-3), 응답 속도, 조건 변경 빈도 | 시간 낭비 위험 |
| 4 | **권리 청결도** | 15 | 등기정보광장(`registry-api`) 근저당·가압류·신탁 | 실사 단계 붕괴 |
| 5 | **규제 통과 가능성** | 10 | 토허 스크리너(P0-2), 용도지역 | 계약 후 무산 |
| 6 | **금융 조달 가능성** | 10 | IM의 LTV·Equity Required, 매수자 자기자본 | 잔금 단계 붕괴 |
| 7 | **매수 수요 두께** | 10 | 크로스브로커 풀(P0-1) 매칭 후보 수 | 장기 정체 |

## 4. 너처링 상태 모델

### 4.1 딜 너처링 상태 (Deal OS `funnel_leads` 7단계 → CRE 재정의)

| 상태 | 정의 | 진입 조건 | 정체 임계 |
|:---|:---|:---|---:|
| `sourcing` | 소유주 접촉 시도 중 | 딜카드 생성 | 30d |
| `mandated` | 매물 수임 완료 | 보수약정 또는 구두 수임 | 45d |
| `marketing` | 매수자 탐색 중 | IM 승인·배포 | 60d |
| `engaged` | 특정 매수자와 진행 | 게이트 G2 이상 승인 | 30d |
| `negotiating` | 조건 협상 중 | 임장 완료 또는 조건 제시 | 30d |
| `contracted` | 계약 체결 | 보수약정 서명 | 90d |
| `closed` | 잔금 완료 | `deal_outcome='closed'` | — |
| `dormant` | 휴면 | 정체 임계 초과 | — |
| `lost` | 소멸 | 명시적 종료 또는 dormant 180d | — |

**Deal OS의 `funnel-stale-daily`는 7일 임계입니다. CRE에서는 30~90일**입니다. 이 숫자를 그대로 가져오면 모든 딜이 하루 만에 dormant가 됩니다.

### 4.2 상태 전이

```
sourcing ──▶ mandated ──▶ marketing ──▶ engaged ──▶ negotiating ──▶ contracted ──▶ closed
   │            │             │            │             │              │
   └────────────┴─────────────┴────────────┴─────────────┴──────────────┘
                              ▼
                          dormant ──(180d)──▶ lost
                              │
                              └──(재접촉 성공)──▶ 이전 상태로 복귀
```

**dormant에서의 복귀 경로가 핵심입니다.** Deal OS에는 dormant가 종착지에 가깝지만, CRE에서는 **6개월 뒤 시장이 바뀌면 되살아나는 딜이 많습니다.** 금리 변동, 토허 해제, 임차인 변경이 전부 재점화 트리거입니다.

## 5. 데이터 모델

### 5.1 `deal_nurture_state`

```sql
-- migration 00085_deal_nurture_state.sql

CREATE TABLE deal_nurture_state (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  building_id       UUID NOT NULL REFERENCES building_ssot_lite(id),
  broker_id         UUID NOT NULL REFERENCES profiles(id),

  stage             TEXT NOT NULL DEFAULT 'sourcing'
                      CHECK (stage IN ('sourcing','mandated','marketing','engaged',
                                       'negotiating','contracted','closed','dormant','lost')),
  previous_stage    TEXT,
  stage_entered_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_activity_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  stale_days        INTEGER GENERATED ALWAYS AS
                      (EXTRACT(DAY FROM (now() - last_activity_at))::INTEGER) STORED,

  readiness_score   NUMERIC,
  readiness_grade   TEXT CHECK (readiness_grade IN ('A','B','C','D')),
  readiness_axes    JSONB,          -- 7축 개별 점수 + 사유
  readiness_at      TIMESTAMPTZ,

  next_action       TEXT,           -- 다음 권고 행동
  next_action_due   DATE,
  snooze_until      DATE,           -- 중개인이 미룬 경우

  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (building_id)
);

CREATE INDEX idx_dns_stale ON deal_nurture_state (broker_id, stale_days DESC)
  WHERE stage NOT IN ('closed','lost');
CREATE INDEX idx_dns_due ON deal_nurture_state (next_action_due)
  WHERE next_action_due IS NOT NULL;
```

> `stale_days`를 GENERATED 컬럼으로 두면 매번 계산할 필요가 없고 인덱스도 걸립니다.

### 5.2 `nurture_actions` — 제안된 행동

```sql
-- migration 00086_nurture_actions.sql

CREATE TABLE nurture_actions (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  building_id       UUID REFERENCES building_ssot_lite(id),
  broker_id         UUID NOT NULL REFERENCES profiles(id),
  target_type       TEXT NOT NULL CHECK (target_type IN ('owner','buyer','tenant','co_broker','expert')),
  target_ref        UUID,

  action_type       TEXT NOT NULL,   -- 아래 6.1 액션 카탈로그 참조
  priority          SMALLINT NOT NULL DEFAULT 3 CHECK (priority BETWEEN 1 AND 5),
  reason            TEXT NOT NULL,   -- 왜 지금 이 행동인지
  suggested_message TEXT,            -- AI 초안 (발송은 중개인이 결정)

  status            TEXT NOT NULL DEFAULT 'pending'
                      CHECK (status IN ('pending','dispatched','completed','dismissed','expired')),
  dispatched_at     TIMESTAMPTZ,
  completed_at      TIMESTAMPTZ,
  dismissed_reason  TEXT,
  expires_at        TIMESTAMPTZ NOT NULL DEFAULT (now() + interval '14 days'),

  generated_by      TEXT NOT NULL,   -- 'nurture-scheduler','readiness-agent' 등
  ai_run_id         UUID,

  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_na_inbox ON nurture_actions (broker_id, status, priority DESC, created_at DESC);
```

**`dismissed_reason`을 반드시 받으십시오.** 중개인이 왜 이 제안을 무시했는지가 규칙 개선의 유일한 학습 신호입니다.

### 6.2 크론 파이프라인 (Deal OS 5개 → CRE 6개)

| 크론 | 주기 | 역할 | Deal OS 원본 |

### 6.3 액션 생성 로직 (규칙 우선, LLM 최소)

```
[nurture-daily-scan]
1. stage NOT IN ('closed','lost') 인 딜 전체 조회
2. 각 딜에 대해 규칙 매트릭스 평가 (6.1 카탈로그)
   → 순수 규칙 기반. LLM 호출 없음
3. 트리거된 액션에 대해서만:
   - 우선도 1~2 → suggested_message를 LLM으로 생성
   - 우선도 3~5 → 템플릿 문구 사용
4. 중개인당 1일 최대 5건으로 제한 (우선도순 절삭)
5. snooze_until 이 미래인 딜은 제외
```

> **1일 최대 5건 제한이 중요합니다.** Deal OS는 B2C라 볼륨이 크지만, CRE 중개인은 파이프라인이 20~50건입니다. 매일 30건의 액션을 받으면 전부 무시하게 됩니다. **적게 주고 실행률을 높이는 것**이 설계 목표입니다.

### 6.4 AI 에이전트 명세

#### `deal-readiness-agent` (Deal OS `funnelDiagnosisAgent` 개작)

```yaml
입력:
  building_ssot: 건물 SSoT
  owner_readiness: 체크리스트 상태
  market_band: 실거래 밴드
  registry: 권리 관계
  ltp_screening: 토허 판정
  match_summary: 풀 매칭 요약 (S/A/B/C 건수)
출력 (Zod 검증):
  score: number (0-100)
  grade: 'A'|'B'|'C'|'D'
  axes: [{ axis, score, max, reason }]  # 7개
  top_gaps: string[]                     # 최대 3개
  suggested_actions: action_type[]
제약:
  - 가격을 제안하지 않는다 (괴리 사실만 서술)
  - 투자 판단을 서술하지 않는다
  - 법률·세무 결론을 내지 않는다
  - 축별 점수는 규칙 계산 결과를 그대로 사용하며 LLM이 임의 조정하지 않는다
```

**마지막 제약이 핵심입니다.** LLM은 **점수를 매기지 않고 사유를 서술만** 합니다. 점수를 LLM이 매기면 재현성이 없고 중개인이 신뢰하지 않습니다.

#### `nurture-message-writer`

```yaml
입력: action_type, 상대방 컨텍스트(비식별), 딜 요약, 중개인 프로필
출력: suggested_message (카톡 3~5줄, 크리딜 kakaoText 규칙 준수)
제약:
  - 가격·수익률 수치를 새로 생성하지 않는다 (기존 필드 인용만)
  - 확정 표현 금지 ("반드시 오릅니다" 등)
  - 발송하지 않는다. 초안만 반환한다
```

#### `proof-expansion-agent` (Deal OS 원본 개작)

```yaml
트리거: fee_agreements.deal_outcome = 'closed'
입력: 딜 요약, 소요기간, 관여 기능(딜카드/IM/게이트/전문가)
출력:
  - 매거진 삽입용 사례 초안 (블라인드 처리)
  - 브로커 프로필 실적 항목
  - 내부 리더보드용 요약
제약:
  - 거래가·당사자 정보는 자동 블라인드 (DisclosureGuardAgent 통과 필수)
  - 초기 상태 draft. 중개인 승인 후 게시
```

> **이 에이전트가 GTM Layer 1의 "성공사례 5건"을 자동 생산합니다.** 400명 조직에서 확산은 제품 성능이 아니라 옆자리 동료의 증언이 만드는데, 그 증언을 시스템이 만들어 줍니다.

## 8. 수용 기준

- [ ] 중개인 1인당 1일 액션 생성이 5건을 초과하지 않는다
- [ ] `snooze_until`이 미래인 딜에는 액션이 생성되지 않는다
- [ ] 액션 생성은 규칙 기반이며, LLM은 메시지 초안에만 사용된다
- [ ] **어떤 메시지도 자동 발송되지 않는다** (거래 사실 알림 제외)
- [ ] `deal-readiness-agent`가 축별 점수를 임의 조정하지 않는다 (규칙 계산값 사용)
- [ ] 준비도 점수가 매수자에게 노출되지 않는다
- [ ] `dismissed_reason`이 기록된다
- [ ] dormant 딜이 재활성화 시 이전 stage로 복귀한다
- [ ] 정체 임계값이 배포 없이 관리자 화면에서 조정된다
- [ ] `proof-expansion-agent` 출력이 `DisclosureGuardAgent`를 통과한다
- [ ] 성사 사례 초안이 중개인 승인 전에 게시되지 않는다
- [ ] 모든 크론 실행이 로깅되며 실패 시 재시도된다
- [ ] 다이제스트가 Morning Intelligence Hub 안에 통합된다 (별도 알림 아님)

## 10. 선행 의존성

이 과제는 **단독으로는 효과가 절반입니다.** 7축 중 4축이 P0 산출물에 의존합니다.

| 축 | 의존 과제 | 없을 때 |
|:---|:---|:---|
| 축5 규제 통과 | **P0-2 토허 스크리너** | 해당 축 제외 (100점 → 90점 스케일) |
| 축7 매수 수요 두께 | **P0-1 매수자 풀** | 내 매수자만으로 계산 (신호 약함) |
| 축3 매도 의사 | **P0-3 보수약정** | 전속 여부 미확인 |
| — | **P0-3 Closed 데이터** | 「딜당 소요일수 −15%」 측정 불가 |

> **권고 순서: P0 3건 완료 → P1-2 너처링 → P1-1 전문가 마켓플레이스**
>
> 다만 P1-1은 P0 의존도가 낮으므로 **병렬 착수가 가능**합니다. 인력이 확보되면 두 과제를 동시에 가는 것이 전체 일정에 유리합니다.
