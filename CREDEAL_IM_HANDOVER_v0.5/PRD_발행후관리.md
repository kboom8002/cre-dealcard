# PRD — 발행 후 관리 (Post-Publish Management)

> 발행된 IM이 낡아 가는 것을 시스템이 알아채고, 매수자 반응을 근거로 개선을 제안합니다.
> 개발 명세는 `POST_PUBLISH_SPEC.md`가 소유합니다.

| | |
|---|---|
| **버전** | v1.0 (draft) |
| **온톨로지** | v0.4.0 |
| **우선순위** | **P1** — Wedge(IM Studio) 다음 |
| **최종 수정** | 2026-08-03 |

---

## 1. 문제

### 1.1 발행하면 끝입니다

지금 구조에서 IM은 발행 시점에 검증되고, 그 뒤로는 아무도 보지 않습니다.

```
발행 (2026-05-12)  ──────────────────────────▶  현재 (2026-08-03)
   룰 통과                                          ?
   등급 B                                          같은 링크가 여전히 유통 중
   등기부 2026-04 발급                              4개월 경과
   301호 계약 만료 2026-09                          D-38
```

**링크는 살아 있고 내용은 낡았습니다.** 매수자는 그 사실을 모른 채 읽습니다.

### 1.2 반응이 보이지 않습니다

`view.section`·`view.completed` 이벤트는 이미 수집됩니다. 그런데 중개인 화면에는 **열람 수 밖에** 안 보입니다.

12명이 열었는데 9명이 3페이지에서 멈췄다면 그 페이지에 문제가 있습니다. 지금은 이 사실이 데이터베이스에만 있고 아무에게도 도달하지 않습니다.

### 1.3 그래서 성사가 관측되지 않습니다

v3.1의 moat은 **매수자 풀 + 성사 관측**입니다. 그런데 `outcome.recorded`는 중개인이 시스템에 돌아와야 쌓입니다.

**발행하고 끝나면 돌아올 이유가 없습니다.** 이것이 관측 설계의 마지막 구멍입니다.

## 2. 목표와 비목표

### 2.1 목표

| # | 목표 | 측정 |
|---:|---|---|
| 1 | 낡은 IM이 유통되는 것을 막는다 | 신선도 경고 해소율 |
| 2 | 반응 데이터를 중개인에게 도달시킨다 | 신호 확인율 |
| 3 | **중개인이 발행 후에도 돌아오게 한다** | 발행 후 30일 내 재방문율 |
| 4 | 성사 결과가 기록되게 한다 | `outcome.recorded` 기록률 |

3번이 핵심입니다. 1·2번은 3번을 위한 수단이고, 3번이 4번을 가능하게 합니다.

### 2.2 비목표

명확히 **하지 않는 것**입니다.

| 안 하는 것 | 이유 |
|---|---|
| 발행된 IM의 내용을 사후 수정 | PublishRecord 재현성이 깨짐. 개선은 **재발행** |
| L1 산술 · L2 기준 재검사 | C01~C32 · G10이 발행 시 이미 판정. 중복이자 정본 충돌 |
| AI에게 법적 판정 요청 | T-C / T-R 규칙군이 소유. AI는 상임법·주임법을 섞음 |
| AI에게 시세·가격 제안 요청 | 근거 없는 수치 생성. 프롬프트 세트와 동일한 금지 |
| 매수자 화면에 점검 기능 노출 | 모바일 IM은 매수자 문서. 관리는 중개인 화면 |
| 자동 재발행 | 재발행은 중개인의 판단·책임 |

## 3. 사용자와 시나리오

### 3.1 주 사용자

**IM을 3건 이상 발행한 중개인.** 1건만 발행한 사람에게는 관리할 것이 없습니다.

### 3.2 시나리오 A — 낡은 IM

> 김 중개사는 5월에 당산동 물건 IM을 발행했다. 8월 초, 앱을 열자 딜 목록에 표시가 떠 있다.
>
> **"당산동 근생빌딩 — 확인 필요 2건"**
>
> 들어가 보니 등기부가 4개월 전 것이고, 301호 헬쓰장 계약이 38일 뒤 만료다. 계약 만료는 알고 있었지만 IM에 그 내용이 없다는 건 생각 못 했다.
>
> 등기부를 새로 뗀다. 변경 없음이 확인된다. 301호는 재계약 협의 중이라고 메모를 남긴다. 두 건 다 해소 표시로 바뀐다.
>
> 재발행할지 묻는다. 등기부는 변경이 없었으니 `cosmetic`이고, 301호 메모는 `material`이다. 재발행하기로 한다.

### 3.3 시나리오 B — 반응 신호

> 박 중개사가 발행한 IM을 14명이 열었는데 문의가 하나도 없다. 딜 화면에 신호가 떠 있다.
>
> **"3페이지(임대 현황)에서 이탈 79% — 평균 24%"**
>
> [원인 가설 보기]를 누른다. AI가 세 가지를 제시한다.
>
> - 3페이지에 표가 두 개 연속으로 나와 모바일에서 스크롤이 길다
> - 공실 정보가 표 안에만 있고 요약 문장이 없다
> - 다음 페이지로 넘어갈 이유가 문장으로 제시되지 않았다
>
> 각 항목에 근거로 삼은 데이터가 붙어 있다. 첫 번째는 맞는 것 같다. 표를 나누고 요약 문장을 넣어 재발행한다.

### 3.4 시나리오 C — 성사 기록

> 이 중개사의 딜이 3주째 열람이 없다. 시스템이 묻는다.
>
> **"이 물건, 어떻게 됐나요?"**  `[진행 중] [성사] [무산] [보류]`
>
> 성사를 누르니 간단한 확인 두 개만 나온다. 거래가와 성사일. 30초면 끝난다.

**C가 4번 목표를 직접 달성합니다.** 물어보지 않으면 아무도 먼저 기록하지 않습니다.

## 5. 무엇을 룰이 하고 무엇을 AI가 하는가

**이 경계가 이 기능의 설계 핵심입니다.** 섞으면 판정의 정본이 둘이 됩니다.

| 영역 | 담당 | 이유 |
|---|---|---|
| 등기부 경과 · 계약 만료 · 공시지가 갱신 | **룰 (F)** | 날짜 비교. 확률이 필요 없음 |
| 이탈률 · 완독률 이상 탐지 | **룰 (S)** | 통계 비교 |
| **이탈 원인 가설** | **AI** | 룰로 표현 불가 |
| **문장 개선안** | **AI** | 룰로 표현 불가 |
| 산술 · 기준 표기 | **검사 안 함** | 발행 시 C·G가 이미 판정 |
| 법적 판정 | **룰 (T-C/T-R)** | AI 위험 |
| 시세 · 가격 | **누구도 안 함** | 근거 없는 수치 생성 금지 |

### 5.1 AI 호출은 온디맨드

전 딜에 자동으로 AI를 돌리면 비용이 폭발하고, 대부분은 읽히지도 않습니다.

```
룰 검사        전 발행 딜 · 일 1회 · 무료
AI 호출        중개인이 [원인 가설 보기] 누를 때만
```

예상 호출률은 신호 발생 딜의 **30% 내외**로 봅니다. 실측 후 조정합니다.

## 6. 성공 지표

| 지표 | 정의 | 목표 (3개월) |
|---|---|---:|
| **발행 후 30일 재방문율** | 발행 딜 중 30일 내 중개인 재방문 | **60%** |
| 신선도 경고 해소율 | 발생 대비 처리 (무시 포함) | 70% |
| `outcome.recorded` 기록률 | 종료 딜 중 결과 기록 | **50%** |
| 재발행률 | 발행 딜 중 1회 이상 재발행 | 35% |
| AI 제안 채택률 | 제안 중 실제 반영 | 25% |

### 6.1 목표치의 근거와 한계

**전부 추정치입니다.** 비교할 만한 선례가 없습니다. 3개월 뒤 실측으로 재설정하며, 특히 `outcome.recorded` 50%는 낙관적일 수 있습니다 — 무산된 딜은 기록하고 싶지 않은 심리가 있습니다.

무산 기록을 유도하려면 **무산 사유가 매칭 품질 개선에 쓰인다는 것**을 보여줘야 합니다. 그냥 물으면 안 답합니다.

## 7. 리스크

| # | 리스크 | 가능성 | 영향 | 대응 |
|---:|---|:-:|:-:|---|
| 1 | **알림 피로** — 경고가 많아 무시하게 됨 | 상 | 상 | 딜당 상위 3건만. 심각도 컷 상향 |
| 2 | AI 가설이 틀림 | 상 | 중 | "가설"로 명시. 근거 데이터 병기. 채택은 중개인 |
| 3 | 반응 표본 부족 (열람 5명 미만) | 상 | 중 | 최소 표본 미달 시 신호 억제 |
| 4 | AI 비용 초과 | 중 | 중 | 온디맨드 + 딜당 월 호출 상한 |
| 5 | 재발행 남발로 매수자 혼란 | 중 | 상 | `critical` 시 grant 무효화 고지 |
| 6 | **중개인이 낡은 IM을 알고도 방치** | 중 | 상 | 무시에도 사유 기록. 반복 시 조직 관리자에게 표시 |

### 7.1 1번이 가장 위험합니다

경고를 다 보여주면 아무것도 안 보여준 것과 같아집니다. 호텔 사례에서 결손 20개를 전부 나열하면 중개인이 그 자리에서 포기한다고 판단했던 것과 같은 문제입니다.

**딜당 3건 상한**을 P0에 넣습니다. 나중에 완화하는 것은 쉽지만, 처음부터 많이 보여주면 신뢰를 잃고 회복이 안 됩니다.

## 8. 의존성

| 의존 | 상태 |
|---|---|
| `publish_record` 테이블 | 존재 |
| `TrackEvent` 수집 (`view.section` · `view.completed`) | 명세 존재 · **구현 확인 필요** |
| 재발행 diff (`cosmetic`/`material`/`critical`) | 명세 존재 |
| 공부 API 재조회 | 존재 (수집 계층) |
| T-C / T-R 규칙군 | **v0.4 신규 — 미구현** |
| AI API | 신규 |

### 8.1 선행 확인 사항

**모바일 IM의 추적 스크립트.** 골든 샘플은 Safari 안정성 때문에 `<script>` 0개로 만들었습니다. 실제 발행물에서 `view.section` 이벤트가 수집되고 있는지 확인이 필요합니다.

수집되지 않는다면 P1-1(반응 신호)이 통째로 불가능합니다. **최소 추적 비콘만 넣고 콘텐츠 렌더링은 정적으로 유지**하면 두 요구를 모두 만족합니다 — 원래 문제는 `innerHTML` 주입이었지 스크립트 존재 자체가 아니었습니다.

## 9. 출시 범위

| 단계 | 범위 | 공수 |
|---|---|---:|
| **1차** | P0 전체 (F 규칙군 · 알림 · 해소 · 재발행 연동 · 성사 유도) | 18.5 solo-day |
| **2차** | P1-1 · P1-2 · P1-3 (반응 신호 · AI) | 14.0 |
| **3차** | P1-4 · P2 일부 | 8.0 |
| | **합계** | **40.5** |

1차만으로도 목표 1·3·4를 달성합니다. **2차가 차별점이지만, 1차 없이 2차만 하면 재방문 이유가 안 생깁니다.**
