# 수임 제안서 ↔ 보수약정(P0-3) 통합 명세

> **문서 버전** v1.0 · **작성 기준일** 2026-07-26
> **통합 대상** CREDEAL v2.0 「수임 제안서」(M2) + P0-3 「보수약정·전속중개 모듈」
> **배치** M2(전반부 12 md) + M5(후반부 26 md) — 총 38 md
> **선행 문서** P0 상세기능명세 P0-3절 · CREDEAL v2.0 기획안 4.2절

---

## 0. 왜 하나의 흐름인가

### 0.1 두 문서가 같은 것을 다루고 있었습니다

v2.0의 수임 제안서와 P0-3의 보수약정 모듈은 별개로 설계되었으나, 실무에서는 **하나의 연속된 대화**입니다.

```
[v2.0 M2]                                  [P0-3]
수임 제안서 ─────────────────────────────▶ 전속중개계약 ─▶ 보수약정
"전속으로 맡기면                            "맡기겠습니다"    "보수는 이렇게"
 이렇게 팔고,
 이렇게 보고합니다"
      │                                          │              │
   마케팅 문서                                 수임 확정      Closed 관측 시작
```

**수임 제안서는 보수약정 모듈의 마케팅 앞단입니다.** 제안서가 하는 약속을 계약이 확정하고, 그 계약이 시스템에 성사 데이터를 만들어 줍니다.

### 0.2 이 통합이 해결하는 세 가지

| # | 문제 | 어떻게 해결되는가 |
|:--|:---|:---|
| 1 | **v2.0에 Closed 확정 지점이 없음** | 파이프라인이 "협상→계약→종결"로 확장되었으나 무엇으로 확정하는지 미정의. **서명이 그 답** |
| 2 | **판례 리스크 노출** | 확인·설명서 기재 요율은 수수료 확정 계약서가 아니라는 판례. 별도 약정서가 유일한 방어 |
| 3 | **전속중개 문화 부재** | 제안서가 전속의 이득을 보여주고, 시스템이 그 약속을 이행 (아래 3절) |

### 0.3 가장 중요한 설계 발견

> **전속중개계약의 법정 의무를 시스템이 자동 이행하면, 그 의무가 부담이 아니라 제품 가치가 됩니다.**

전속중개계약을 체결하면 개업공인중개사는 정보 공개 의무와 **업무처리상황을 정기적으로 문서 통보할 의무**를 부담합니다. 이 통보 부담이 중개인이 전속을 꺼리는 이유 중 하나입니다.

그런데 크리딜은 이미 **열람 추적·리드 스코어링·Gate 요청 이력**을 갖고 있습니다. 이것을 정기 리포트로 자동 생성하면:

- 중개인: 통보 의무가 버튼 1회로 해결됨 → 전속 채택 장벽 제거
- 매도인: 실제 마케팅 진행 상황을 데이터로 확인 → 전속의 이득 체감
- 시스템: 정기 접점이 생김 → 딜이 잊히지 않음

**제안서가 "이렇게 보고합니다"라고 약속한 것을 시스템이 그대로 이행합니다.** 이것이 이 통합의 핵심 가치입니다.

> ⚠️ **법무 확인 필수**: 정보 공개 기한, 통보 주기, 통보 방식(문서/전자문서 인정 범위)의 구체 수치는 반드시 법무 확정 후 시드하십시오. 본 명세는 데이터 구조와 자동화 방식만 정의하며 법정 수치를 확정하지 않습니다.

## 1. 3문서 체계

| 문서 | 성격 | 법적 위상 | 서명 | 생성 시점 |
|:---|:---|:---|:---:|:---|
| **① 수임 제안서** | 마케팅·설득 문서 | 계약 아님 | ✕ | 매도인 접촉 시 |
| **② 중개계약서** (전속/일반) | 수임 관계 확정 | 법정 서식 기반 | ○ | 제안 수락 시 |
| **③ 보수약정서** | 보수 조건 확정 | 별도 약정 | ○ | ②와 동시 또는 직후 |

### 1.1 왜 ②와 ③을 분리하는가

법정 중개계약서 서식에도 보수 관련 기재란이 있으나, **판례상 확인·설명서에 기재된 요율만으로는 보수가 확정되지 않는다**는 점을 고려하면 보수 조건은 별도 약정으로 명확히 하는 것이 안전합니다. 특히 고액 상업용 거래에서는 상한 요율을 그대로 적용하지 않고 협의로 낮추는 것이 관행이므로, **협의 결과를 별도 문서로 남기는 것 자체가 방어**입니다.

다만 UX상으로는 **한 번의 서명 세션에서 ②와 ③을 연속 처리**합니다. 매도인에게 두 번 서명을 요구하지 마십시오.

### 1.2 일반중개 경로도 지원해야 합니다

한국 시장에 전속중개 문화가 없으므로, **전속을 강요하면 수임 자체를 놓칩니다.**

```
제안서 → [전속중개] → 전속계약 + 보수약정 → 법정 통보 자동화 ★
      → [일반중개] → 일반계약 + 보수약정 → 통보 자동화 없음
      → [약정만]   → 보수약정서만        → 최소 방어선
```

**세 번째 경로가 중요합니다.** 계약서 없이 구두로 진행 중인 딜에도 **보수약정서 하나만이라도** 받게 하십시오. 판례 리스크 방어의 최소선이며, Closed 관측의 최소 조건입니다.

## 2. 통합 상태 머신

```
                    ┌──────────────────────────────────────────┐
                    │            제안 단계 (M2)                 │
                    └──────────────────────────────────────────┘
  proposal_draft ──▶ proposal_sent ──▶ proposal_viewed ──▶ proposal_accepted
        │                  │                  │                    │
        └─ cancelled       ├─ expired         └─ (열람 이벤트 기록) │
                           └─ declined                             │
                                                                   ▼
                    ┌──────────────────────────────────────────┐
                    │            계약 단계 (M2)                 │
                    └──────────────────────────────────────────┘
                    agreement_draft ──▶ agreement_sent ──▶ signed
                           │                  │              │
                           └─ cancelled       └─ declined    │
                                                             ▼
                    ┌──────────────────────────────────────────┐
                    │         수임 이행 단계 (M5)               │
                    └──────────────────────────────────────────┘
                    mandated ──▶ (정기 통보 자동 발송) ──▶ 거래 결과 입력
                        │                                        │
                        ├─ expired (전속 기간 만료)                ├─ closed  → Pipeline: 종결
                        └─ terminated (해지)                      └─ failed  → 무산 사유 기록
```

### 2.1 파이프라인 연동

v2.0 파이프라인 7단계와의 매핑입니다.

| v2.0 파이프라인 | 통합 문서 상태 | 전이 트리거 |
|:---|:---|:---|
| 발굴 | — | 딜 생성 |
| 분석 | — | 데이터 충전 |
| **제안** | `proposal_sent` ~ `proposal_accepted` | 제안서 발송 |
| **마케팅** | `mandated` | **계약 서명 완료** ★ |
| 협상 | `mandated` (유지) | 매수 후보 등장 |
| **계약** | — | 매매계약 (시스템 밖) |
| **종결** | `deal_outcome = 'closed'` | **거래 결과 입력** ★ |

> **★ 표시 두 지점이 시스템이 딜의 실체를 관측하는 유일한 순간입니다.** v2.0 원안에는 이 두 지점이 없어 파이프라인 단계가 중개인의 수동 드래그에만 의존했습니다.

## 3. 전속중개 법정 의무 자동화 ★ 핵심 차별화

### 3.1 의무 → 기능 전환표

| 법정 의무 (확인 필요) | 크리딜 기존 자산 | 자동화 방식 |
|:---|:---|:---|
| **매물 정보 공개** (일정 기한 내) | 딜카드 공개 발행, 공동중개 네트워크(M5) | 계약 서명 시 공개 옵션 제시 → 발행 이력을 이행 증빙으로 보관 |
| **업무처리상황 정기 통보** (문서) | 열람 추적, Gate 요청, 리드 스코어, 활동 타임라인 | **정기 리포트 자동 생성 → 매도인 발송 → 발송 이력 보관** |
| 의뢰인 비공개 요청 존중 | Gate/블라인드 시스템 | 계약 시 공개 범위 선택 → 시스템이 강제 |

### 3.2 업무처리상황 통보 리포트 구성

```
┌──────────────────────────────────────────────────┐
│  업무처리상황 통보서                              │
│  역삼동 근린생활시설 · 제3회차                     │
│  통보 기간: 2026.09.01 ~ 2026.09.14              │
├──────────────────────────────────────────────────┤
│  ■ 마케팅 활동                                    │
│    투자설명서 발송         12건                   │
│    딜카드 공유            28건                    │
│    매거진 게재             1회                    │
│                                                  │
│  ■ 반응                                          │
│    IM 열람자              17명 (누적 41명)        │
│    상세정보 요청(Gate)      3건                   │
│    현장 임장               2건                    │
│                                                  │
│  ■ 매수 후보 현황                                 │
│    적합도 상위 후보         4건                   │
│    진행 중 협의            1건                    │
│                                                  │
│  ■ 다음 기간 계획                                 │
│    (중개인 입력 또는 AI 초안)                     │
│                                                  │
│  담당 개업공인중개사 · 등록번호 · 발송일시         │
└──────────────────────────────────────────────────┘
```

### 3.3 설계 원칙

| 원칙 | 이유 |
|:---|:---|
| **자동 생성, 수동 발송** | 중개인이 내용을 확인하고 발송 버튼을 누릅니다. 자동 발송은 하지 않습니다 |
| **개별 매수자 신원 미노출** | "17명 열람"은 되지만 "A법인 열람"은 안 됩니다. 매수자 정보 보호 |
| **가격·전망 서술 금지** | 활동 사실만 보고. 크리딜 AI 규칙("가격 권장·투자 조언 금지") 준수 |
| **발송 이력 영구 보관** | 의무 이행의 증빙. 분쟁 시 방어 자료 |
| **미발송 알림** | 통보 기한 도래 시 액션 큐에 표시 (M2 정체 탐지와 동일 메커니즘) |

### 3.4 부수 효과 — 딜이 잊히지 않습니다

정기 통보는 **강제된 접점**입니다. 2주에 한 번 매도인에게 리포트를 보내려면 그 딜을 열어야 하고, 그 순간 중개인은 딜 상태를 재확인합니다.

제가 P1-2에서 설계한 정체 탐지가 "시스템이 찔러 주는" 방식이라면, 정기 통보는 **"의무가 밀어 주는"** 방식입니다. 후자가 더 강력합니다.

## 4. 데이터 모델

### 4.1 `mandate_proposals` — 수임 제안서 (신규, M2)

```sql
-- migration 00088_mandate_proposals.sql

CREATE TABLE mandate_proposals (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  deal_id           UUID NOT NULL REFERENCES deals(id),
  broker_id         UUID NOT NULL REFERENCES profiles(id),

  -- 매도인 정보
  owner_name        TEXT NOT NULL,
  owner_contact     TEXT,                    -- 암호화 저장
  owner_client_id   UUID REFERENCES clients(id),

  -- 제안 내용 (Asset 데이터에서 파생)
  proposed_price_band JSONB,                 -- {min, max, basis} — 단일값 금지
  comparable_refs   JSONB,                   -- 비교 실거래 근거
  marketing_plan    JSONB,                   -- {channels[], timeline, sample_docs[]}
  proposed_type     TEXT NOT NULL CHECK (proposed_type IN ('exclusive','general')),
  proposed_period_days INTEGER,
  reporting_cycle_days INTEGER,              -- 통보 주기 (법무 확정값)

  -- 문서
  document_html     TEXT,
  document_hash     TEXT,

  status            TEXT NOT NULL DEFAULT 'draft'
                      CHECK (status IN ('draft','sent','viewed','accepted','declined','expired','cancelled')),
  sent_at           TIMESTAMPTZ,
  first_viewed_at   TIMESTAMPTZ,
  view_count        INTEGER NOT NULL DEFAULT 0,
  accepted_at       TIMESTAMPTZ,
  declined_reason   TEXT,
  expires_at        TIMESTAMPTZ,

  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_mp_broker ON mandate_proposals (broker_id, status, created_at DESC);
CREATE INDEX idx_mp_deal ON mandate_proposals (deal_id);
```

> **`proposed_price_band`를 단일값이 아니라 범위(JSONB)로 강제합니다.** v2.0의 원칙("재무 수치는 범위(±)·출처 표기")과 일관되며, AI가 특정 가격을 제시하는 것을 구조적으로 차단합니다.

### 4.2 `mandate_agreements` — 중개계약 + 보수약정 (P0-3 `fee_agreements` 확장)

```sql
-- migration 00089_mandate_agreements.sql
-- P0-3 명세의 fee_agreements를 제안서 연계 형태로 확장

CREATE TABLE mandate_agreements (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  proposal_id       UUID REFERENCES mandate_proposals(id),   -- NULL 가능(제안서 없이 직접 체결)
  deal_id           UUID NOT NULL REFERENCES deals(id),
  broker_id         UUID NOT NULL REFERENCES profiles(id),
  org_id            UUID REFERENCES organizations(id),

  -- 계약 유형
  mandate_type      TEXT NOT NULL
                      CHECK (mandate_type IN ('exclusive','general','fee_only')),
  counterparty_role TEXT NOT NULL
                      CHECK (counterparty_role IN ('seller','buyer','lessor','lessee')),
  counterparty_name TEXT NOT NULL,
  counterparty_contact TEXT,

  -- 전속 조건 (mandate_type='exclusive')
  mandate_from      DATE,
  mandate_to        DATE,
  disclosure_optout BOOLEAN NOT NULL DEFAULT false,   -- 의뢰인 비공개 요청
  reporting_cycle_days INTEGER,                       -- 법무 확정값
  next_report_due   DATE,

  -- 보수 조건 (P0-3 원안 유지)
  fee_basis         TEXT NOT NULL CHECK (fee_basis IN ('rate','fixed')),
  fee_rate          NUMERIC,
  fee_fixed_amount  NUMERIC,
  fee_cap_amount    NUMERIC,
  vat_included      BOOLEAN NOT NULL DEFAULT false,
  payment_timing    TEXT,
  negotiated_at     TIMESTAMPTZ,          -- ★ 협의 일시 (판례 방어)
  negotiation_note  TEXT,                 -- ★ 협의 내용 요지
  special_terms     TEXT,

  -- 상태
  status            TEXT NOT NULL DEFAULT 'draft'
                      CHECK (status IN ('draft','sent','signed','declined','expired','terminated','cancelled')),
  document_html     TEXT,
  document_hash     TEXT,
  sent_at           TIMESTAMPTZ,
  signed_at         TIMESTAMPTZ,
  terminated_at     TIMESTAMPTZ,
  termination_reason TEXT,

  -- 거래 결과 (Closed 관측)
  deal_outcome      TEXT CHECK (deal_outcome IN ('closed','failed','pending')),
  closed_price      NUMERIC,
  closed_at         DATE,
  failure_reason    TEXT,
  failure_detail    TEXT,

  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_ma_broker  ON mandate_agreements (broker_id, status);
CREATE INDEX idx_ma_report  ON mandate_agreements (next_report_due)
  WHERE mandate_type = 'exclusive' AND status = 'signed';
CREATE INDEX idx_ma_outcome ON mandate_agreements (deal_outcome, closed_at)
  WHERE deal_outcome IS NOT NULL;
```

#### 두 필드가 특히 중요합니다

| 필드 | 왜 중요한가 |
|:---|:---|
| **`negotiated_at` + `negotiation_note`** | "본 보수는 의뢰인과 협의하여 결정되었음"의 근거. 상한을 그대로 적용한 것이 아니라 협의했다는 사실이 기록됩니다 |
| **`failure_reason`** | 무산 사유는 성사가만큼 중요한 학습 데이터입니다. 대출 부결 / 호가 미합의 / 토허 불허 / 매수자 이탈 / 권리 문제 / 기타 — **선택지 기반**으로 받으십시오 |

### 4.3 `mandate_reports` — 업무처리상황 통보 (신규, M5)

```sql
-- migration 00090_mandate_reports.sql

CREATE TABLE mandate_reports (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  agreement_id      UUID NOT NULL REFERENCES mandate_agreements(id) ON DELETE CASCADE,
  sequence_no       INTEGER NOT NULL,        -- 제N회차
  period_from       DATE NOT NULL,
  period_to         DATE NOT NULL,

  activity_summary  JSONB NOT NULL,          -- 집계된 활동 (아래 구조)
  next_plan         TEXT,                    -- 중개인 입력 또는 AI 초안
  document_html     TEXT,
  document_hash     TEXT,

  status            TEXT NOT NULL DEFAULT 'generated'
                      CHECK (status IN ('generated','sent','viewed','overdue')),
  generated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  sent_at           TIMESTAMPTZ,
  sent_channel      TEXT,                    -- 'kakao','email','sms'
```

## 5. 제안서 생성 (M2 · v2.0 원안 스코프)

### 5.1 자동 구성 요소

v2.0의 "입력은 한 번, 산출은 여러 번" 원칙에 따라, 제안서는 **Deal 데이터에서 파생 생성**됩니다.

| 섹션 | 데이터 출처 | 자동/수동 |
|:---|:---|:---:|
| 자산 개요 | Asset 표준 스키마 (공공데이터 자동 파생) | 자동 |
| 시장 분석 | 실거래가 API + 권역 비교사례 | 자동 |
| **제안 가격 범위** | 비교사례 밴드 + 수익환원 | 자동 (**범위만**) |
| 마케팅 계획 | 템플릿 + 중개인 편집 | 반자동 |
| **산출물 샘플** | 이 딜의 실제 딜카드·IM 미리보기 | 자동 ★ |
| **보고 방식 데모** | 열람 추적 화면 캡처 | 자동 ★ |
| 중개인 프로필 | 브로커 프로필 (경력·자격·실적) | 자동 |
| 보수 조건 (예시) | 중개인 입력 | 수동 |

### 5.2 두 개의 ★ 항목이 설득력의 핵심입니다

**한국에 전속중개 문화가 없는 이유는 매도인이 전속의 이득을 체감하지 못하기 때문입니다.** 제안서에 다음 두 가지가 들어가면 이야기가 달라집니다.

1. **이 물건의 실제 딜카드·IM 미리보기** — "이렇게 만들어 드립니다"가 아니라 "이미 만들었습니다"
2. **열람 추적 화면 데모** — "몇 명이 봤는지, 누가 관심 있는지 2주마다 보고드립니다"

두 번째가 곧 3절의 법정 통보 자동화와 연결됩니다. **제안서의 약속과 시스템의 이행이 같은 기능입니다.**

### 5.3 AI 가드

```yaml
제안서 생성 시 금지:
  - 단일 가격 제시 (범위만 허용)
  - "지금이 매도 적기입니다" 등 시점 판단
  - 수익률 전망·상승 예측
  - 세무 효과 단정 ("양도세를 줄일 수 있습니다")
허용:
  - 비교 실거래 사실 서술
  - 마케팅 계획 서술
  - 과거 실적 인용 (검증된 것만)
```

## 6. 서명 플로우 (M2 후반 · P0-3 전반부)

### 6.1 단일 세션 설계

```
1. 매도인이 제안서 수락 (제안서 하단 [맡기겠습니다] 버튼)
       ↓
2. 중개인에게 알림 → 중개인이 계약 조건 입력
   - 계약 유형 (전속/일반/약정만)
   - 기간, 공개 범위(비공개 요청 여부), 통보 주기
   - 보수 조건 + 협의 내용 기록 (negotiation_note)
       ↓
3. 미리보기 → document_html 생성 + SHA-256
       ↓
4. 발송 → 매도인에게 카카오 알림톡 서명 링크
       ↓
5. 매도인: 링크 → 본인확인(SMS OTP) → 계약서 + 약정서 연속 열람 → 서명 1회
       ↓
6. 양측 PDF 사본 발송, status='signed', Deal 파이프라인 '마케팅'으로 전이
       ↓
7. (전속인 경우) 첫 통보 예정일 자동 설정 → 액션 큐 등록
```

### 6.2 서명 UX — 고령 사용자 전제

매도인은 60~70대일 수 있습니다.

| 항목 | 설계 |
|:---|:---|
| 테마 | **라이트 모드 고정** (크리딜 기본은 다크 모드) |
| 글자 크기 | 최소 18px, 본문 20px |
| 인증 | SMS OTP 기본. 카카오·토스 간편인증 선택 |
| 스크롤 | 계약서 전문 열람 후에만 서명 버튼 활성화 |
| 이탈 복구 | 링크 재발송 1탭 |
| 브라우저 | 카카오톡 인앱 브라우저 필수 대응 |

### 6.3 보안

- 서명 토큰 1회용, 만료 7일
- OTP 없이 서명 불가
- 서명 완료 후 문서 **불변** (수정 필요 시 신규 생성 + 이전 건 `cancelled`)
- 서명 링크 접근 로그 전량 기록

### 6.4 준법 설계 (P0-3 원안 승계)

| # | 원칙 | 구현 |
|:--|:---|:---|
| 1 | **상한 요율을 프리필하지 않는다** | 요율 입력란은 빈 값. 상한은 안내 문구로만 |
| 2 | **협의 사실을 기록한다** | `negotiated_at` + `negotiation_note` 필수 입력 |
| 3 | **컨설팅 명목 우회를 유도하지 않는다** | 실질이 알선이면 중개로 판단됨. 우회 UI 제공 금지 |
| 4 | **AI가 요율을 권장하지 않는다** | 문안 작성만 지원. 금액·요율 제안 금지 |
| 5 | **약정 주체는 자격 중개사** | 플랫폼은 계약 당사자가 아님을 명시 |
| 6 | **전자서명 효력** | 법무 확인. 미흡 시 공인전자서명 승격 |

## 8. Closed 관측과 학습 데이터

### 8.1 트리거

```sql
-- migration 00092_mandate_pipeline_sync.sql

CREATE OR REPLACE FUNCTION sync_deal_on_mandate()
RETURNS TRIGGER AS $$
BEGIN
  -- 서명 시 → 마케팅 단계
  IF NEW.status = 'signed' AND OLD.status IS DISTINCT FROM 'signed' THEN
    UPDATE deals SET pipeline_stage = 'marketing', updated_at = now()
     WHERE id = NEW.deal_id AND pipeline_stage IN ('sourcing','analysis','proposal');
  END IF;

  -- 성사 시 → 종결
  IF NEW.deal_outcome = 'closed' AND OLD.deal_outcome IS DISTINCT FROM 'closed' THEN
    UPDATE deals SET pipeline_stage = 'closed', closed_at = NEW.closed_at
     WHERE id = NEW.deal_id;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_deal_mandate
  AFTER UPDATE ON mandate_agreements
  FOR EACH ROW EXECUTE FUNCTION sync_deal_on_mandate();
```

### 8.2 파이프라인 수동 전이 제한

**`Closed` 단계로의 수동 드래그를 차단하십시오.** 약정서 결과 입력으로만 전이 가능해야 데이터 무결성이 유지됩니다.

### 8.3 학습 데이터 산출

| 산출물 | 용도 |
|:---|:---|
| 성사가 vs 최초 호가 괴리 | 가격 현실성 축(P1-2 준비도 7축) 보정 |
| 무산 사유 분포 | Deal Prediction 위험 요인 그래프 |
| 수임 → 성사 소요일 | 딜 단계 이동 속도 지표 |
| 전속 vs 일반 성사율 비교 | **전속의 실효성 입증 → 다음 제안서의 근거** ★ |

**마지막 항목이 복리로 작동합니다.** "저희 전속 물건은 평균 4.2개월에 팔렸습니다"가 데이터로 뒷받침되면, 그것이 다음 수임 제안서의 가장 강력한 문장이 됩니다.

## 10. 수용 기준

### M2 (전반부)

- [ ] 제안서의 `proposed_price_band`가 단일값으로 저장되지 않는다 (범위 강제)
- [ ] AI가 제안서에 시점 판단·수익률 전망을 생성하지 않는다 (프롬프트 가드 테스트)
- [ ] 제안서 열람 이벤트가 기록되고 중개인에게 알림된다
- [ ] 요율 입력란에 상한값이 프리필되지 않는다
- [ ] `negotiated_at`과 `negotiation_note` 없이 서명 발송이 불가하다
- [ ] 계약서와 약정서가 **한 번의 서명 세션**에서 처리된다
- [ ] OTP 없이 서명이 완료되지 않는다
- [ ] 서명 완료 문서는 수정 불가하며 `document_hash`로 검증된다
- [ ] 서명 링크는 1회용이며 7일 후 만료된다
- [ ] 서명 페이지가 라이트 모드로 표시되고 카카오 인앱 브라우저에서 동작한다
- [ ] 서명 시 Deal 파이프라인이 '마케팅'으로 자동 전이된다
- [ ] `fee_only` 경로(계약서 없이 약정서만)가 동작한다

### M5 (후반부)

- [ ] 통보 리포트가 기한 2일 전 자동 생성된다
- [ ] 리포트가 **자동 발송되지 않는다** (중개인 확인 후 발송)
- [ ] `activity_summary`에 개별 매수자 신원 필드가 존재하지 않는다
- [ ] 리포트에 가격·전망 서술이 포함되지 않는다
- [ ] 발송 이력이 영구 보관된다
- [ ] 통보 기한 경과 시 액션 큐에 우선도 1로 표시된다
- [ ] `deal_outcome='closed'` 입력 시 파이프라인이 '종결'로 자동 전이된다
- [ ] 파이프라인에서 '종결'로 수동 드래그가 불가하다
- [ ] `failure_reason`이 선택지 기반으로 입력된다
- [ ] 전속 만료 30/14/7일 전 알림이 발송된다

## 13. 이 통합의 전략적 의미

```
제안서가 전속을 판다
        ↓
전속이 법정 통보 의무를 만든다
        ↓
시스템이 통보를 자동화한다 → 의무가 제품 가치로 전환
        ↓
통보가 정기 접점을 만든다 → 딜이 잊히지 않는다
        ↓
서명과 결과 입력이 성사 데이터를 만든다
        ↓
성사 데이터가 "전속이 더 빨리 팔린다"를 입증한다
        ↓
그 입증이 다음 제안서의 가장 강력한 문장이 된다  ← 복리
```

**단일 기능이 아니라 순환 구조입니다.** v2.0의 수임 제안서와 P0-3의 보수약정을 따로 만들면 이 순환이 생기지 않습니다. 통합해야 하는 이유가 여기에 있습니다.
