# 통합 고도화 적용순서와 경영·제품 의사결정

## 1. 최종 권고

CREDEAL 개발팀은 네 문서군을 다음처럼 적용한다.

| 문서군 | 역할 | 적용 방식 |
|---|---|---|
| D54·D54-A·D55 | 제품·도메인 헌법 | 먼저 동결하고 모든 완료조건의 기준으로 사용 |
| D58 | 시스템 경계 결정 | 모바일·PPTX 형제채널과 CORE 책임분리를 채택 |
| 제작 파이프라인 SDD | 실행 기반 | 장시간 단일 요청을 재개 가능한 단계실행으로 교체 |
| IM CORE SDD | 사실·판정·발행계약 | 유효기준본·산출항목·공통 발행묶음을 구현 |
| 게이트 하네스 SDD | 검증·승인 통제 | 공통기반은 선행, 산출물별 검사는 해당 기능과 동시 구현 |

따라서 문서군 전체를 순차 프로젝트 네 개로 실행하지 않는다. **하나의 통합 프로그램 안에서 공통 선행작업을 먼저 하고, 산출물별 수직완결 단위로 전환한다.**

## 2. 효과적이고 안정적인 적용순서

### 1순위: 방법론과 정본을 동결한다

먼저 D54·D54-A·D55에서 다음을 제품 결정으로 승인한다.

- 외부 문서형식: 딜카드, L1, L1.5, L2, 향후 전문가형
- 렌트롤 표시수준과 임대 산출항목 허용조건
- 다필지 객체와 네 가지 면적 분모
- 중개인 의견과 분석가정의 분리
- 근거상태와 외부사용 허가상태의 분리
- 한국어 외부 카피와 내부 개발용어의 경계
- 사진 역할·대표사진 승인·적응형 배치
- 사람 편집승인이 필요한 범위

이 작업은 화면개발이 아니라 **후속 코드가 무엇을 사실로 저장하고 무엇을 외부에 말할 수 있는지 고정하는 선행 설계**다.

### 2순위: 현행 허위 안전신호를 봉합한다

아키텍처를 바꾸기 전에 현재 발행경로의 치명적 오류를 막는다.

- 생성 당시 주장목록·판정·검사보고서·규칙버전 저장
- 승인 API의 빈 Registry 재생성 제거
- `expectedHash` 없는 승인 거부
- `NOT_RUN/INDETERMINATE/SYSTEM_ERROR`의 차단 처리
- 무조건 통과·0 고정·false 고정 검사의 실제 관측기 연결
- 운영비 없는 NOI·자본환원율, 관리비 자동합산, 채권최고액 오표현 차단
- 기계검사와 사람승인 분리

이 단계는 기존 사용자 흐름을 유지한 채 배포한다. 새 UI보다 먼저 끝내야 한다.

### 3순위: 파이프라인 실행기반과 게이트 공통기반을 만든다

CORE의 도메인 객체보다 먼저 다음 기반을 확보한다.

- 실행·단계실행·산출물·사건보관함·승인사건 저장
- 멱등 명령, 임대시간, 심장박동, 재시도, 중단·재개
- 불변 산출물과 내용해시
- 7상태 검사결과와 적용성 판정
- 산출물 종류별 검사 프로필 실행면
- 스키마 검증과 규칙버전

이 기반 없이 CORE를 먼저 만들면 장시간 HTTP 요청, 중복 실행, 부분실패, 승인 재현성 문제를 다시 고쳐야 한다.

### 4순위: 딜카드를 독립 수직단위로 완성한다

딜카드는 IM보다 먼저 사용자에게 공개되므로 별도 발행물로 먼저 완성한다.

- 메모 원문과 `MemoObservationSet`
- 정확주소·간접 재식별·밴딩·과장표현 검사
- 중개인 공개확인
- 바텀시트 정정 후 오래된 딜카드 자동 전환

딜카드가 IM CORE의 미완성 사실을 대신하지 않도록 발행경계를 분리한다.

### 5순위: IM CORE v1을 완성한다

파이프라인 위에 다음 순서로 쌓는다.

```text
원자료·근거
→ 불일치·정정·매각범위
→ 불변 유효기준본
→ 산출항목·산식·허용상태
→ L1/L1.5/L2 가능범위와 CORE 검사
→ 공통 발행묶음
```

이 단계에서 렌트롤·다필지·사진·중개인 의견을 별도 부가기능으로 미루지 않는다. D55의 L1/L1.5가 요구하는 최소 객체를 포함해야 채널에서 임시 JSON을 만들지 않는다.

### 6순위: 모바일 L1/L1.5를 첫 IM 채널로 전환한다

모바일은 중개인의 일상 업무와 가장 가까우며 빠른 수직완결 검증이 가능하다.

- L1 자동 초안
- 적격한 경우 L1.5 후보 제안
- 중개인 의견·사진 반영표
- 한국 중개실무 카피
- 모바일 검사·편집승인·최종발행

PPTX 없이 독립적으로 발행되고, 기존 공개 URL은 유지한다.

### 7순위: PPTX IM Studio를 형제 채널로 만든다

공통 발행묶음이 안정된 후 별도 Studio를 활성화한다.

- 프로젝트·버전·독자·목적·소구점
- 페이지 구성, 문안, 사진, 표, 부록 편집
- 구조화 수치토큰
- 미리보기·지면검사·최종파일 검사
- 편집승인과 파일승인

Studio는 모바일 body를 변환하거나 원시 공공자료를 재판정하지 않는다.

### 8순위: 변경영향·최소 재생성과 전환을 완성한다

양 채널이 존재한 뒤 전체 의존그래프를 검증한다.

- 사실 변경: CORE부터 양 채널 무효화
- 의견·공개문구 변경: 해당 제안단위와 채널만 무효화
- 모바일 순서 변경: 모바일만 재조립
- PPTX 사진·레이아웃 변경: PPTX만 재렌더
- 정책·산식 변경: 영향 산출항목부터 재판정

그림자 실행과 카나리 1→10→50→100%를 거친 후 구형 신규생성 경로를 폐기한다.

## 3. 게이트 적용의 올바른 위치

| 시점 | 함께 구현할 게이트 |
|---|---|
| M1 | 공통 7상태, 해시 승인, 미실행 차단, 죽은 검사 제거 |
| M2 | 적용성, 관측값, 판정근거, 프로필, 검사보고서 영속화 |
| M3 | 메모·딜카드 블라인드 공개검사 |
| M4 | 근거·불일치·산출항목·산식·패키지 CORE 검사 |
| M5 | 모바일 카피·숫자·사진·가독성·승인 검사 |
| M6 | PPTX 수치대조·넘침·겹침·사진·파일해시 검사 |
| M7 | 승인 무효화·최소 재생성·교차채널 일관성 검사 |
| M8 | 변조시험·하네스 자기감사·실물 회귀검사 |

게이트팀의 완료조건은 검사코드 수가 아니라 **실제 원자료와 최종 발행물 변조를 검출하고 발행 API가 이를 차단하는 것**이다.

## 4. 병렬개발 허용범위

다음은 병렬로 진행할 수 있다.

- M1 안전봉합과 M2 DB·작업대기열 설계
- M2 계약 동결 후 모바일·Studio UI 뼈대
- M4 공통 발행묶음 안정 후 M5와 M6의 내부 개발
- 모든 단계에서 시험자료·관측성·운영도구 개발

다음은 병렬로 외부 활성화하면 안 된다.

- M1 완료 전 신규 모바일·PPTX 외부발행
- M4 패키지 계약 전 채널별 사실·재무계산 구현
- PPTX 최종파일 관측기 전 Studio 외부배포
- 승인 무효화 전 자동 재생성 외부발행

## 5. 전환 성공의 최종 판정

- 차단급 미실행·판정불가·시스템오류 외부발행 0건
- 동일 공통 발행묶음의 모바일·PPTX 핵심값 불일치 0건
- 핵심값·중개인 의견·사진의 역추적률 100%
- 구형 경로와 신규 경로의 중대한 허용 오류 차이 0건
- 당산동·상도동·양평동과 최소자료·다필지·사진변종 통과
- 중개실무 품질평가 평균 4/5 이상, 개별항목 3 미만 없음
- 기능깃발 되돌리기 훈련 성공, 데이터 손실 0건
- 신규 거래건의 모바일→PPTX 직접변환 사용 0건
