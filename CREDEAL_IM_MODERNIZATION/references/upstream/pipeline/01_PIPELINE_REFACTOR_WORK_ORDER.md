# IM 제작 파이프라인 개편 작업지시서

> 작업명: D58 기반 IM 제작 파이프라인 재구축  
> 우선순위: P0  
> 목표 릴리스: 기능깃발 병행운영 후 단계 전환  
> 소유: 제품책임자 1명, 기술책임자 1명  
> 승인: 부동산 도메인 책임자, 보안·개인정보 책임자, 품질책임자

## 1. 작업목표

현행의 장시간 단일 생성과 모바일 문서 기반 PPTX 변환을, 단계별 체크포인트·불변 산출물·독립 채널 분기를 가진 재개 가능한 파이프라인으로 바꾼다.

완료 후 사용자는 다음을 경험해야 한다.

- 입력을 제출하면 즉시 실행번호를 받고 단계별 진행상태와 보완요청을 볼 수 있다.
- 공공자료 일부가 늦거나 실패해도 이미 확보한 원자료와 성공단계는 보존된다.
- 모바일 L1/L1.5와 PPTX Studio를 필요한 순서와 시점에 각각 만들 수 있다.
- 사실이 바뀌지 않은 문안·사진·레이아웃 수정은 해당 채널만 빠르게 다시 만든다.
- 승인한 버전과 실제 배포한 파일이 같은지 추적할 수 있다.

## 2. 작업범위

### 포함

- 파이프라인 실행·단계실행·체크포인트·산출물 등록부
- 명령 수락, 멱등성, 작업 임대시간, 심장박동, 중단·재개
- 원자료 수집부터 공통 발행묶음까지 CORE 단계
- 모바일 L1/L1.5 독립 제작·검사·승인·발행
- PPTX Studio 독립 프로젝트·편집·미리보기·검사·승인·내보내기
- 변경영향 판정과 최소범위 재생성
- 이벤트 보관함, 운영관측, 오류분류, 보상작업
- 구형 API·저장·PPTX 렌더러의 호환 어댑터
- 단계적 데이터 이전, 병행검증, 기능깃발, 되돌리기

### 제외

- 전문가가 직접 작성하는 L3/L4 투자자문 업무흐름
- 자동 가치평가나 법률·세무 의견을 새로 제공하는 기능
- PPTX 웹 편집기의 상세 UI 시각설계
- 공공 API 공급자 자체 품질개선
- 구형 발행본의 일괄 재생성

## 4. 작업지시 상세

### W0. 현재 오류경로를 먼저 봉합한다

1. `writer`가 반환하는 주장목록, 산출항목판정, 발행검사 결과, 규칙버전을 직렬화한다.
2. `document_objects.body`에 임시 저장하더라도 전체 판정묶음의 해시와 참조를 남긴다.
3. 승인 API에서 새 빈 `ClaimRegistry`를 만드는 경로를 제거한다.
4. 승인 요청은 `expectedSnapshotHash`, `expectedGateHash`, `expectedContentHash`를 받아 현재값과 비교한다.
5. `publishBlocked`, 미실행 검사, 오래된 판정 중 하나라도 있으면 승인하지 않는다.
6. 기계검사 결과와 사람승인 상태를 다른 필드·다른 사건으로 보존한다.

### W1. 장시간 HTTP 작업을 재개 가능한 실행으로 바꾼다

1. `POST /generate-async`는 실행레코드와 최초 명령만 만든 뒤 `202 Accepted`를 반환한다.
2. `after()` 1회 실행을 유일한 완료수단으로 사용하지 않는다.
3. 각 단계는 작업대기열에서 독립 소비하며 임대시간·심장박동·재시도횟수를 가진다.
4. 성공한 단계의 출력은 불변 산출물로 등록하고 다음 단계는 산출물 ID와 해시만 받는다.
5. 동일 멱등키 명령은 새 실행을 만들지 않고 기존 결과를 반환한다.
6. 실행상태는 단계상태의 투영결과이며 운영자가 임의로 `completed`로 덮어쓰지 못한다.

### W2. CORE를 7개 결정단계로 고정한다

```text
P00 접수
P10 근거수집·정규화
P20 불일치·매각범위 조정
P30 유효기준본 생성
P40 산출항목 계산·판정
P50 문서등급 가능범위·기계검사
P60 공통 발행묶음 생성
```

각 단계는 `04_STAGE_CONTRACTS.md`의 입력·출력·차단조건을 따른다. 단계를 합쳐 구현해도 외부 계약과 체크포인트는 유지해야 한다.

### W3. 모바일 제작을 독립 자식실행으로 만든다

1. P60 성공 후 또는 사용자의 모바일 생성명령으로 M10을 시작한다.
2. 기본 목표는 L1, 조건을 충족하면 L1.5 후보를 제안한다.
3. 구조화 `ContentUnit`을 카드·표·사진묶음으로 조립한다.
4. 중개인 의견 원문·공개문구·근거·반영위치를 추적한다.
5. 모바일 기계검사, 중개인 승인, 외부발행을 분리한다.

### W4. PPTX Studio를 독립 자식실행으로 만든다

1. P60 패키지에서 Studio 프로젝트를 만든다.
2. 모바일 문서 존재 여부는 선행조건이 아니다.
3. 페이지구성, 문안, 사진계획, 레이아웃, 렌더파일을 각각 버전화한다.
4. 미리보기와 최종 내보내기는 같은 고정 프로젝트 버전에서 실행한다.
5. 지면검사와 최종파일 승인 전에는 배포 URL을 만들지 않는다.

### W5. 변경영향과 재생성을 자동화한다

1. 사실·근거·기준일 변경은 P20부터 또는 필요 시 P10부터 다시 실행한다.
2. 산식·판정규칙 변경은 P40부터 다시 실행한다.
3. 중개인 공개문구 변경은 영향을 받는 채널 조립부터 다시 실행한다.
4. 모바일 순서변경은 모바일만, PPTX 사진·레이아웃 변경은 PPTX만 다시 만든다.
5. 기존 발행본은 삭제하지 않고 `stale` 또는 `superseded`로 전환한다.

## 5. 구현제약

- 기존 사용자 데이터와 발행파일을 삭제하지 않는다.
- 전환기간 중 신규·구형 결과를 같은 실행번호에서 구분 가능하게 한다.
- 채널 렌더러에서 공공 API를 직접 호출하지 않는다.
- LLM 응답을 숫자 정본이나 발행허가 판정으로 사용하지 않는다.
- 외부 API 실패 시 캐시·과거값 사용 여부와 기준일을 명시한다.
- 이벤트 발행과 DB 반영은 트랜잭션 보관함 방식으로 결박한다.
- 동시 실행은 스냅샷·프로젝트 버전의 낙관적 잠금으로 충돌을 감지한다.

## 7. 병합 차단조건

- 스키마검사 없이 JSONB를 새 정본으로 저장함
- 산출물 해시나 규칙버전이 없음
- `not_evaluated`를 허가로 처리함
- 채널 코드가 원시 `enrichment` 또는 모바일 마크다운에서 사실을 재판정함
- 승인 API가 대상해시를 확인하지 않음
- 외부 API 재시도에 상한·시간제한·중복방지가 없음
- 실패한 단계가 성공단계의 산출물을 삭제함
- 신규경로 실패 시 구형경로 복구절차가 없음
