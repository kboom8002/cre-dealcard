## 1. v0.4가 작성 경험을 바꾸는 지점

### 1.1 첫 질문이 하나 늘어납니다

```
v0.3            [주소] ──▶ 자동수집 ──▶ 슬롯 채우기 ──▶ 발행

v0.4            [주소] ──▶ 자동수집 ──▶ [이 물건을 누구에게 파는가] ──▶ 슬롯 채우기 ──▶ 발행
                                              ↑
                                    investmentPosture 확정
                                    이후 모든 화면이 여기서 갈림
```

**`investmentPosture`를 뒤로 미룰 수 없습니다.** 관점이 정해지지 않으면 어떤 슬롯을 물어야 할지 결정할 수 없습니다. 개발형인데 렌트롤 18개 필드를 다 채우게 하면 그 시간이 전부 낭비입니다.

### 1.2 왜 이것이 개선인가

역설계 5건 중 잠원동은 v0.3에서 `income`으로 분류되었습니다. 실제 IM의 핵심은 **신축 제언**이었고, 임대차는 명도 대상일 뿐이었습니다. 수익형 화면으로 작성하면:

- 임대료 인상 여지를 묻는데 → 어차피 명도할 임차인
- Cap Rate를 계산하는데 → 매수자가 안 봄
- 신축 규모·사업수지를 물을 화면이 없음 → **IM의 핵심이 빠짐**

관점을 먼저 물으면 이 전부가 해결됩니다.

## 2. 1단계 — 3축 분류

### 2.1 화면 구성

```
┌─────────────────────────────────────────────┐
│ 서울 영등포구 양평동4가 117                    │
│                                             │
│ ✓ 업무시설          건축물대장에서 확인됨      │  ← buildingUse (자동·읽기전용)
│                                             │
│ 물건 유형                                    │
│ [사무용빌딩 ▾]      추천                     │  ← assetType (제안 + 변경 가능)
│                                             │
│ 어떤 매수자를 찾으시나요?                     │  ← investmentPosture (필수 선택)
│  ○ 임대수익  ○ 사옥  ○ 개발  ○ 운영  ○ 단기매매 │
└─────────────────────────────────────────────┘
```

### 2.2 축별 입력 방식

| 축 | 방식 | 근거 |
|---|---|---|
| `buildingUse` | **자동·읽기전용** | 건축물대장이 정본. 중개인이 고칠 대상이 아님 |
| `assetType` | **제안 + 변경 가능** | 용도로 대부분 추론되나 상가주택·복합은 사람만 앎 |
| `investmentPosture` | **필수 선택 · 제안 없음** | 매수자 목적은 시스템이 알 수 없음 |

**`investmentPosture`에 기본값을 두지 않습니다.** 기본값을 두면 대부분 그대로 두고 넘어가며, 그 순간 v0.3의 오분류가 재현됩니다. 5개 선택지를 한 화면에 놓고 반드시 고르게 합니다.

### 2.3 `assetType` 자동 제안

```ts
export function suggestAssetType(use: BuildingUse, b: BuildingFacts): Suggestion {
  // 1순위 — 층별 용도 혼합 검사 (상가주택·복합 판별)
  if (hasResidentialFloors(b) && hasCommercialFloors(b))
    return { value: 'mixed_shop_house', confidence: 'medium', reason: '층별 용도가 주거·근생 혼합' };

  // 2순위 — 세대수 기반 (다가구 판별)
  if (use === 'house_single' && (b.householdCount ?? 0) >= 3)
    return { value: 'multi_household', confidence: 'high', reason: `${b.householdCount}세대` };

  // 3순위 — 용도 직결
  return { value: PRIMARY_TYPE_OF[use], confidence: 'high', reason: `법정용도 ${label(use)}` };
}
```

`confidence: 'medium'` 이하는 **제안을 펼쳐 놓고 확인을 요구**합니다. 조용히 채워 넣지 않습니다.

### 2.4 조합 검증

`CATALOG_ASSET_TYPES.md` §4 매트릭스를 적용합니다.

| 결과 | 화면 동작 |
|---|---|
| ○ | 그대로 진행 |
| △ | 경고 배너 1줄. 닫으면 진행 |
| ✗ | 해당 선택지를 **비활성**하고 사유 표시 |

```
나대지는 임대수익형으로 선택할 수 없습니다 — 임대차가 없습니다.
개발형 또는 단기매매형을 선택하세요.
```

**차단은 물리적으로 불가능한 경우에만** 씁니다. 실무는 항상 예외를 만들고, 시스템이 중개인을 막으면 시스템을 안 씁니다.

### 2.5 관점 변경 — 늦을수록 비쌉니다

작성 도중 `investmentPosture`를 바꾸면 이미 채운 슬롯 중 일부가 무의미해집니다.

```ts
export function posturChangeImpact(from: Posture, to: Posture, filled: SlotState[]) {
  const dropped = filled.filter(s => !requiredBy(to).includes(s.key) && requiredBy(from).includes(s.key));
  return {
    droppedSlots: dropped,           // 값은 삭제하지 않고 보존
    newRequired: requiredBy(to).filter(k => !filled.some(s => s.key === k)),
    gradeDelta: recompute(to) - recompute(from),
  };
}
```

| 규칙 | 이유 |
|---|---|
| **입력값은 절대 삭제하지 않습니다** | 되돌릴 때 다시 채우게 하면 신뢰를 잃음 |
| 변경 전 영향 요약을 보여줍니다 | "렌트롤 12건이 IM에서 빠지고, 신축 규모 4항목이 새로 필요합니다" |
| 등급 변화를 함께 표시합니다 | 관점만 바꿔도 점수가 오르내리는 것을 이해시켜야 함 |

## 3. 2단계 — 슬롯 채우기

### 3.1 관점이 질문 목록을 결정합니다

| posture | 먼저 묻는 것 | 묻지 않는 것 |
|---|---|---|
| `income` | 렌트롤 · 취득비용 · 비교사례 | 신축 규모 · 명도 |
| `owner_occupied` | 입주 인원·필요 면적 · 현 임차료 | 임대료 인상 여지 |
| `development` | 용적률 상한 · 명도 조건 · 인허가 | 임차인 업종 · 관리비 |
| `operating` | 객실·ADR·OCC · 운영사 계약 | **렌트롤 전체** |
| `trading` | 비교사례 · 권역 거래량 | NOI · 임차인 상세 |

`operating`에서 렌트롤을 통째로 묻지 않는 것이 핵심입니다. 호텔 IM에 임차인 표는 존재하지 않습니다.

### 3.2 메모 파싱 — 입력의 주 경로

중개인은 폼을 채우지 않습니다. **말하듯 적습니다.** 역설계한 5건의 입력 데이터셋이 전부 자유 메모 형식이었던 이유입니다.

```ts
export interface MemoParseResult {
  extracted: Array<{
    slotKey: string;
    value: unknown;
    confidence: number;        // 0~1
    sourceSpan: [number, number];   // 메모 내 위치 — 하이라이트용
  }>;
  ambiguous: Array<{ span: [number, number]; question: string }>;
  unmatched: string[];
}
```

| 규칙 | 이유 |
|---|---|
| `confidence ≥ 0.85`만 자동 채움 | 낮은 확신으로 채우면 검수가 형식화됨 |
| 채운 값은 **메모의 해당 부분을 하이라이트** | 어디서 왔는지 보여야 고칠 수 있음 |
| provenance는 `broker`(0.60) | 메모는 공부가 아님 |
| `ambiguous`는 질문 1개로 환원 | "12m·6m·4m 중 주 진입로는?" |

**추출 실패는 실패가 아닙니다.** `unmatched` 문장은 IM의 `중개인 코멘트`로 그대로 실립니다. 버리지 않습니다.

### 3.3 우선순위 큐

`IM_DATA_PIPELINE.md` §3.5의 `GradeAdvice`를 화면에 적용합니다.

```
지금 채우면 좋은 것 3가지

  임대차계약서 6건 업로드          +3.75점  약 8분   → 현금흐름 분석 잠금해제
  등기부 확인                      +2.50점  약 3분
  인근 비교사례 3건                +3.00점  약 12분  → 가격 근거 슬라이드
```

**3개만 보여줍니다.** 전체 목록은 접어 둡니다. 호텔 사례(등급 4.58 D)처럼 20개가 비어 있을 때 전부 나열하면 중개인은 그 자리에서 포기합니다.

### 3.4 배열 슬롯의 부분 입력

수택동은 **필지별 면적 없이 합계만** 있었습니다. 양평동은 **층별 임대 내역 없이 총계만** 있었습니다. 실무 IM의 절반이 이렇습니다.

```ts
export type ArraySlotState =
  | { mode: 'total_only'; total: number }                    // 합계만 — 정상 상태
  | { mode: 'itemized'; items: Item[]; total: number }       // 항목별
  | { mode: 'partial'; items: Item[]; total: number; unaccounted: number };
```

| 규칙 | 이유 |
|---|---|
| `total_only`를 **결손으로 표시하지 않습니다** | 실무의 정상적인 상태 |
| 항목 합계 ≠ 총계면 **총계를 정본**으로 | IM 기재값이 근거 |
| 차이는 `unaccounted`로 노출 | 숨기면 나중에 오해가 됨 |
| 등급은 `itemized`에서만 만점 | 정밀도의 차이는 있음 |

## 4. 3단계 — 임대차

### 4.1 법령 분기 화면

`buildingUse`가 `ambiguous`거나 혼합 물건이면 **호실별로 지정**하게 합니다.

```
호실별 적용 법령                     자동 판정: 1층만 상가, 나머지 주택

  1층  근린생활       [상가 ▾]   갱신 10년 · 권리금 보호
  2층  주택           [주택 ▾]   갱신 4년 · 직접거주 거절 가능
  3층  주택           [주택 ▾]
```

| 규칙 | 이유 |
|---|---|
| 자동 판정은 **제안까지만** | 오피스텔 주거 사용은 대장으로 알 수 없음 |
| 미확정 시 **주택(보수적)** 적용 | 갱신 4년이 매수자에게 불리한 쪽 |
| 미확정은 IM에 **표기** (G15) | 확인 안 된 것을 확인된 것처럼 쓰지 않음 |
| 각 선택지에 **결과를 병기** | "주택 = 갱신 4년"을 모르면 고를 수 없음 |

### 4.2 갱신요구권 — 주택은 묻지 않으면 알 수 없습니다

**묵시적 갱신은 갱신요구권을 소진시키지 않습니다.** 4년을 넘겨 거주 중이어도 권리가 그대로 남아 있을 수 있습니다.

```
이 임차인이 계약갱신요구권을 행사한 적이 있나요?

  ○ 있음      갱신권 소진 — 계약 만료 시 갱신 거절 가능
  ○ 없음      갱신 요구 시 2년 연장 (묵시적 갱신은 권리 소진 아님)
  ○ 모름      IM에 '확인 필요'로 표기됩니다
```

**"모름"을 선택지로 둡니다.** 두지 않으면 중개인이 추측으로 고르고, 그 추측이 IM에 사실처럼 실립니다. 경과년수로 자동 추정하면 **매수자에게 유리한 쪽으로** 틀립니다.

### 4.3 표준 ↔ 정밀 전환

`IM_DATA_PIPELINE.md` §4.4의 제안 로직을 3축으로 갱신합니다.

```ts
export function suggestPreciseMode(deal: DealFacts): PreciseSuggestion | null {
  if (deal.posture === 'operating') return null;                      // 렌트롤 자체가 없음
  if (deal.posture === 'development' && deal.vacatePlanned) return null; // 어차피 명도
  if (deal.leaseUnits.length < 4) return null;                        // 표준으로 충분

  return {
    gradeGain: estimateGain(deal),
    effortMinutes: deal.leaseUnits.length * 2,
    unlocks: ['호실별 분석', '갱신 시점 타임라인', '임대료 갭 분석'],
  };
}
```

**제안하되 강제하지 않습니다.** 표준 모드로도 IM은 나오고, 등급이 낮을 뿐입니다.

## 5. 4단계 — 편성

### 5.1 관점별 IM 서사

레이아웃 규칙(L16~L24)이 슬라이드를 **선택**한다면, 서사는 그 **순서와 강조**를 결정합니다.

| posture | IM이 답하는 순서 |
|---|---|
| `income` | ① 지금 얼마 버는가 → ② 안정적인가 → ③ 더 벌 수 있는가 → ④ 가격이 적정한가 |
| `owner_occupied` | ① 우리가 들어갈 수 있는가 → ② 지금 임차료보다 유리한가 → ③ 자산가치는 |
| `development` | ① 얼마나 지을 수 있는가 → ② 언제 착공하는가 → ③ 사업수지 → ④ 토지비 부담 |
| `operating` | ① 영업 성과 → ② 지속 가능한가 → ③ 운영사 → ④ 리스크 |
| `trading` | ① 권역 시세 대비 → ② 거래 회전율 → ③ 되팔 수 있는가 |

### 5.2 `income` 안의 분기 — 아키타입

같은 수익형이라도 IM이 정반대일 수 있습니다.

| 아키타입 | IM 중심 | 실증 |
|---|---|---|
| `R-INC-01` 초안정형 | 임대 안정성 · 임차인 분산 · 공실 해소 | 양평동 (용적률 여유 1.2%p · 신축 8년) |
| `R-INC-02` 임대료 정상화형 | 임대료 갭 · 인상 경로 | 당산동 |
| `R-INC-03` 공실 해소형 | 공실 원인 · 유치 전략 | — |
| `R-INC-04` 리모델링형 | 투입 대비 수익 개선 | — |

```ts
export function suggestArchetype(d: DealFacts): ArchetypeSuggestion {
  if (d.farHeadroom < 5 && d.buildingAge < 10 && d.rentCapRatio > 0.9)
    return { code: 'R-INC-01', reason: '증축 여지 없음 ∧ 신축 ∧ 인상 상한 적용 → 밸류애드 여지 없음' };
  if (d.marketRentGap > 0.15)
    return { code: 'R-INC-02', reason: `시세 대비 ${pct(d.marketRentGap)} 저렴` };
  if (d.vacancyRate > 0.15)
    return { code: 'R-INC-03', reason: `공실률 ${pct(d.vacancyRate)}` };
  if (d.buildingAge > 20) return { code: 'R-INC-04', reason: `건물연령 ${d.buildingAge}년` };
  return { code: 'R-INC-01', reason: '기본값', confidence: 'low' };
}
```

**제안 + 중개인 확정**입니다. 근거 문장을 함께 보여주어 판단할 수 있게 합니다.

### 5.3 밸류애드 여지가 없다는 것도 서사입니다

양평동은 증축 불가·리모델링 불필요·인상 5% 상한·갱신권 2~7년 잔여로 **개선할 것이 없는 물건**이었습니다. 이것을 약점으로 쓰면 안 됩니다.

```
❌  용적률 여유가 1.2%p뿐이라 증축이 불가능합니다.
✓   2018년 준공, 용적률 398.8%로 상한에 근접 — 추가 투입 없이 현 수익이 유지됩니다.
```

같은 사실입니다. `R-INC-01`에서는 **손댈 것이 없음 = 예측 가능성**입니다. NLG 마스크가 아키타입별로 분기해야 하는 이유입니다.

## 6. 실무 관행 대응

역설계 5건에서 반복 확인된 것들입니다. 이것을 모르면 IM 숫자가 실무와 어긋납니다.

### 6.1 용적률은 지상 연면적 기준

**서로 다른 세 중개법인이 독립적으로 같은 관행을 씁니다.**

| 물건 | 전체 연면적 기준 | 지상층 기준 | IM 기재값 |
|---|---:|---:|---|
| 잠원동 | — | **247.0%** | 247.0% |
| 당산동 | — | **221.8%** | 221.8% |
| 양평동 | 480.2% | **398.8%** | 398.8% |

```
용적률   398.8%   ⓘ 지상 연면적 기준
         480.2%     전체 연면적 기준 (지하 포함)
```

**둘 다 보여주고 어느 쪽인지 명시**합니다. 하나만 쓰면 반드시 오해가 생깁니다.

### 6.2 티저 수준 입력 — 차단하되 길을 알려줍니다

호텔 사례는 4개 항목(물건명·입지·객실 수·매각가)뿐이었고 등급 **4.58점 D**였습니다.

```
아직 IM을 만들 수 없습니다 — 자료등급 D

매수자가 판단할 수 있는 정보가 부족합니다.
아래 3가지를 채우면 B등급에 도달합니다.

  객실 구성      4항목    약 5분
  운영 지표      3항목    약 3분   ADR · 가동률 · GOP 마진
  물건 제원      6항목    약 8분
```

**"부족합니다"로 끝내면 안 됩니다.** 무엇을 얼마나 채우면 되는지가 없으면 중개인은 시스템을 탓하고 떠납니다.

### 6.3 공동담보 중복 합산

당산동에서 층별 구분등기 물건의 공동담보를 단순 합산해 **실제의 두 배(32억 vs 16억)** 가 나왔습니다.

```
근저당 입력

  호실       채권최고액      공동담보 그룹
  201호      16억           [A ▾]
  301호      16억           [A ▾]     ← 같은 그룹 = 1회만 합산
                            ─────
                            합계 16억  (중복 제외됨)
```

그룹을 지정하지 않으면 각각 합산됩니다. **지정 UI가 없으면 이 오류는 반드시 재발합니다** (C32).

### 6.4 위반건축물

다가구·상가주택에서 흔하고, **등재 시 매수자 대출이 막힙니다.**

| 상태 | 동작 |
|---|---|
| 미확인 | 대출 시나리오 **억제** (C29·G16) |
| 없음 | 정상 |
| 있음 | IM에 고지 + 대출 제약 경고 |

## 7. 작성 보조 — 하는 것과 안 하는 것

| 하는 것 | 안 하는 것 |
|---|---|
| 메모에서 슬롯 추출 (확신 0.85 이상) | 없는 값 생성 |
| 아키타입 제안 + 근거 제시 | 아키타입 자동 확정 |
| 문장 다듬기 (사실 불변) | 사실 추가·강화 |
| 누락 항목 우선순위 제시 | 누락을 가정으로 메움 |
| 조합 위반 경고 | 중개인 판단 대체 |

```ts
// NLG 호출 시 강제되는 계약
export interface NLGRequest {
  facts: ReadonlyArray<Fact>;      // 이 밖의 사실을 쓰면 위반
  mask: MaskCode;                  // M01~M29
  archetype: ArchetypeCode;
  forbidden: ['추정', '예상', '전망'];  // 시나리오 마스크 외에서 금지
}
```

생성 문장은 **`facts`에 없는 고유명사·수치를 포함할 수 없습니다.** 사후 검사로 강제하며, 위반 시 마스크 기본 문장으로 대체합니다.

## 8. 미리보기와 발행

### 8.1 미리보기는 작성 중 항상 보입니다

```
┌──────────────────┬─────────────────┐
│  입력 (좌)        │  IM 미리보기 (우) │
│                  │                 │
│  방금 입력한 값이  │  해당 슬라이드가  │
│  반영되는 위치를   │  하이라이트됨     │
│  즉시 보여줌      │                 │
└──────────────────┴─────────────────┘
```

**채우면 무엇이 좋아지는지를 점수가 아니라 결과물로 보여줍니다.** "+3.75점"보다 "이 표가 채워집니다"가 강합니다.

### 8.2 발행 전 게이트 표시

G1~G16 중 실패 항목만 보여줍니다.

```
발행할 수 없습니다 — 2건

  G10   3층 임대수익률에 기준이 없습니다        [기준 선택]
  G16   위반건축물 확인이 필요합니다             [확인하기]

경고 1건 — 발행은 가능합니다
  G15   2·3층 적용 법령이 미확정입니다 (주택으로 표기됩니다)
```

각 항목에 **바로 고칠 수 있는 링크**를 답니다. 목록만 주면 중개인이 해당 화면을 찾아 헤맵니다.

### 8.3 복수 관점 IM

같은 물건을 **개발형과 수익형 두 벌로** 만드는 일이 실무에서 일어납니다. 잠원동이 그런 물건이었습니다.

```
deal (물건 1개)
 ├── im_variant  posture=development   "신축 부지 제안"    v1.2  발행됨
 └── im_variant  posture=income        "임대수익 물건"     v1.0  작성중
```

| 규칙 | 이유 |
|---|---|
| 슬롯 값은 **딜 수준에서 공유** | 두 번 입력하게 하면 안 씀 |
| 편성·서사·등급은 **variant별** | 관점이 다르면 결과가 다름 |
| 발행 이력·추적은 **variant별** | 어느 쪽이 반응이 좋았는지가 신호 |
| 검수 서명은 **딜 수준** | 사실 확인은 한 번이면 충분 |
