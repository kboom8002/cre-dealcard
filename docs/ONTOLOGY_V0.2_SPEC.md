## 1. provenance 5-tier

### 1.1 등급 재정의

| 배지 | 코드 | 정의 | 점수 | 책임 |
|---|---|---|---:|---|
| ✓ 공부확인 | `public` | 건축물대장·등기부·토지이음·공시지가 등 공적 자료 | 1.00 | 발급기관 |
| ★ 전문가검증 | `expert` | 감정평가사·세무사·건축사 검토 | 0.95 | 해당 자격사 |
| **▲ 매도인고지** | **`seller`** | **매도인이 진술한 값. 공부로 확인 불가** | **0.65** | **매도인** |
| ● 중개인입력 | `broker` | 담당 중개인 직접 입력·검수 | 0.60 | 중개인 |
| ◇ AI추정·가정 | `assumed` | 명시된 가정에 따른 시스템 계산 | 0.30 | 없음 (가정) |

**`seller` 신설이 이번 개정에서 가장 실무적인 변경입니다.**

v0.1에서는 "실 대출잔액 약 80억"을 `broker`로 표기했으나, 이는 중개인이 확인한 값이 아니라 **매도인이 말한 값**입니다. 책임 소재가 다르고, 매수자가 실사에서 다르게 확인했을 때 중개인이 책임을 지게 됩니다.

`seller`로 분리되는 대표 항목 — 실 대출잔액 · 임차인 연체 이력 · 관리비 실비 내역 · 설비 교체 이력 · 매각 희망가.

### 1.2 파생값 합성 규칙 — 신설

v0.1에는 NOI·Cap Rate 같은 **계산값의 출처 표기 규칙이 없었습니다.** 샘플에서 NOI 4.594억에 배지가 없는 이유가 이것입니다.

세 가지 규칙으로 처리합니다.

```ts
// packages/ontology/src/provenance.ts
export type CompositionKind = 'additive' | 'ratio' | 'scenario';

/** A. 가감산 — 기여 절대값 가중 평균 */
export function composeAdditive(
  inputs: Array<{ value: number; score: number }>,
): number {
  const total = inputs.reduce((s, i) => s + Math.abs(i.value), 0);
  if (total === 0) return 0;
  return inputs.reduce((s, i) => s + (Math.abs(i.value) / total) * i.score, 0);
}

/** B. 비율 — 분자·분모 중 낮은 쪽 */
export function composeRatio(numerator: number, denominator: number): number {
  return Math.min(numerator, denominator);
}

/** C. 시나리오 — 미래 예측은 입력이 아무리 정확해도 가정이다 */
export const SCENARIO_SCORE = 0.30;   // 항상 ◇
```

**적용 예 — NOI**

| 입력 | 값 | provenance | 점수 | 기여 |
|---|---:|---|---:|---:|
| GPI | 6.014 | ● 중개인 | 0.60 | 80.9% |
| 재산세·종부세 | −0.620 | ★ 전문가 | 0.95 | 8.3% |
| 기타 운영경비 | −0.800 | ◇ 가정 | 0.30 | 10.8% |
| **NOI** | **4.594** | **● 중개인** | **0.597** | — |

**적용 예 — Cap Rate**

`composeRatio(NOI 0.597, 매각희망가 0.65)` = **0.597** → ● 중개인입력

**적용 예 — 총수익률 · NPV · IRR**

`scenario` → **항상 ◇ AI추정·가정**. 입력이 전부 공부여도 미래 지가는 가정입니다. 이 규칙에 예외를 두지 않습니다.

### 1.3 최약 고리 표시

합성 점수만으로는 어디가 약한지 알 수 없습니다. **가장 낮은 점수의 입력을 각주로 병기**합니다.

```
NOI 4.594억 ● 중개인입력
  └ 최약 고리: 기타 운영경비 ◇ 가정 (권역 평균 기준)
```

이 표기가 매수자의 질문을 유도하고, 실사 우선순위를 알려줍니다.

## 5. 규칙군 재편

### 5.1 문제 — R10은 아키타입이 아니었다

v0.1의 R01~R10은 **물건 유형 판정** 규칙군인데, R10에 "전 임차인 대항력 없음"이 들어가 있었습니다. 이는 임대차 법적 지위이지 물건 유형이 아닙니다.

게다가 판정 자체가 부정확했습니다 — 대항력은 건물 인도 + 사업자등록으로 발생하며 환산보증금과 무관하므로, 영업 중인 임차인은 사실상 전부 갖습니다.

### 5.2 재편

| 규칙군 | 소유 질문 | 코드 |
|---|---|---|
| **R** (Archetype) | 이 물건은 어떤 유형인가 | R01~R09 (R10 폐기) |
| **T** (Tenancy) | 임대차의 법적 지위는 어떠한가 | **T01~T06 신설** |
| **P** (Parcel) | 토지의 유효 규모는 얼마인가 | **P01~P03 신설** |

> 레이아웃 규칙 `L01~L15`(`AGENTS.md`)와 코드 충돌을 피하려고 토지 규칙군을 `P`로 두었습니다.

### 5.3 T 규칙군 (신설)

| 코드 | 판정 | 근거 |
|---|---|---|
| T01 | 환산보증금 = 보증금 + 월세×100, 지역 기준과 대조 | 상임법 제2조·시행령 |
| T02 | **대항력** — 인도 + 사업자등록 시 성립. **기본값 `true`** | 제3조 |
| T03 | 계약갱신요구권 — 최초 계약일부터 10년, 잔여 산출 | 제10조 |
| T04 | 우선변제권 — 환산보증금 이하 + 확정일자 | 제5조 |
| T05 | 차임 인상률 5% 상한 — 환산보증금 이하만 | 제11조 |
| T06 | 권리금 회수기회 보호 — 환산보증금 무관 적용 | 제10조의3~7 |

```ts
// packages/ontology/src/rules/tenancy.ts
export const T02: TenancyRule = {
  id: 'T02',
  name: '대항력',
  evaluate(unit) {
    // 반증이 없으면 true. false로 표기하려면 근거를 요구한다.
    if (unit.opposingPowerOverride === false && !unit.opposingPowerEvidence) {
      throw new OntologyViolation('T02',
        '대항력 부정 표기에는 근거가 필요합니다 (사업자등록 미신청 등).');
    }
    return unit.opposingPowerOverride ?? true;
  },
};
```

**T02의 기본값을 `true`로 둔 것이 핵심 설계 결정입니다.** 매수자에게 불리한 사실을 기본값으로 두어, 중개인이 유리하게 표기하려면 근거를 대게 만듭니다.

### 5.4 P 규칙군 (신설)

| 코드 | 산출 |
|---|---|
| P01 | 유효 대지면적 = Σ(필지 면적 × 지분) − Σ(제척 면적 where affectsFAR) |
| P02 | 유효 용적률 = 용적률 산정 연면적 ÷ 유효 대지면적 |
| P03 | 제척 영향도 = 제척 면적 ÷ 대장 대지면적 합계 |

### 5.5 R 규칙군 재판정 주의

아키타입 판정에 쓰이는 용적률은 **P02의 유효 용적률**로 바뀝니다.

```
v0.1  R02 VALUE_ADD ← 건물연령 ≥20년 ∧ (조례상한 − 대장기준 용적률) ≥ 50%p
v0.2  R02 VALUE_ADD ← 건물연령 ≥20년 ∧ (조례상한 − 유효 용적률) ≥ 50%p
```

제척이 있는 다필지 물건에서는 **판정이 뒤집힐 수 있습니다.** 마이그레이션 시 전 딜을 재판정하고, 결과가 바뀐 딜은 목록으로 보고합니다.

역삼동 샘플처럼 제척 0인 단일 필지에서는 결과가 동일합니다 (여유 113.9%p 유지).

| M23 | "{metric}은 {source} 기준이며, 가장 신뢰도가 낮은 입력은 {weakest}입니다." |
| M24 | "본 수치는 미래 시나리오 가정에 기반하며 확정 값이 아닙니다." |

M24는 `scenario` 합성이 적용된 모든 지표에 **자동 부착**됩니다.

## 7. 마이그레이션

### 7.1 절차

```
1. v0.1 스냅샷 백업 (되돌림 지점)
2. 슬롯 배열화 — 스칼라를 단일 원소 배열로 승격
3. provenance 재분류 — broker 중 매도인 진술분을 seller로 이동
4. 파생값에 합성 provenance 부여 (C21 충족)
5. Cap Rate에 basis='noi_price' 주입 (C16 충족)
6. R10 → deprecated 처리, T 규칙군으로 재판정
7. R 규칙군 유효 용적률 기준 재판정
8. 전 딜 등급 재산정
9. 변경 영향 보고서 생성
10. 검증 통과 후 커밋 / 실패 시 1로 롤백
```

### 7.2 3번 — provenance 재분류 대상

자동으로 판정할 수 없으므로 **후보 목록을 만들어 중개인 확인**을 받습니다.

| 슬롯 | v0.1 | v0.2 |
|---|---|---|
| 실 대출잔액 | ● broker | ▲ seller |
| 임차인 연체 이력 | ● broker | ▲ seller |
| 관리비 실비 내역 | ● broker | ▲ seller |
| 설비 교체 이력 | ● broker | ▲ seller |
| 매각 희망가 | ● broker | ▲ seller |
| 임대차 조건 | ● broker | ● broker (계약서 확인분) |

### 7.3 되돌림 가능성

**모든 단계는 역방향 스크립트를 함께 작성합니다.** 배열 → 스칼라 강등은 원소가 1개일 때만 가능하므로, 다필지 딜이 생성된 이후에는 롤백이 불가능해집니다.

> 롤백 가능 기간은 **마이그레이션 후 첫 다필지 딜 생성 전까지**입니다. 이 사실을 배포 계획에 명시하고, 그 전에 검증을 끝냅니다.

### 7.4 발행 이력 보호

이미 발행된 IM은 **v0.1 엔진으로 계속 재현 가능해야 합니다.**

```ts
export interface PublishRecord {
  ontologyVersion: string;     // 'v0.1.0' — 발행 시점 Pin
  engineVersion: string;
  snapshot: IMDoc;             // 발행 시점 IR 전문
}
```

온톨로지 v0.1 엔진을 삭제하지 않고 `packages/ontology/legacy/v0.1`에 보존합니다. 발행 이력 조회 시 Pin된 버전으로 렌더합니다.
