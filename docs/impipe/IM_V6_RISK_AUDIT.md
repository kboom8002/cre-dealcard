## 2. 🔴 R2 — 타임아웃 안에 완주할 수 없습니다

`02 §2.1` `StageTimer(90, 105, 120)` — Soft 90s / Hard 105s / **Kill 120s**
`02 §5.1` income은 **5-Stage 순차**입니다.

| Stage | 섹션 |
|:-:|---|
| 1 (병렬) | property_overview · decision_snapshot · location_access · next_steps |
| 2 | lease_status · income_analysis |
| 3 | market_rent_gap · value_add_plan · stabilized_scenario |
| 4 | risk_check |
| 5 | investment_thesis |

스테이지 내부를 전부 병렬로 잡고, 섹션당 LLM 호출을 **최소 30초**로 잡아도:

```
5 스테이지 × 30초 = 150초  >  Kill 120초
```

섹션당 60초면 300초, 90초면 450초입니다.
**최선의 경우에도 Kill을 넘습니다.**

### 무엇이 실제로 일어나는가

`02 §2.2` — 「타임아웃 도달 시 미완성 섹션 → `checklist` 안전 이관」

income의 **Stage 5는 `investment_thesis`(투자 논거)** 입니다.
그리고 `02 §6` 필수 섹션은 `property_overview` · `lease_status` ·
`income_analysis` · `checklist` — **투자 논거는 필수가 아닙니다.**

🔴 **투자 논거가 구조적으로 상시 누락되고, 필수가 아니라서 차단도 되지 않습니다.**
   조용히 체크리스트로 이관되어 「자료 현황」 항목으로 바뀝니다.
   `risk_check`(Stage 4)도 같은 위험에 있습니다.

이것은 V4 표본에서 관찰된 **반복 문단**의 또 다른 발생 경로일 수 있습니다 —
잘린 섹션 자리를 일반 문구가 메웁니다.

### 개선

```
P0-D   income Stage 를 5 → 3 으로 통합
       Stage 3(rentGap·valueAdd·stabilized)은 서로 독립이므로 Stage 2 와 병렬 가능
P0-E   Kill 을 실측 기반으로 재설정. 섹션당 p95 지연을 계측한 뒤 정합니다
P0-F   risk_check · investment_thesis 를 income 필수 섹션에 추가
       — 미완이면 이관이 아니라 차단
P0-G   타임아웃 이관이 발생하면 산출물에 표시. 지금은 조용합니다
```

세 곳의 집계가 전부 다릅니다.

| 출처 | block | warn | 합 |
|---|---:|---:|---:|
| `01 §8.1` 표기 | 38 | 11 | **49** |
| `01 §8.1` 범위(`G01~G45, G48~G52`)를 전개하면 | **50** | — | — |
| `02 §7.1·7.2` 실제 열거를 세면 | **37** | **14** | **50** |

그리고 **`G50`(기준일 전수 표시)이 `02 §7.1` block 목록(`G48~G52`)과

🔴 **실행 시 어느 쪽인지 결정할 수 없습니다.** block이면 발행이 멈추고
   warn이면 통과합니다. `G34`(요소 겹침)는 V4 표본에서 **17건** 나왔던 항목입니다.

부수: `01 §8.2`가 `G46`·`G47`을 건너뛰고 `G48`부터 시작합니다.
D35에서 `G46`(업종·상호 추론) · `G47`(면적 분리)을 부여했으므로 **충돌은 없지만
조율되지 않았습니다.** 레지스트리를 한 곳에서 읽어야 합니다.

### 개선

```
P0-H   게이트 심각도를 im.errors.yaml 단일 출처에서만 정의
       문서는 표를 만들지 말고 생성해 넣습니다
P0-I   G50 을 warn 으로 확정 (기준일 누락은 결손 표시로 충분)
P0-J   G34 심각도 결정 — 권고: block. 겹침은 읽을 수 없게 만듭니다
```

```

V6 규칙에서 NOI 15% 미만이므로 무통과
```

그리고 Cap Rate 0.5%p는 2.41%짜리 자산에서 **상대오차 21%**입니다.

### 개선

```

       전 섹션이 참조합니다 — 비교할 두 값이 애초에 생기지 않습니다
```

## 5. 🟠 R5 — `expert_required`가 도달 불가능하고 뜻이 뒤집혔습니다

`01 §5.2`:

| Tier | 최소 등급 | 재무 허용 |
|---|:-:|:-:|
| `internal_only` | **D** | ❌ |
| `fact_om` | C | ❌ |
| `analysis_im` | B | ✅ 기본 |
| `decision_im` | A | ✅ 전체 |
| `expert_required` | **A+** | ✅ 전체 |

두 가지가 틀렸습니다.

1. **「A+」는 존재하지 않는 등급입니다.** 등급은 A/B/C/D뿐입니다(`01 §4.2`).
   `expert_required`는 **어떤 물건도 도달할 수 없습니다.**

2. **뜻이 뒤집혔습니다.** 07 §1.1에서 `EX`(Expert Required)는
   「전문가 판단 없이는 핵심결론 **불가** · 외부 사용 **제한**」입니다.
   V6는 이것을 `decision_im`보다 위의 최상위 티어로 만들었습니다.
   전문가가 필요하다는 것은 **결론을 낼 수 없다**는 뜻이지 더 좋은 등급이 아닙니다.

3. `internal_only`는 최소 등급 D인데 `03 §2.3`이 D를 `G30`으로 throw합니다.
   → **`internal_only`는 PPTX로 절대 렌더되지 않습니다.** 5종 중 실렌더 4종입니다.

### 개선

```
P1-A   expert_required 를 등급 축에서 빼고 **직교 플래그**로 (07 §1.1)
       재무 허용 ❌ · 외부 배포 제한 · 자료 목록만 산출
P1-B   internal_only 를 D등급 전용 산출물로 정의하거나 티어에서 제거
```

## 6. 🟠 R6 — 안전 영역이 콘텐츠 영역보다 넓습니다

`03 §7.1` · `§8.3`:

```
W  13.333in   H 7.5in   M 0.62in
CW = W − 2M = 12.093in                    ← 콘텐츠 폭
Safe = 12.713 × 6.75in                    ← assertBounds 한계
```

```
12.713 = 13.333 − 0.62      ← 🔴 마진을 한쪽만 뺐습니다
6.75   = 7.5 − 0.75         ← 🔴 마진 0.62 와 맞지 않습니다
```

**`assertBounds`가 `CW`보다 0.62in 넓은 영역을 허용합니다.**
우측 마진이 사라진 배치가 통과합니다. 세로도 0.62가 아니라 0.75 기준입니다.

부수 — `03 §7.2`의 `fitBox(text, box)`는 **텍스트 맞춤**입니다.
D31에서 만든 `fit_box`는 **사진 비율 보존**용이었습니다. 같은 이름, 다른 일입니다.
그리고 **사진 배치 함수가 §7.2 목록에 없습니다.** `G36`(종횡비 왜곡) 검사는
있는데 **왜곡을 만들지 않는 배치 함수가 없습니다.** 검사만 있고 예방이 없습니다.

### 개선

```
P1-C   Safe = (W − 2M) × (H − 2M) = 12.093 × 6.26 으로 정정
P1-D   사진 배치 전용 fitPicture(img, box, minDpi) 신설 — 비율 유지 contain
       fitBox(text) 와 이름을 분리
```

## 9. 🟠 R9 — `G41`에 임계값이 있습니다

`03 §10`:

```
vacancy_narrative   서술어↔수치 모순 (G41)   임계값: 만실 + 공실 > 5%
```

🔴 **「만실」은 공실 0%를 뜻합니다.** 공실 4%인 물건에 「만실」이라고 쓰면
   이 규칙은 **통과**시킵니다.

V4 표본은 공실 17%에 「만실」이었으므로 5% 규칙에도 걸립니다. 그러나
경계에 있는 물건(공실 3~5%)은 그대로 나갑니다. 그리고 4%라도 거짓입니다.

### 개선


## 11. 🟡 R11 — 기준값이 두 개입니다

`02 §2.1`에 두 메커니즘이 나란히 있습니다.

```
Stage 3  수치 앵커        new NumericalAnchors(...)      전 섹션 수치 불변성
Stage 4  결정론적 계산    FinancialCalculator.calculate() 1회 실행, Claim 등록
```

앵커는 **LLM에게 숫자를 프롬프트로 고정**시키는 방식이고,
Claim/Calculation은 **값을 계산해 참조**시키는 방식입니다.

07 §19 Phase 0-2와 D37 P0-2는 **「LLM Numerical Anchor 제거」** 였습니다.
V6는 둘을 병존시켰고, `03 §10`은 `cap_rate`를 **앵커와** 비교합니다.
→ **앵커가 여전히 기준값 역할을 합니다.**

```
P2-C   NumericalAnchors 를 제거하거나, 앵커를 Calculation 에서 파생시켜
       단일 진실로 만듭니다. 두 개를 두면 반드시 갈립니다
```

## 15. 하지 말 것

- **모바일 IM만 보고 「D37 완료」로 판정하지 마십시오.** `01 §6`은
  「D37 P0+P1+P2 전량 완료」라고 적었는데 `§10.1` 매트릭스가 PPTX 열을
  비워 두고 있습니다. **완료 판정과 연결 매트릭스가 서로를 반박합니다.**
- **게이트를 더 만들지 마십시오.** 이미 50종이고 그중 6종의 심각도가 미정입니다.
- **허용오차를 「현실적 조정」으로 정당화하지 마십시오.** `CF3`에서 한 번
  폐기한 규칙입니다. 파생값을 한 번만 계산하면 비교할 두 값이 생기지 않습니다.
- **Kill 타임아웃을 늘려서 R2를 해결하지 마십시오.** Stage 수가 줄어야 합니다.
  120 → 300으로 늘리면 사용자가 5분을 기다립니다.
- **부록을 「한도 제외」로 두지 마십시오.** 상한 없는 예산은 예산이 아닙니다.
