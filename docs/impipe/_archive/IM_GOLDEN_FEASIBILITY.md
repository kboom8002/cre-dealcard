## 1. 왜 필요한가

### 1.1 이 시스템의 반복 실패 패턴

V3부터 V6까지 같은 일이 네 번 있었습니다.

```
검사기를 통과한 산출물에서 결함이 나옴 → 검사기를 추가함 → 다음 판에서 다른 결함
```

검사기는 **찾으라고 시킨 것만** 찾습니다. 종횡비 왜곡 60%가 세 판을 통과한 것은
크로핑만 봤기 때문입니다.

**골든은 음성이 아니라 양성 기준입니다.** "무엇이 틀렸는가"가 아니라
**"무엇이 옳은가"**를 파일 하나로 고정합니다.

### 1.2 이 시스템에서 특별히 필요한 이유

문서가 수렴하지 않습니다.

| 항목 | 문서 간 값 |
|---|---|
| income 아키타입 개수 | **4종 / 5종 / 9종** |
| 본문 면수 상한 | **16 / 20 / 「자르지 않음」** |
| 불변조건 개수 | **21 / 23 / 26** |
| `ProvenanceKind` | **8종(09) / 10종(08)** — 이름이 하나도 안 겹칩니다 |
| 대조군 주의 건수 | **7 / 19** (04 vs 실측) |

여섯 판의 개정으로도 좁혀지지 않았습니다.
**산출물은 하나의 값만 가집니다.** 골든 파일이 이 논쟁을 끝냅니다.

### 1.3 지금 동결하면 안 되는 이유

`04 §7` 수용 기준 —

```
□ target_yangpyeong.pptx → runApprovalGate(registry, 'decision_im')
  → passed=true · blockers=[]
```

D39에서 확인한 것 — `ClaimStatus`가 4종이고 `conflicted`가 없어
`findConflicted()`는 언제나 빈 배열이고 **`G48`(block)은 무조건 통과**합니다.

> 🔴 이 기준으로 검수하면 **`G48` 통과가 아무것도 증명하지 않습니다.**
>   그리고 그 상태가 「사람이 검수하여 정답이라고 확인한 산출물」로 동결됩니다.

| 미해결 | 동결 시 |
|---|---|
| `Claim.id` 없음 (D39 R14) | 「모든 수치가 Claim으로 역추적」을 확인할 수 없는데 확인했다고 기록 |
| im-core → PPTX 1/9 (D38 R1) | `04 §3.3` Step 3 「Claim 검증」을 **실행 불가** |
| 대조군 주의 7 vs 19 (§3.1) | 겹침 12건이 남은 채 「주의 0」으로 동결 |

### 3.1 🔴 `ProvenanceKind`가 08과 하나도 겹치지 않습니다

```
08 §2.5 (구현 · 10종)  registry · public_api · public_api_identified · ledger ·
                       seller · broker · broker_opinion · derived · assumed · not_available
09 §9   (요구 · 8종)   public_data · broker_input · field_verified · llm_generated ·
```

09를 따라 채우면 `DISPLAY_LABEL_MAP` 조회가 **전량 실패**합니다.
그리고 `llm_generated`·`llm_calculated`는 07 §2.4 원칙에 어긋납니다 —
「AI 생성 표시는 내부 이력에 남기되 **외부에서는 근거유형을 표시**한다」.

### 3.2 🔴 「모든 플래그를 true로」가 골든의 정의를 뒤집습니다

**골든은 「최대 면수」가 아니라 「그 자료 상태에서 옳은 산출물」입니다.**
플래그를 억지로 true로 하면 없는 데이터를 있다고 표시하게 되고 빈 면·폴백이 생깁니다
(D33 BL-F · 07 §16.3 금지). 그리고 **필동의 목적이 「결손 처리 기준선」**인데
플래그를 채우면 목적이 사라집니다. `§1.4` 표는 실제로 ❌를 두었으므로 **본문과 표가 모순**입니다.

### 3.3 🔴 표본 정의가 실물과 다릅니다

## 4. 방법 ① — 참조 산출물을 만들고 시스템이 반영하게 하는 법

### 4.1 문제

참조본은 다른 엔진(python-pptx)이 만들었습니다. 바이트도 색도 글꼴도 다릅니다.
**파일을 비교하면 영원히 다르고, 그래서 회귀 기준선이 될 수 없습니다.**

### 4.2 해법 — 파일이 아니라 **구조 지문**을 계약으로

```
참조본.pptx  ──fingerprint.py──▶  구조 지문(JSON)
                                      │
                                      ├─ emit-spec ─▶ acceptance_*.yaml  ← 렌더러의 계약
                                      │
렌더러 산출물.pptx ──diff_ref.py──────┘ ─▶ 결손 목록 (차단/주의)
```

지문이 보는 것과 **보지 않는 것**을 분명히 나눴습니다.

| 본다 | 보지 않는다 |
|---|---|
| 면 개수 · 면 순서 · 면 종류(`page_key`) | 색 · 글꼴 · 여백 |
| 표 개수 · 표 행수 · 표 머리행 | 문장 표현 |
| 사진 장수 · 사진 상자 크기 | 사진 파일 자체 |
| 면별 수치 존재(`250억원`·`15,933만원`) | 수치 위치의 픽셀 좌표 |

> 🔴 **렌더러가 지문을 만족하면 색과 글꼴이 달라도 같은 IM입니다.**
>   이것이 「다른 엔진의 산출물」을 계약으로 쓸 수 있게 만드는 유일한 방법입니다.

### 4.3 실증 — V4 산출물을 참조본에 걸었습니다

```
$ python3 qa/diff_ref.py --ref tests/corpus/target_yangpyeong_ref.pptx \
                         --out v4_goldilocks.pptx

참조  target_yangpyeong_ref.pptx  12면 · 표 12(76행) · 사진 4
산출  v4_goldilocks.pptx          15면 · 표  1(13행) · 사진 8
──────────────────────────────────────────────────────────────
  [차단] 면 결손        capital   — 참조 1면 · 산출 0면
  [차단] 면 결손        checklist — 참조 1면 · 산출 0면
  [차단] 면 결손        pricing   — 참조 1면 · 산출 0면
  [차단] 면 결손        upside    — 참조 1면 · 산출 0면
  [주의] 면 순서        참조 …rentRoll·gallery·process / 산출 …gallery·summary·building…
  [차단] 표 개수        참조 12 · 산출 1
  [차단] 표 행수        참조 76행 · 산출 13행 (불변조건 18 — 렌트롤 전량)
  [주의] cover 수치     참조 3개 중 3개 부재 · 예 ['15,933만원','2.24%','250억원']
  [차단] summary 표 행  참조 4행 · 산출 0행
  [차단] building 표 행 참조 12행 · 산출 0행
  [차단] location 표 행 참조 5행 · 산출 0행
  [차단] rentRoll 표 행 참조 14행 · 산출 13행
  [차단] process 표 행  참조 12행 · 산출 0행
──────────────────────────────────────────────────────────────
차단 11 · 주의 4
```

**이것이 렌더 팀이 받아야 할 작업 목록입니다.** 「위반 20건」보다 훨씬 구체적입니다 —
어느 면이 없고 어느 표가 문장으로 바뀌었는지 말합니다.

자기 자신과 비교하면 **결손 0**입니다 (공허하지 않은 검사).

### 4.4 시스템이 반영하는 절차

| # | 단계 | 담당 | 산출 |
|:-:|---|---|---|
| 1 | 참조본을 `tests/corpus/`에 편입 (`*_ref.pptx`) | 완료 ✅ | 3종 |
| 2 | `fingerprint --emit-spec` → `acceptance_*.yaml` 커밋 | 완료 ✅ | 양평동 1종 |
| 3 | **렌더러가 `acceptance` YAML을 읽어 자기 산출을 검사** | 렌더 팀 | `pptx-renderer.ts` Step 7 |
| 4 | CI에 `diff_ref` 추가 — 차단 > 0이면 병합 불가 | 렌더 팀 | GitHub Action |
| 5 | 결손이 0이 되면 **그 산출물이 골든 후보**가 됩니다 | 렌더 팀 | `target_*.pptx` |

> 🔴 **참조본은 절대 `target_*.pptx`가 되지 않습니다.**
>   `polarity: 'reference'`로 남고, 골든은 언제나 **렌더러가 만든 것**입니다.
>   §5 절차가 끝나면 참조본은 역할을 다하고 보관 자료가 됩니다.

### 5.3 🔴 팩의 핵심 — 의도된 결함 3건

```jsonc

```

> **골든 입력은 완벽한 데이터가 아닙니다.**
> 완벽한 입력만 넣으면 게이트가 한 번도 발동하지 않고, 그러면
> 게이트가 살아 있는지 알 수 없습니다. **결함을 넣어야 게이트를 시험합니다.**

이것이 09 §1.4 「모든 플래그를 true로」와 정반대인 이유입니다.

### 5.4 가이드라인 — 필드별 결손 처리 규칙

| 상태 | 렌더러가 해야 할 것 | 하면 안 되는 것 |
|---|---|---|
| `null` (미확인) | 확인사항으로 이관 · 해당 칸 비움 | 「해당 없음」으로 바꾸기 · 문장으로 메우기 |
| `hasOpex: false` | Gross Yield만 · 라벨 「총임대료 기준」 | NOI·Cap Rate 산출 |
| `hasAsOf: false` | `G21` 차단 또는 「기준일 미확인」 명시 | 조용히 오늘 날짜 채우기 |
| `_conflict.resolution: null` | `G48` 차단 · 양쪽 값 병기 | 한쪽을 우선순위로 채택 |
| `permit_required: null` | 「해당 여부 · 기준면적 · 확인 필요」 | 「허가 가능」·「허가 불필요」 단정 |
| `negative_leverage: true` | 경고 블록 + 금리별 ROE 3안 | ROE 단독 표시 |

## 6. 방법 ③ — 골든 파이프라인 정비

### 6.1 04에 없는 것 — 수명주기

04는 **생성 절차**(§3.3 Step 1~6)만 있고 **그 뒤**가 없습니다.
골든은 만드는 것보다 **유지하는 것**이 어렵습니다.

```
생성 ─▶ 검수 ─▶ 동결 ─▶ ┬─▶ 회귀 감시 (매 PR)
                        ├─▶ 갱신 (정본이 바뀔 때만)
                        └─▶ 폐기 (표본이 대표성을 잃을 때)
```

### 6.2 🔴 가장 중요한 규칙 — 골든이 깨졌을 때

**골든이 깨지면 둘 중 하나입니다. 코드가 회귀했거나, 골든이 낡았거나.**
이 둘을 구별하는 규칙이 없으면 사람들은 **골든을 갱신해서 통과시킵니다.**
그 순간 골든은 죽습니다(baseline rot). 04에 이 규칙이 없습니다.

```
골든 테스트 실패
  │
  ├─ 정본(credeal/ssot/*.yaml)이 이 PR에서 바뀌었는가?
  │    ├─ 아니오 →  🔴 코드 회귀. **골든을 고치지 마십시오.** 코드를 고칩니다
  │    └─ 예     →  정본 변경이 CHANGELOG 에 파괴적 변경으로 기재됐는가?
  │                   ├─ 아니오 → 🔴 기재부터 하십시오
  │                   └─ 예     → 골든 재생성 허용 · 승인자 2인 · 재검수
  │
  └─ 렌더러 코드만 바뀌었는데 지문이 달라졌다면 → **회귀입니다**
```

**골든 갱신 커밋에는 반드시 정본 변경이 동반돼야 합니다.**
정본이 그대로인데 골든만 바뀌는 커밋은 **차단**하십시오. CI로 강제할 수 있습니다.

```yaml
# .github/workflows/golden.yml (요지)
- name: 골든 단독 변경 차단
  run: |
    if git diff --name-only origin/main | grep -q 'tests/corpus/target_'; then
      git diff --name-only origin/main | grep -q 'credeal/ssot/' \
        || { echo "🔴 정본 변경 없이 골든만 바꿀 수 없습니다"; exit 1; }
    fi
```

### 6.3 골든 등록 조건 — 무엇이 골든이 될 수 있는가

| 조건 | 확인 방법 |
|---|---|
| 1. **렌더러가 생성** — 손 수정 0 | 같은 입력으로 재렌더 시 지문 동일 |
| 2. `layout_check` 위반 0 · 주의 0 | `qa/layout_check.py` |
| 3. `standard_check` 위반 0 · 충족 3 | `qa/standard_check.py` |
| 4. 참조본 대비 결손 0 | `qa/diff_ref.py` |
| 5. **의도된 결함이 게이트를 발동** | 입력 팩 `known_defects` 대조 |
| 6. 멱등 — 2회 렌더 시 구조·수치·게이트 판정 동일 | `l5-golden-regression` |
| 7. 사람 검수 서명 (2인) | 커밋 메시지 `Reviewed-by:` |

🔴 **조건 5가 04에 없습니다.** 위반 0만 보면 「게이트가 죽어서 0」과
   「정말 깨끗해서 0」을 구별하지 못합니다.

### 6.4 CI 배치

```
매 커밋   L1 계산 · L2 게이트 판정
매 PR     L3 편성 · L4 산출물 · diff_ref(참조본) · 대조군 falsifiability
          └ 차단 > 0 이면 병합 불가
야간      L5 멱등 · 골든 회귀 · 실물 3종 E2E
정본 변경 골든 재생성 + 2인 승인 요구
```

### 6.5 드리프트 방지

| 위험 | 방지 |
|---|---|
| 골든을 고쳐서 통과시킴 | §6.2 CI 규칙 |
| 임계값을 완화해서 통과시킴 | 임계값은 `credeal/ssot/*.yaml` 단독 소유 · 코드 리터럴 0건 |
| 새 게이트를 warn으로 넣어 회피 | 게이트 심각도 변경도 정본 변경으로 취급 |
| 참조본이 target으로 승격됨 | `expected_ref.json` `polarity: 'reference'` · 파일명 `_ref` 유지 |
| 가상 표본이 실증으로 인용됨 | 파일명·문서에 「가상」 명시 |

## 7. 권고 실행 순서

`04 §9`의 「Phase B(골든 5종) → Phase C(SSOT)」로는 결함이 동결됩니다.

```
✅ Phase A   PPTX 파서 (완료)

   Phase A′  선결 — 타입·연결·기준 해소                     ← 신설
      · ClaimStatus 6종 · Claim.id · provenance          (D39 P0)
      · im-core → PPTX 연결                               (D38 R1)
      · ProvenanceKind 단일화 (08 10종 / 09 8종)          (D40 §3.1)
      · 두 검사기 겹침 판정 대조 — 주의 7 vs 19            (D40 §2.2)
      · 임계값 통일 crop 0.40/0.45 · overlap 0/0.015      (D40 §2.3)

   Phase B′  골든 **1종만** — 양평동                        ← 축소
      · 입력 팩 투입 → 렌더 → diff_ref 결손 0 → 검수 → 동결
      · 손 수정 금지 (§2.4)
      · 이것으로 면수·아키타입·불변조건 개수 논쟁 종결

   Phase C   SSOT 코드 연결 (병행 가능)

   Phase B″  나머지 4종 — 표본 정의 정정 후 (§5.5)

   Phase D   종단 테스트 + 수명주기 CI (§6)
```

**양평동 1종을 먼저 하는 이유** — 골든의 최대 효용은 회귀 방지가 아니라
**명세 충돌의 종결**입니다(§1.2). 한 종이면 충분하고,
5종을 한꺼번에 만들면 5개의 미확정을 5배로 굳힙니다.

## 9. 하지 말 것

- **골든을 손으로 고치지 마십시오.** 렌더러가 만든 것만 골든입니다(§2.4).
- **골든이 깨졌을 때 골든을 갱신하지 마십시오.** 정본이 바뀌지 않았다면 회귀입니다(§6.2).
- **플래그를 억지로 true로 채우지 마십시오.** 결함을 넣어야 게이트를 시험합니다(§5.3).
- **참조본을 `target_*.pptx`로 승격하지 마십시오.** 다른 엔진 산출물입니다.
- **`ProvenanceKind`를 정하기 전에 provenance를 채우지 마십시오.** 전량 재작업입니다.
- **「주의 0」을 수용 기준으로 쓰기 전에 두 검사기를 대조하십시오.**
  지금은 같은 파일에 대해 7과 19라고 말합니다.
- **당산동을 사옥형으로 바꾸지 마십시오.** 실물이 아닌 골든은 근거가 약합니다.
- **5종을 한꺼번에 동결하지 마십시오.**
