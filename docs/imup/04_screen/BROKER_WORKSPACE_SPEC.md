## 1. 딜카드는 무엇인가

### 1.1 역할

중개인이 물건을 받은 순간부터 성사·무산까지 **돌아오는 단 하나의 화면**입니다.

```
주소 입력 ──▶ [딜카드 생성] ──▶ 자료 채우기 ──▶ IM 발행 ──▶ 발송 ──▶ 관리 ──▶ 결과
                    │                                                          │
                    └──────────────── 이 화면 하나 ─────────────────────────────┘
```

### 1.2 왜 하나여야 하는가

지금은 작성·발행·매칭·너처링·약정이 **각자 화면을 요구**합니다. 중개인은 물건 하나를 보려고 다섯 곳을 돌아다닙니다. 그러면 안 씁니다.

> **신규 라우트를 만들지 마십시오.** 새 기능은 딜카드의 탭이나 섹션으로 들어옵니다 (`P1-2` §7.1의 판단을 그대로 승계).

## 2. 두 점수 충돌 — 이번 정리의 핵심

### 2.1 문제

지금 시스템에는 **0~100점 A~D 등급이 두 개** 있습니다.

| 점수 | 묻는 질문 | 정본 | 배점 근거 |
|---|---|---|---|
| **자료등급** | 이 자료로 **IM을 발행할 수 있는가** | `IM_DATA_PIPELINE.md` §3 | 슬롯군 충족도 × provenance |
| **딜 준비도** | 이 딜이 **성사되겠는가** | `P1-2` §3 | 7축 (자료·가격·의사·권리·규제·금융·수요) |

둘 다 100점 만점, 둘 다 A/B/C/D입니다. **나란히 놓으면 중개인은 반드시 혼동합니다.** 골든 IM에서 자료등급 76.6 B가 나왔는데, 같은 딜의 준비도가 72 B라면 두 개가 같은 것으로 읽힙니다.

### 2.2 해소 — 표기 체계를 분리합니다

```
자료등급    A / B / C / D          ← 문자 유지. IM 발행 게이트와 직결
딜 준비도   준비완료 / 보완필요 / 위험 / 정체   ← 문자 폐기, 상태어로 변경
```

| 상태어 | 점수 | 의미 |
|---|---|---|
| **준비완료** | 80~100 | 지금 매수자를 만나도 됩니다 |
| **보완필요** | 60~79 | 한두 축이 약합니다 |
| **위험** | 40~59 | 성사 확률이 낮습니다 |
| **정체** | < 40 또는 `stale_days > 60` | 되살리거나 접어야 합니다 |

**상태어가 문자보다 낫습니다.** "B"는 아무 행동도 지시하지 않지만 "보완필요"는 다음 행동을 암시합니다. 준비도의 목적이 행동 유도이므로 이쪽이 맞습니다.

> 💥 **`P1-2` §7.2의 "준비도 등급 배지 (A/B/C/D)"는 폐기됩니다.** 산정 로직은 그대로이고 표기만 바뀝니다.

### 2.3 중복 계산 제거

7축의 **축1 「자료 완비도」(20점)** 는 Owner Readiness 10항목을 셌고, 자료등급은 슬롯군을 셉니다. **같은 것을 두 번 다르게 셉니다.**

```ts
// 변경 전 — P1-2 §3.2
export const axis1_before = (ownerReadiness.checkedCount / 10) * 20;

// 변경 후 — 자료등급을 단일 진실로 사용
export const axis1_after = (dataGrade.score / 100) * 20;
```

Owner Readiness 체크리스트는 **입력 보조 UI로 남기고 점수원에서 제외**합니다. 진실이 둘이면 반드시 어긋납니다.

### 2.4 카드에서의 배치

두 점수를 **같은 시야에 두지 않습니다.**

```
개요 탭    딜 준비도  ← 주 지표. 크게.
자료 탭    자료등급   ← IM 발행 맥락에서만
```

## 5. 개요 탭 — 준비도 7축

### 5.1 배점 (v0.4 반영)

| # | 축 | 배점 | 출처 | v0.4 변경 |
|---:|---|---:|---|---|
| 1 | 자료 완비도 | 20 | **자료등급** | 🔄 Owner Readiness → 자료등급 |
| 2 | 가격 현실성 | 20 | 실거래 밴드 | — |
| 3 | 매도 의사 확실성 | 15 | 전속·응답성 | — |
| 4 | 권리 청결도 | 15 | 등기 · **공동담보 그룹 반영** | 🔄 C32 적용 |
| 5 | 규제 통과 가능성 | 10 | 토허 · 용도지역 | — |
| 6 | 금융 조달 가능성 | 10 | LTV · Equity | — |
| 7 | 매수 수요 두께 | 10 | 크로스브로커 풀 | — |

**합계 100.** 축5는 데이터 부재 시 제외하고 90점으로 재스케일합니다 (기존 규칙 유지).

### 5.2 축4에 공동담보를 반영합니다

당산동·연남동 사례에서 확인된 것입니다. 채권최고액을 단순 합산하면 실제의 두 배가 나와 **권리 청결도가 부당하게 낮게** 나옵니다.

```ts
// C32 — 공동담보 그룹당 1회만 합산
export function axis4_cleanliness(deal: DealFacts): number {
  const byGroup = new Map<string, number>();
  for (const o of deal.owners) byGroup.set(o.jointCollateralGroup, o.maxClaim);
  const totalLien = [...byGroup.values()].reduce((a, v) => a + v, 0);
  return 15 * (1 - Math.min(1, totalLien / deal.price));
}
```

`Map`을 쓰는 이유는 **같은 그룹의 두 번째 호실이 값을 덮어쓰되 더하지 않게** 하기 위함입니다. 배열로 모으면 실수로 합산하기 쉽습니다.

### 5.3 블랙박스 금지

```
딜 준비도  72  보완필요                            [근거 펼치기 ▾]

  자료 완비도      15.3 / 20    자료등급 76.6 (B)
  가격 현실성      20.0 / 20    실거래 밴드 대비 +2.2%
  매도 의사        11.0 / 15    전속 아님 · 응답 평균 2일
  권리 청결도      12.0 / 15    공동담보 8.4억 / 매각가 42억
  규제 통과         8.0 / 10    토허 비대상 · 2종일반주거
  금융 조달         4.0 / 10    역레버리지 — 대출금리 > Cap
  매수 수요         1.7 / 10    조직 풀 매칭 후보 2명
```

**점수만 보여주면 중개인은 안 믿습니다.** 각 축에 근거 한 줄을 반드시 답니다 (`P1-2` §리스크 3번의 결정을 승계).

## 7. 탭 구조

### 7.1 개요

| 섹션 | 내용 |
|---|---|
| 준비도 7축 | §5 |
| 물건 요약 | 면적·용도지역·준공·주차 |
| 오늘의 행동 | 너처링 액션 (`P1-2`) |

### 7.2 자료

| 섹션 | 내용 |
|---|---|
| 자료등급 | 점수 + 슬롯군별 충족 |
| 우선순위 3개 | `GradeAdvice` (`IM_DATA_PIPELINE` §3.5) |
| 슬롯 입력 | `IM_AUTHORING_SPEC` 위임 |
| 결손 항목 | **"확인 중"도 표시** — 숨기지 않습니다 |
| 공부 재조회 | 발급일 표시 + 재조회 버튼 |

### 7.3 IM

**복수 variant를 다루는 유일한 화면입니다.**

```
투자 관점별 IM

  임대수익형   v1.2  발행됨 2026-05-12   열람 12 · 완독 58%   [열기] [재발행]
               ⚠ 확인 필요 2건 · ○ 기회 1건

  개발형       —     초안                                      [작성 시작]

  [+ 다른 관점으로 IM 만들기]
```

| 규칙 | |
|---|---|
| 슬롯 값은 **딜 수준에서 공유** | 두 번 입력하게 하지 않습니다 |
| 편성·등급·발행 이력은 **variant별** | 관점이 다르면 결과가 다릅니다 |
| 검수 서명은 **딜 수준** | 사실 확인은 한 번이면 충분합니다 |
| 발행물은 **수정 불가** | 고치면 재발행 (`POST_PUBLISH_SPEC` §7.1) |

### 7.4 매수자

| 섹션 | 출처 |
|---|---|
| 내 매수자 | `P0-1` |
| 조직 매수 수요 | `P0-1` 크로스브로커 · `[G2 연결 요청]` |
| 풀 공개 토글 | 공개 만료일 · **미리보기 모달 필수** |

> **`MatchResult`에는 매수자 식별정보가 없습니다.** 딜카드가 이를 우회해 표시하는 경로를 만들지 마십시오 (출시 불변조건 1).

### 7.5 이력

| 섹션 | 내용 |
|---|---|
| 발행 이력 | variant × 버전 · diff 요약 |
| 너처링 액션 | 수행/미룸/완료 |
| 보수약정 | `[만들기]` · 상태 배지 (`수임제안서-P0-3_통합명세.md`) |
| 전문가 의뢰 | `[검토 의뢰]` (`P1-1`) |
| 결과 | 성사/무산/보류 + 사유 |

```
                                              republish ◀─────┘
```

딜 상태는 `IM_DATA_PIPELINE.md` §4.1이 소유합니다. 딜카드는 **표시와 전이 버튼만** 담당합니다.

| 상태 | 카드 표시 |
|---|---|
| `draft`~`authoring` | 준비도 + 자료 탭 강조 |
| `verifying` | 검수 요청 배너 |
| `ready` | `[발행]` 버튼 활성 |
| `published` | IM 탭 · 신호 표시 시작 |
| `closed`/`lost`/`held` | **신호 생성 중단** · 결과 요약 표시 |

## 10. 접근성 · 성능

### 10.1 접근성

| 항목 | 규칙 | 이유 |
|---|---|---|
| 색상 | **상태를 색으로만 구분하지 않습니다** | 상태어·아이콘 병기 |
| 본문 최소 | 14px | 중개인 연령대가 높습니다 |
| 테마 | **라이트 고정** | `P0` §3.9 판단 승계 |
| 터치 타깃 | 44×44px 이상 | 현장에서 모바일로 봅니다 |
| 숫자 | 천 단위 구분 · 단위 병기 | "42억"과 "4,200,000,000" 혼용 금지 |

### 10.2 성능

| 작업 | 예산 |
|---|---:|
| 카드 진입 → 헤더·상태 바 | **300 ms** |
| 준비도 7축 (사전 계산) | 포함 |
| 탭 전환 | 150 ms |
| IM variant 목록 | 400 ms |

**준비도는 화면 진입 시 계산하지 않습니다.** 매일 07:00 배치로 미리 계산합니다 (`P1-2` §스케줄 승계).

### 10.3 장애 내성

```
LURIS 실패     → 축5 제외 · 90점 재스케일 · "규제 확인 불가" 표시
등기 API 실패  → 축4 이전 값 유지 · 발급일 경과 표시
매칭 실패      → 축7 0점 아님. 축 제외
```

**어떤 외부 API 실패도 딜카드 렌더를 막지 않습니다** (`P0` §graceful degradation 승계).
