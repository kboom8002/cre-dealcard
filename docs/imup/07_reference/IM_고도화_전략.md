## 0. 결론 세 줄

1. **하드코딩 상수는 0.85 하나가 아니라 22개**였고, 개발형 기본 용적률 400%는 실물 대비 **60% 과대**입니다.
2. **오류가 증식하는 폐순환**이 확인됐습니다 — 명세 예시 → 퓨샷 → Judge 통과 → Golden 자동 승격 → RAG → 다음 생성물.
3. **Vercel 60초 < AI 90초**라 품질 게이트가 프로덕션에서 상시 스킵 중일 가능성이 높습니다.

## 1. 🔴 오류 증식 루프 — 최우선 차단 대상

### 1.1 확인된 폐순환

```
① 명세 문서 예시가 오염          (03_income_sections.md — 4행 중 3행 오류)
       ↓
② 퓨샷·골든 예시로 프롬프트 주입
       ↓
③ 생성물에 오류 재현             ("401호" · "갱신요구권 7년")
       ↓
④ LLM-as-Judge 통과             (문체가 유창하면 4.5점 가능)
       ↓
⑤ Golden 자동 승격               (source_type='auto_approve')
       ↓
⑥ RAG 인덱스 적재                (과거 IM 문서만 검색 · 법령 검증 없음)
       ↓
⑦ 다음 생성물 프롬프트에 주입     → ③으로 복귀 · 증폭
```

### 1.2 각 고리의 실증 근거

| 고리 | 근거 | 출처 |
|:-:|---|---|
| ① | 렌트롤 예시 4행 중 금액 일치 1행 | 답변 없음 · 제 대조 |
| ② | 퓨샷 `buildIMFewShotBlock()` | 00_architecture §6.2 |
| ④ | Judge는 정확성을 **SSoT 대조로만** 평가 · SSoT 자체가 오염되면 통과 | T2 답변 |
| ⑤ | `source_type DEFAULT 'auto_approve'` | T1-5 ④ |
| ⑥ | RAG는 **과거 IM 문서만** 검색 · 법령 DB 없음 | T3-2 ① |
| ⑦ | topK 5건 **전문 주입 · 토큰 제한 없음** | T3-2 ③ |

### 1.3 🔴 법령 최신성 미보장이 특히 위험합니다

> RAG 컨텍스트에 포함된 과거 IM 문서에 법령이 인용되어 있더라도, 현행법과 일치하는지 **검증하는 메커니즘이 없습니다.** — T3-2 ④

이번 세션에서 저 자신이 **블로그 근거로 "3+3년 개정"을 사실로 받아들일 뻔했습니다.** 시스템은 그 검증 장치조차 없습니다.

**한 번 잘못 쓰인 법적 판정이 RAG를 통해 영구히 재생산됩니다.**

### 1.4 차단점 3개 — 응급 조치

| # | 조치 | 공수 | 효과 |

### 2.1 Vercel 타임아웃 — 품질 게이트가 안 돌고 있습니다

| | 값 |
|---|:-:|
| Vercel `maxDuration` | **60초** |
| AI 일반 모드 타임아웃 | **90초** |
| AI `FAST_MODE` | 30초 |

**90초는 도달 불가능합니다.** Vercel이 60초에 먼저 끊습니다.

```
FAST_MODE = false  →  60초 타임아웃 오류
따라서 프로덕션은 사실상 FAST_MODE 강제
    →  LLM-as-Judge 스킵
    →  CRE Quality Gate 스킵
```

**설계상 존재하는 6단계 가드레일 중 ②⑤가 상시 비활성 상태일 가능성이 높습니다.**

| 조치 | 공수 |
|---|--:|
| `maxDuration` 60 → 300 상향 (Vercel Pro 기준) 또는 AI 타임아웃 55초로 하향 | 0.25일 |
| **결정론 게이트를 FAST_MODE에서도 실행** (합계·basis·소재지 — 밀리초 단위) | 0.5일 |
| FAST_MODE 실제 사용률 로깅 | 0.25일 |

> **결정론 검증은 LLM을 안 쓰므로 타임아웃과 무관합니다.** 끌 이유가 없습니다.

## 3. 가정값 외부화 — 하드코딩 22개

### 3.1 실물 대조 결과

| 상수 | 시스템 | 실물 | 오차 |
|---|--:|--:|--:|
| **개발형 평당 공사비** | 800만원 | **1,200만원** (잠원동) | **−33%** |
| **개발형 기본 용적률** | **400%** | **250%** (2종 완화 상한) | **+60%** |
| 개발형 기타비용 | 매입+공사의 15% | 5억 정액 | — |
| Trading 비교사례 | 매입 평당가 × 1.15 | comps 실측 필요 | — |
| Trading 목표 매각가 | **매입가 × 1.2** | comps 실측 필요 | — |
| NOI 추정 계수 | 0.85 | 근거 없음 | — |
| Opex Ratio 6종 | 12~35% | 출처 없음 | — |

### 3.2 🔴 가장 위험한 둘

#### ① 개발형 용적률 400% 기본값

```
잠원동 대지 616.1㎡ · 제2종일반주거지역
  시스템 기본값 400% → 신축 연면적 2,464㎡ (745평)
  실제 가능    250% → 신축 연면적 1,540㎡ (466평)
  → 60% 과대. 분양수입·사업이익률이 1.6배 부풀려집니다
```

**용도지역을 무시한 기본값입니다.** 준공업 400%, 2종주거 250%, 3종주거 300%가 전부 다른데 하나로 고정돼 있습니다.

#### ② Trading 목표 매각가 = 매입가 × 1.2

```
당산동 115억 · comps 미입력 상태
  시스템 자동 산출: 시세갭 15% 할인 · 목표 매각 138억 · 차익 23억
  실측 comps 기반: 출구가 130.3억 · 차익 8.99억 (취득비용 반영)
```

**데이터가 없어도 차익 23억이 IM에 실립니다.** 근거 없는 수익 제시입니다.

### 3.3 개선 원칙 — 3계층 분리

```ts
export interface Assumption<T> {
  value: T;
  source: 'measured' | 'market_default' | 'legal' | 'user_input';
  basis: string;              // 출처 문장 (화면 노출)
  confidence: 'high' | 'medium' | 'low';
  editable: boolean;
}

export const ASSUMPTIONS = {
  constructionCostPerPyeong: {
    value: 12_000_000,
    source: 'market_default',
    basis: '서울 소형 근생 신축 2026년 통상 단가 (실매물 IM 기준)',
    confidence: 'medium',
    editable: true,
  },
  targetFarByZoning: {
    source: 'legal',
    basis: '용도지역별 법정 상한 · 토지이용계획 API 연동',
    // 기본값 없음 — 조회 실패 시 산출 거부
  },
} as const;
```

| 원칙 | 내용 |
|---|---|
| 1 | **`legal` 계층은 기본값을 두지 않습니다.** 조회 실패 시 산출 거부 |
| 2 | **모든 가정값은 화면에 출처와 함께 노출**합니다 |
| 3 | **중개인이 편집 가능**하게 하되 편집 사실을 기록합니다 |
| 4 | `market_default`는 **연 1회 갱신 대상**으로 목록화합니다 |

### 3.4 Opex와 GOP 마진 혼동 의심

```
financials.ts:132  Opex Ratio — 호텔 = 35%
financials.ts:421  GOP 마진율 기본값    = 35%
```

**Opex 35%면 GOP 마진이 65%가 됩니다.** 업계 통상 GOP 마진은 30~40%입니다. 두 값이 같은 35%인 것은 우연으로 보기 어렵습니다.

**호텔 포스처에서 GOP가 약 2배로 산출되고 있을 가능성**을 확인해야 합니다.

## 4. 단일 코어 전환 — 이중 변환 폐기

### 4.1 현행 구조의 문제

```
모바일: financials.ts → 마크다운 생성 → 화면
PPTX:  모바일이 만든 마크다운 → 정규식 split('|') 재파싱 → 슬라이드
```

> PPTX 렌더러는 `financials.ts`를 **직접 호출하지 않고**, 모바일 측에서 이미 렌더링된 Markdown 텍스트를 `split('|')`과 정규식으로 파싱합니다. — T1-1 ④

| 문제 | 결과 |
|---|---|
| **정보 손실** | 숫자 → 문자열 → 숫자. 반올림·단위 표기가 굳어짐 |
| **취약성** | 마크다운이 조금만 바뀌면 PPTX가 빈약해짐 (T2-1 ②) |
| **basis 소실** | `CapRateBasis` 같은 메타데이터가 문자열에 안 실림 |
| **이중 유지** | 두 경로를 따로 고쳐야 함 |

### 4.2 목표 구조

```
                  ┌──────────────────────┐
                  │  IMCore (타입 객체)   │
                  │  · 검증된 수치 + basis│
                  │  · DeficiencyLedger  │
                  │  · numericalAnchors  │
                  └───────┬──────────────┘
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    모바일 렌더      PPTX 렌더        마크다운 (보관용)
```

**마크다운은 최종 산출물이지 중간 자료구조가 아닙니다.**

### 4.3 전환 방식 — 점진적

| 단계 | 내용 | 공수 |
|:-:|---|--:|
| 1 | `IMCore` 타입 정의 · `financials.ts` 반환형 확장 | 3.0일 |
| 2 | PPTX가 `IMCore`를 직접 받도록 `data-binder` 개조 | 6.0일 |
| 3 | 마크다운 파싱 경로를 **폴백으로만** 유지 | 1.0일 |
| 4 | 아키타입 등록을 설정 기반으로 (현재 4곳 하드코딩) | 3.0일 |

> **아키타입 추가에 최소 4곳을 고쳐야 합니다** (T2-1 ③). A16 신설이 어려운 이유입니다.
> A11·A12는 파일만 있고 매핑이 없는 **dead code**입니다 (T3-3 ④).

## 11. 남은 미확인 사항

답변서로 해소되지 않은 것입니다. **DB 쿼리 3건이면 대부분 해결됩니다.**

```sql
-- ① Golden 오염 규모
SELECT source_type, COUNT(*), AVG(judge_score)
FROM im_golden_sets GROUP BY source_type;

-- ② 실제 생성량·비용
SELECT DATE_TRUNC('month', created_at) m, COUNT(*), SUM(cost_usd)
FROM im_generation_cost_log GROUP BY 1 ORDER BY 1 DESC LIMIT 6;

-- ③ RAG 인덱스 규모
SELECT COUNT(*) FROM im_documents;
```

| # | 미확인 | 영향 |
|:-:|---|---|
| 1 | Golden 중 `auto_approve` 비중 | 정리 대상 규모 |
| 2 | 월 생성 건수 | 개선 ROI 산정 |
| 3 | RAG 인덱스에 오염 문서 비중 | 재구축 필요 여부 |
| 4 | 실거래가 API 소형 상업용 커버리지 | comps 확보 경로 |
| 5 | 등기정보광장 대체 수단 | 권리분석 자동화 가능성 |

> **5번은 답변에서 "비활성 상태"로 확인됐습니다.** 권리분석은 당분간 수동 입력이 전제입니다. `data-absence.ts`의 정적 안내는 적절한 처리입니다.
